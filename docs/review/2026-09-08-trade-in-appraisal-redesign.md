# ตรวจสภาพ iPhone และประเมินราคาหน้าร้าน

ปรับหน้าประเมินรายการรอรับซื้อให้พนักงานตอบแบบตรวจเดียวกับหน้าเว็บ `/sell` แล้วใช้ราคาจากเซิร์ฟเวอร์ ผู้ใช้ยืนยันว่าปัจจุบันรับซื้อเฉพาะ iPhone

## พฤติกรรม

- แสดงรุ่น ความจุ ผู้ขาย IMEI และ Serial Number ก่อนตรวจ พร้อมจำนวนข้อที่ตรวจแล้ว
- ดึงคำถาม ตัวเลือก และค่าหักที่เปิดใช้จากชุดเดียวกับหน้าเว็บ ไม่มีสูตรราคาอีกชุดในหน้าแอดมิน
- ทุกข้อต้องตรวจใหม่ รวมถึงข้อที่เลือกได้หลายอาการ: หากไม่พบอาการ ต้องยืนยัน “ตรวจแล้ว ไม่พบปัญหา”
- เมื่อครบ ระบบแสดงราคาประเมิน รายการหัก เกรด และราคาเงินสด/เทิร์นตามประเภทของรายการ เปลี่ยนคำตอบแล้วคำนวณใหม่ ราคาที่มาช้าจากคำตอบก่อนหน้าไม่สามารถนำมาบันทึกได้
- บันทึกคำตอบและรายละเอียดราคาที่คำนวณจากเซิร์ฟเวอร์ พร้อมผู้ประเมินและเวลาประเมินในรายการเดิม การประเมินยังไม่รับเครื่องเข้าสต็อก
- โหมด “สภาพไม่ตรง แก้คำตอบ” ของรายการออนไลน์ใช้แบบตรวจเดียวกัน ส่วนการยืนยันสภาพเดิมและการปรับราคาโดยเจ้าของตามสิทธิ์เดิมยังอยู่
- ไม่สามารถใช้แบบตรวจนี้กับยี่ห้ออื่น รายการที่ไม่มีความจุ แบบตรวจว่าง หรือรุ่นที่ไม่มีราคากลาง
- แบบฟอร์มเลื่อนได้ภายใน ปุ่มบันทึกอยู่ด้านล่าง รองรับมือถือและธีมสว่าง/มืด ระหว่างบันทึกป้องกันการแก้ไข ปิด หรือส่งซ้ำ

## API และข้อมูล

- `GET /trade-ins/appraisal-questions?tradeInId=...` — คำถามสำหรับรุ่น/ความจุในรายการ ตรวจสิทธิ์สาขาก่อน
- `POST /trade-ins/:id/appraisal-preview` — ส่งคำตอบ; รุ่น ความจุ ประเภทรายการอ่านจากข้อมูลเครื่องในระบบ
- `PATCH /trade-ins/:id/appraise-online` — `REVISED` ส่งคำตอบและ `previewToken` คำนวณซ้ำและปฏิเสธหากข้อมูล/ราคาต่างจากที่แสดง
- ใช้ `ShopBuybackService.quoteForAnswers` และเครื่องคำนวณ Decimal เดิม บันทึก `conditionAnswers`, `quoteBreakdown`, เกรด และราคาเป็นชุดเดียวกัน
- ใช้สิทธิ์ SHOP + OWNER/BRANCH_MANAGER ตรวจสาขาของรายการ และป้องกันการเขียนทับจากการประเมินพร้อมกัน
- ใช้คอลัมน์เดิม ไม่ต้องเพิ่ม migration

## การตรวจ

เพิ่ม unit tests สำหรับแบบตรวจ ราคาเปลี่ยน/ตอบกลับล่าช้า สถานะบันทึกและข้อผิดพลาด รวมถึง API tests สำหรับราคา snapshot สิทธิ์สาขา การเปลี่ยนราคาและการประเมินพร้อมกัน

`npm run local:check` ตรวจ flow แบบตรวจ iPhone เพิ่มทั้ง desktop และ mobile ด้วยเซิร์ฟเวอร์จริงบนฐานข้อมูล local แยก รายการรับซื้อใน local เป็นข้อมูลจำลอง ราคาและเงื่อนไขอ้างอิง iPhone 82 รายการนำเข้าจาก Yellobe ณ 8 กันยายน 2026 ในฐาน local แยก ตาม [รายงานข้อมูลต้นทาง](../reference/yellobe-2026-09-08/README.md) ผลตรวจรอบล่าสุดอยู่ใน `.tmp/local-preview/check.json`

ผลตรวจก่อนเพิ่มข้อมูล Yellobe: `npm run local:check` PASS 19 checks รวม browser 1440px/390px; ผลตรวจหลังเชื่อมข้อมูลอ้างอิงดู `.tmp/local-preview/check.json`

แก้ test proxy ของ flow แนบไฟล์แชทให้รอหลัง HTTP สำเร็จแล้วค่อยส่ง response กลับเบราว์เซอร์ เพื่อทดสอบการสลับห้องระหว่างรอผลอย่างเดิมโดยไม่ค้างตอนอ่าน browser cookies; ยังตรวจปุ่มเปิดแผง ห้องต้นทาง และแผงผลตรวจครบ

งานนี้เป็นการแก้ไขและตรวจบน local ยังไม่ได้ push/merge/deploy

## ราคาอ้างอิงรายรุ่นจาก Yellobe

นำเข้า 82 ราคาเกรด A และ 32 ชุดเงื่อนไขสำหรับ 26 รุ่นใน local โดยแยก 3 ความจุที่ไม่ตรงสเปก Apple ไม่กระทบใบเสนอเดิม ใช้ SystemConfig เดิมเก็บชุดอ้างอิง ไม่เพิ่ม migration

ทั้งพนักงานและหน้าเว็บต้องยืนยันเงื่อนไขรับซื้อก่อนประเมิน เก็บผู้ตรวจ/เวลาในผลตรวจหน้าร้าน สูตรรวมค่าหักบาทแล้วใช้เปอร์เซ็นต์สูงสุดตรงกับผลราคาจากเว็บไซต์ 13 กรณี แท็บแบบตรวจแสดงเงื่อนไขแยกตามรุ่นและความจุพร้อมวันที่อ้างอิง ส่วนแบบตรวจทั่วไปแยกออกให้ชัด

เครื่องมือนำเข้าเริ่มจาก dry-run และรองรับการเขียนเฉพาะ managed isolated local ที่ตรวจ runId/ฐานข้อมูลแล้ว มีสำรองก่อน transaction และนำเข้าซ้ำไม่เพิ่มรายการซ้ำ

เพิ่มชุดทดสอบ storefront ถาวร (`npm run test --workspace=apps/web-shop`) และใส่ storefront tests/build กับ importer tests ใน `local:check` เพื่อให้การตรวจรอบต่อไปครอบคลุมด้วย
