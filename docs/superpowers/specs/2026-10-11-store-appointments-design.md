# BESTCHOICE — ระบบนัดเข้าร้านหลังผ่านเครดิตเบื้องต้น

วันที่: 11 ตุลาคม 2026 · เขตเวลา Asia/Bangkok

สถานะ: ร่างสเปกฉบับปรับหลัง scrutinize — เจ้าของให้แก้ข้อค้นพบทั้ง 4 จุดแล้ว ยังไม่ได้เริ่มพัฒนา

## 1. เป้าหมายและขอบเขตที่เจ้าของยืนยัน

ให้ลูกค้าที่ผ่านเครดิตเบื้องต้นนัดเข้าร้านล่วงหน้าได้ ร้านรู้ว่าใครจะมา เวลาใด และใครรับผิดชอบ โดยจำนวนคิวสัมพันธ์กับพนักงานที่พร้อมให้บริการจริง

- พนักงานนัดให้ได้ และลูกค้าจองเองผ่านลิงก์เฉพาะลูกค้าได้ ใช้ตารางคิวเดียวกัน
- กันเวลา 45 นาทีต่อท่าน พนักงานหนึ่งคนรับได้หนึ่งท่านต่อช่วงเวลา
- ผู้จัดการกำหนดพนักงานและช่วงเวลารับนัดของแต่ละคน แยกตามสาขา
- ลูกค้าเลือกสาขา วัน และเวลา ระบบเลือกพนักงานว่างให้ พนักงานหน้าร้านเปลี่ยนผู้รับผิดชอบได้เมื่อคนใหม่ว่าง
- เริ่มจองได้เมื่อผ่านเครดิตเบื้องต้น ไม่ต้องรออนุมัติยอดผ่อน
- รองรับเช็กอิน เริ่มบริการ เสร็จงาน เลื่อนนัด ยกเลิก และไม่มาตามนัด

การนัดหมายเป็นขั้นตอนเข้ารับบริการ ไม่ได้ทำให้เครดิตเต็มผ่าน ไม่อนุมัติสัญญา และไม่รับรองว่ามีเครื่องพร้อมส่งมอบ การทำสัญญายังคงใช้กติกาอนุมัติเดิม

## 2. ค่าเริ่มต้นที่เสนอในสเปกนี้

รายละเอียดต่อไปนี้เป็นข้อเสนอในการออกแบบ ไม่ใช่คำตอบที่เจ้าของระบุไว้แล้ว:

| รายการ | ค่าเริ่มต้นรุ่นแรก |
| --- | --- |
| วันและเวลาเปิดรับ | ใช้ช่วงเวลาที่ผู้จัดการลงไว้ ไม่มีตารางเท่ากับไม่เปิดรับ |
| คิวสุดท้าย | เริ่ม 18:30 น. ตามเวลาไทย สิ้นสุด 19:15 น. ต้องมีพนักงานว่างครบช่วง |
| ระยะเวลาต่อคิว | 45 นาทีคงที่ ไม่มีเวลาพักเผื่อเพิ่มอัตโนมัติ |
| วันเปิดให้จองล่วงหน้า | 14 วันตามปฏิทินไทย รวมวันนี้ |
| ระยะเผื่อก่อนนัด | เลือกเวลาเริ่มที่ห่างจากเวลาปัจจุบันอย่างน้อย 30 นาที |
| นัดที่ยังไม่จบต่อลูกค้า | สูงสุด 1 นัด รวมทุกสาขา |
| สิทธิ์สร้างนัดจากลิงก์ | 30 วันนับจากออกลิงก์ เพิกถอนและออกใหม่ได้ |
| สิทธิ์ดู/จัดการนัดที่ยืนยันแล้ว | ลิงก์เดิมใช้กับนัดที่ผูกไว้ได้ถึง 24 ชั่วโมงหลังเวลาจบนัด แม้สิทธิ์สร้างนัดหมดอายุแล้ว |
| เลื่อน/ยกเลิกด้วยตนเอง | ทำได้ก่อนเวลาเริ่มและก่อนเช็กอิน หลังจากนั้นให้ติดต่อสาขา |
| จัดพนักงานอัตโนมัติ | เลือกผู้ว่างที่มีนัดคงเหลือในวันนั้นน้อยที่สุด เสมอกันเรียงรหัสพนักงาน |

เวลาและจำนวนวันอยู่ในนโยบายกลางของโมดูล ไม่ hard-code ซ้ำตามหน้าจอ รุ่นแรกยังไม่เพิ่มหน้าตั้งค่านโยบายทั้งหมด

## 4. หน้าจอและการใช้งาน

### ผู้จัดการ: ตารางรับนัด

อยู่ใน BESTCHOICE SHOP เมนู “นัดเข้าร้าน” แท็บ “ตารางพนักงาน” เลือกสาขาและวัน แล้วเพิ่มช่วงเวลาให้พนักงานแต่ละคน เช่น 10:00–12:15 และ 13:00–17:30 ช่วงที่ไม่ระบุถือว่ารับนัดไม่ได้

เลือกเฉพาะผู้ใช้ที่ active ไม่ถูกลบ และสังกัดสาขานั้น ใช้ข้อมูลชื่อและรหัสผู้ใช้ ไม่ดึงข้อมูลเงินเดือนหรือข้อมูล HR ส่วนตัว หนึ่งคนมีหลายช่วงเวลาในวันเดียวได้ แต่ช่วงเวลาห้ามซ้อนกัน

มีคำสั่งคัดลอกตารางของวันหนึ่งไปวันอื่น โดยตรวจทุกแถวก่อนบันทึกทั้งหมด ไม่มี recurring schedule หรือระบบจัดกะอัตโนมัติในรุ่นแรก

### พนักงาน: สร้างนัด

จากหน้าลูกค้าหรือห้องแชทที่ผูกลูกค้าแล้ว กด “นัดเข้าร้าน” ระบบแสดงสิทธิ์นัดและนัดที่ยังเปิดอยู่ ถ้ามีนัดแล้วให้เปิดนัดเดิมเพื่อจัดการ แทนการสร้างเพิ่ม

เลือกสาขาที่ตนมีสิทธิ์ทำงาน วัน และเวลา ยืนยันแล้วได้รับเลขนัด พร้อมข้อมูลวัน เวลา สาขา และผู้รับผิดชอบ หรือกด “สร้างลิงก์ให้ลูกค้าเลือกเวลา” แล้วคัดลอกลิงก์ไปส่งเอง

ห้องที่ยังไม่ผูกลูกค้าต้องผูกลูกค้าก่อน สร้างนัดจากหมายเลขห้องอย่างเดียวไม่ได้

### ลูกค้า: จองผ่านลิงก์

หน้าเว็บรองรับมือถือ ไม่บังคับสมัครบัญชี: เลือกสาขา → วันและเวลา → ตรวจรายละเอียด → ยืนยัน แสดงเฉพาะสาขา active ในขอบเขตลิงก์และมีตารางรับนัด ไม่แสดงรายชื่อพนักงานหรือรายชื่อลูกค้าคนอื่น

หลังจอง แสดงเลขนัด สาขา ที่อยู่/เบอร์โทรที่มีในระบบ วันเวลา และปุ่มเลื่อน/ยกเลิก พร้อมข้อความ “กรุณามาตามเวลานัด การอนุมัติยอดผ่อนและเอกสารจะดำเนินการตามขั้นตอนของร้าน” ไม่ใช้ข้อความรับรองว่าอนุมัติสัญญาแล้ว

### หน้าร้าน: คิวประจำวัน

ตารางรายวันแบ่งตามพนักงาน มีรายการที่ใช้งานสะดวกบนมือถือ กรองสาขา วันที่ พนักงาน และสถานะได้ แสดงลูกค้า เวลา ผู้รับผิดชอบ สัญญาณเตือนผลเครดิตเปลี่ยน และกลุ่ม “ต้องจัดพนักงานใหม่” เมื่อผู้รับผิดชอบถูกปิดบัญชี/ลบ/ย้ายสาขาหรือเสียสิทธิ์ SHOP

ปุ่มตามสถานะ: เช็กอิน → เริ่มบริการ → เสร็จงาน; ยกเลิกและไม่มาตามนัดเป็นทางออกอื่น มีประวัติผู้เปลี่ยนและเวลา พนักงานเปลี่ยนผู้รับผิดชอบหรือเลื่อนเวลาได้ก่อนเริ่มบริการและต้องตรวจตารางใหม่เสมอ ข้อยกเว้น: ผู้จัดการรับช่วงงาน IN_SERVICE ที่เจ้าหน้าที่เดิมเสียสิทธิ์ได้ตาม §7

## 5. เงื่อนไขเครดิตสำหรับนัด

“ผ่านเบื้องต้น” สำหรับการนัดหมายถึงมีผลตัดสิน APPROVED จากขั้นตอนเครดิตเดิม แม้แถวนั้นเป็น FULL และยังไม่มี CreditApproval ไม่เพิ่มการให้คะแนนเครดิตหรือทางอนุมัติใหม่ และไม่บังคับให้สร้าง PRE เพื่อให้จองได้

เก็บผลตัดสินสำหรับนัดไว้บน CreditCheck ด้วย `lastAppointmentDecision` (NONE / APPROVED / REJECTED / UNKNOWN) และ `appointmentDecisionRecordedAt` เพื่อให้การเปิดตรวจใหม่หรือเปลี่ยนสถานะเป็นรอตรวจไม่ล้างหลักฐานผ่าน/ไม่ผ่านเดิม:

- แถวใหม่ที่ยังไม่ตัดสินเริ่ม NONE; เมื่อขั้นตอนเดิมตัดสิน APPROVED หรือ REJECTED ให้เขียนผลนี้และเวลาบันทึกใน transaction เดียวกับ status การเปลี่ยนเป็น PENDING/MANUAL_REVIEW คงผลตัดสินที่มีอยู่
- ครอบคลุมการสร้างเครดิตทั้งระดับลูกค้า/สัญญา, วิเคราะห์ AI ทั้งสองเส้นทาง, override และนำเข้าผลจากแชท ผู้เขียนต้องใช้ customer → credit-check lock ร่วมกับการจอง ไม่ใช้ JourneyEntry ที่เขียนหลัง commit เป็นฐานตัดสิทธิ์
- สำหรับข้อมูลก่อน migration: แถว APPROVED/REJECTED ใช้สถานะปัจจุบันเป็นหลักฐาน; แถว PENDING/MANUAL_REVIEW ที่ยืนยันผลเก่าไม่ได้เริ่ม UNKNOWN ห้ามเดาว่าไม่เคยถูกปฏิเสธจากการไม่มี log โดยเวลาที่เติมคือเวลาบันทึก snapshot ไม่อ้างว่าเป็นเวลาตัดสินในอดีต ไม่ backfill จากคะแนนหรือ badge อย่างเดียว

เปิดใช้การจองหลัง backfill และ writer ทุกเส้นทางรองรับฟิลด์นี้แล้วเท่านั้น ระหว่าง rollout ค่า null/ข้อมูลที่ยังไม่แปลงต้องตีความเป็น UNKNOWN ไม่ใช่ NONE และต้องตรวจว่าไม่มี API instance รุ่นเก่าเขียนเฉพาะ status อยู่ก่อนเปิด feature

ตัวประเมินสิทธิ์อ่านแถวที่ไม่ถูกลบของลูกค้าทั้ง PRE/FULL เรียงรอบตรวจ `createdAt DESC, id DESC` และเลือกแถวแรกที่ `lastAppointmentDecision != NONE`:

| ผลที่เลือก | สิทธิ์นัด |
| --- | --- |
| APPROVED | จองได้ ไม่ต้องมี CreditApproval หรือยอดผ่อน |
| REJECTED | จองไม่ได้ ผลผ่านของรอบเก่าไม่ข้ามผลปฏิเสธรอบใหม่ |
| UNKNOWN หรือไม่มีผล | ให้พนักงานตรวจสอบ/ดำเนินขั้นตอนเครดิตเดิมก่อน ไม่สรุปว่าผ่าน |

ตัวอย่างที่ต้องรองรับ: รอบ A เป็น FULL/APPROVED → เปิดรอบ B เป็น FULL/PENDING/NONE → ยังจองได้จาก A; B ถูกตัดสิน REJECTED → จองไม่ได้; B ถูกตั้งกลับรอตรวจ → ยังคง REJECTED สำหรับนัดจนมีผลผ่านใหม่ การวิเคราะห์ซ้ำแถว A แล้วกลับ PENDING ไม่ล้าง APPROVED ที่เคยบันทึกไว้ การแก้ผลของรอบเก่าไม่ล้มผลตัดสินของรอบที่สร้างใหม่กว่า

ข้อมูลเก่าที่เป็น UNKNOWN ต้องแสดงเหตุผลให้พนักงานทราบว่าไม่มีหลักฐานผลก่อนหน้าเพียงพอ ไม่เรียกว่าเครดิตไม่ผ่าน และไม่อ้างว่าการย้ายข้อมูลกู้ประวัติที่หายไปได้

ตรวจสิทธิ์ตอนออกลิงก์ อ่านเวลาว่าง สร้างนัด และเลื่อนนัด การยกเลิกต้องยังทำได้แม้เครดิตเปลี่ยน ผลเครดิตที่เปลี่ยนภายหลังไม่ลบนัดเดิมอัตโนมัติ: แสดงให้เจ้าหน้าที่ทบทวน และลูกค้าเห็นเพียงให้ติดต่อสาขา นัดเดิมยังกันเวลาจนพนักงานยกเลิกหรือจัดการ

บันทึก `creditCheckId`, ชนิดตรวจ และ snapshot ผล/เวลาบันทึกที่ใช้ตอนสร้างหรือเลื่อนเพื่อสอบย้อนกลับ ไม่คัดลอก statement หรือข้อมูลวิเคราะห์ลงนัด ประเมินผลจริงทุกแถวภายในโดยไม่ให้การกรองสิทธิ์อ่านซ่อนผลปฏิเสธที่ใหม่กว่า แต่คืนเฉพาะสิทธิ์นัด/เหตุผลทั่วไปแก่ผู้ที่อ่านแหล่งเครดิตไม่ได้

## 6. การคำนวณเวลาและป้องกันจองซ้อน

- เก็บเวลาเป็น UTC แสดงและเลือกวันด้วย Asia/Bangkok ช่วงเวลาทั้งหมดเป็น `[start, end)` จึงนัดต่อกันที่เวลาเดียวกับจบคิวก่อนหน้าได้
- ไม่เปิดเวลาเริ่มหลัง 18:30 น.; เพิ่มตัวเลือก 18:30 แม้ไม่ลงกริดเดิมเมื่อมีช่วงรับนัดครอบคลุมถึง 19:15 น. และไม่มีนัดซ้อน
- แต่ละช่วงรับนัดสร้างเวลาเริ่มทุก 45 นาทีจากต้นช่วง เช่น 10:00–12:00 เปิด 10:00 และ 10:45; ไม่เปิด 11:30 เพราะเวลาที่เหลือไม่ครบ
- ช่วงพักแบ่งเป็นคนละช่วงรับนัด ห้ามนำเวลาว่างสองฝั่งช่วงพักมาต่อกัน
- รวมเวลาเริ่มที่ซ้ำกันจากพนักงานแต่ละคนเป็นตัวเลือกเดียว จำนวนว่างคือจำนวนคนที่ให้บริการช่วงนั้นได้จริง
- จองได้เมื่อครบทั้ง 45 นาทีอยู่ในช่วงรับนัด และไม่มีนัดเปิดของพนักงานทับช่วงนั้น ใช้เงื่อนไข `existing.start < requested.end AND existing.end > requested.start` ไม่ตรวจแค่เวลาเริ่มตรงกัน
- นัดสถานะ BOOKED, CHECKED_IN และ IN_SERVICE ยังกันเวลา COMPLETED, CANCELED และ NO_SHOW ไม่กันเวลา; ไม่เปิดเวลาที่ผ่านไปแล้วกลับให้จอง
- จบก่อนเวลาจะไม่เปิดคิวสั้นแทรกนอกกริดเดิม หากทำงานเกิน 45 นาที ให้แสดงว่าเกินเวลาและนัดถัดไปต้องได้รับการจัดการโดยหน้าร้าน ไม่เลื่อนนัดลูกค้าอัตโนมัติ
- การเปลี่ยนตารางหรือลบช่วงรับนัดตามปกติที่ทำให้นัดไม่มีคนรองรับ ให้ปฏิเสธพร้อมแสดงนัดที่ต้องย้าย/ยกเลิกก่อน
- การปิดบัญชี/ลบผู้ใช้ ถอนสิทธิ์ หรือย้ายสาขาพนักงานต้องสำเร็จได้โดยไม่รอจัดนัด ระบบหยุดนับพนักงานนั้นใน availability และแสดงนัดเปิดเดิมเป็น “ต้องจัดพนักงานใหม่” โดยคำนวณจากสถานะ/สาขา/สิทธิ์ปัจจุบันของผู้ใช้ ไม่ลบนัด ไม่เลื่อนเวลา ไม่ยกเลิก session revocation และไม่เพิ่มการเขียนนัดทั้งหมดใน transaction ปิดบัญชี
- นัดที่ต้องจัดพนักงานใหม่ยังนับเป็นนัดเปิดของลูกค้า แต่ไม่กันเวลาของพนักงานคนอื่น การโอนให้คนใหม่ต้องตรวจคิวว่างจริง ผู้จัดการเห็นความเสี่ยงที่ยังหาคนแทนไม่ได้ในกลุ่มแยก; ฝั่งลูกค้ายังเห็นวันเวลาเดิมพร้อมข้อความ “สาขากำลังจัดผู้ดูแลนัด” ไม่เปิดเผยสาเหตุการปิดบัญชี

ทุกการสร้าง/เลื่อน/ย้ายพนักงาน/ยกเลิกและแก้ตารางใช้ transaction บน PostgreSQL พร้อม lock ร่วมกัน ไม่พึ่ง UI หรือ cache เพื่อกันซ้อน:

1. ล็อกลูกค้าและผลเครดิตที่เกี่ยวข้องตามลำดับ lock ของระบบเครดิตเดิม แล้วอ่านสิทธิ์ซ้ำเฉพาะสร้าง/เลื่อนนัด; การยกเลิก เช็กอิน จัดคนแทน และปิดงานตรวจสิทธิ์ผู้กระทำกับสถานะนัด แต่ไม่ใช้ผลเครดิตเป็นเหตุขวางการจัดการนัดเดิม
2. ล็อกนัดเดิมเมื่อเป็นการแก้ และล็อกแถว User ของพนักงานที่เกี่ยวข้องเรียง ID คงที่ ก่อนอ่านตารางและนัดซ้ำ; การจองแบบจัดคนให้อัตโนมัติต้องล็อกผู้สมัครที่พิจารณาเรียงลำดับเดียวกัน
3. ผู้แก้ตารางล็อก User ก่อนแก้ ไม่ย้อนมาล็อกลูกค้า จึงไม่สร้างวงจรรอ lock กันกับการจอง
4. ตรวจ invariant ของ action นั้นและเขียนนัดพร้อมประวัติใน transaction เดียว การย้ายล้มเหลวต้องคงนัดเดิมครบทั้งเวลาและผู้รับผิดชอบ; การยกเลิก/ปิดงานต้องทำได้แม้พนักงานเดิมเสียสิทธิ์หรือตารางไม่รองรับแล้ว
5. ใช้ partial unique index ให้ลูกค้ามีนัดเปิดไม่เกินหนึ่งนัด และ idempotency key สำหรับ create/reschedule/cancel เพื่อรองรับกดซ้ำหรือ retry

เส้นทางแก้ผู้ใช้/ย้ายสาขาใช้ User lock เพื่อให้การจองอ่านสถานะหลังล็อกซ้ำได้ แต่ห้ามมี appointment guard ปฏิเสธการระงับบัญชี หากจอง commit ก่อนการปิดผู้ใช้ นัดจะเข้ากลุ่มต้องจัดพนักงานใหม่; หากปิดก่อน การจองจะไม่เลือกคนนั้น การแสดงกลุ่มนี้คำนวณตอนอ่านและไม่พึ่ง cron หรือ event ที่อาจส่งไม่สำเร็จ การกันซ้อนรายคนต้องทดสอบกับฐานข้อมูลจริงแบบ concurrent transactions ข้าม API instance

เมื่อช่วงเวลาเต็มระหว่างกดยืนยัน ส่ง 409 พร้อมข้อความ “ช่วงเวลานี้เต็มแล้ว กรุณาเลือกเวลาใหม่” แล้วโหลดเวลาว่างอีกครั้ง หาก transaction ขัดแย้งให้ retry แบบจำกัดจำนวน ไม่วนไม่สิ้นสุด

## 7. สถานะและการแก้ไข

| สถานะ | ไปต่อได้ | ผู้ดำเนินการ |
| --- | --- | --- |
| BOOKED | CHECKED_IN, CANCELED, NO_SHOW | พนักงาน; ลูกค้ายกเลิกได้ก่อนเริ่ม |
| CHECKED_IN | IN_SERVICE, CANCELED | พนักงาน |
| IN_SERVICE | COMPLETED, CANCELED | พนักงาน; ยกเลิกต้องมีเหตุผล |
| COMPLETED / CANCELED / NO_SHOW | สิ้นสุด | สร้างนัดใหม่เมื่อเข้าเงื่อนไข |

NO_SHOW ทำได้เมื่อถึงเวลาเริ่มแล้วและยังไม่เช็กอิน ไม่เปลี่ยนเป็นไม่มาตามนัดอัตโนมัติ เลื่อนนัดไม่ใช่สถานะใหม่: คง BOOKED หรือ CHECKED_IN ตามเดิมและเก็บประวัติเวลาเก่า/ใหม่ การเลื่อนไปวันอื่นหลังเช็กอินต้องคืนสถานะ BOOKED และล้างเวลาเช็กอินปัจจุบัน โดยเก็บหลักฐานเช็กอินเดิมใน event

“ต้องจัดพนักงานใหม่” เป็นปัญหาการมอบหมายที่คำนวณแยกจากสถานะบริการ เก็บ staffUserId เดิมไว้เป็นหลักฐานจนเปลี่ยนผู้รับผิดชอบ เจ้าหน้าที่เดิมที่เสียสิทธิ์ดำเนินการต่อไม่ได้ ผู้จัดการย้าย IN_SERVICE ไปคนว่างได้โดยคงสถานะและเวลาเริ่มจริง พร้อมเหตุผลและ event; ตรวจการชนของเวลานัดเดิมและห้ามคนใหม่มีงาน IN_SERVICE อื่น การเปลี่ยนผู้รับผิดชอบอย่างเดียวไม่ใช้กฎจองล่วงหน้า 30 นาที ไม่ตรวจเครดิตใหม่เพื่อขัดขวางการจัดคนแทน และไม่เปลี่ยนเวลานัดลูกค้า

ตรวจ version ของนัดทุก mutation หากเจ้าหน้าที่สองคนแก้พร้อมกันให้แจ้งโหลดข้อมูลใหม่ ไม่เขียนทับเงียบ ๆ สำหรับ retry ให้ตรวจ idempotency record หลังยืนยันสิทธิ์ผู้เรียกและก่อนตรวจ version/เงื่อนไขธุรกิจซ้ำ เพื่อคืนผลเดิมของคำขอที่สำเร็จแล้ว

## 8. โครงสร้างข้อมูลและขอบเขตโมดูล

เพิ่มโมเดลแบบ additive ตามมาตรฐาน UUID, timestamps และ soft delete ของ repo:

- `StaffAppointmentWindow`: branchId, staffUserId, startsAt, endsAt, createdById และ version; index สำหรับสาขา/วันและพนักงาน/เวลา
- `StoreAppointment`: reference, customerId, branchId, staffUserId, windowId, sourceRoomId แบบ optional, creditCheckId, creditCheckTypeAtBooking, creditDecisionAtBooking, creditDecisionRecordedAtBooking, startsAt, endsAt, status, source STAFF/CUSTOMER_LINK, createdById แบบ optional, checkedInAt, serviceStartedAt, completedAt, canceledAt, noShowAt, reason และ version; `assignmentIssue` เป็นค่าคำนวณจากผู้รับผิดชอบปัจจุบัน ไม่เก็บ boolean ที่อาจค้าง
- `StoreAppointmentLink`: customerId, tokenHash แบบ unique, allowedBranchIds ที่ตรวจสิทธิ์ตอนออกลิงก์, bookingExpiresAt, revokedAt, issuedById; ลิงก์ลูกค้าไม่รับ customerId จาก request body
- `AppointmentLinkAccess`: linkId, appointmentId, manageExpiresAt; unique(linkId, appointmentId) จำกัดสิทธิ์จัดการให้เฉพาะนัดที่ผูก ไม่ใช่ทุกนัดของลูกค้าตลอดไป
- เพิ่ม `CreditCheck.lastAppointmentDecision` และ `appointmentDecisionRecordedAt` ตาม §5 พร้อม migration แยกกรณีข้อมูลเก่า UNKNOWN จากแถวใหม่ NONE
- `StoreAppointmentEvent`: นัด, ชนิดเหตุการณ์, ผู้กระทำ STAFF/CUSTOMER_LINK, staffUserId/linkId ตามกรณี, old/new ค่าเวลา/สาขา/ผู้รับผิดชอบ/สถานะ, createdAt เป็นประวัติ append-only
- `AppointmentRequest`: actor scope, key, requestHash และผลลัพธ์อ้างอิงนัด/เวอร์ชัน เพื่อรับ retry อย่างคงที่ ไม่เก็บ token ดิบในผลลัพธ์; key เดิมกับ payload ต่างกันส่ง 409

ใช้ FK แบบ Restrict กับข้อมูลอ้างอิงสำคัญ ประวัติไม่มีการแก้/ลบผ่าน API ปกติ ระบุข้อยกเว้น timestamps ของ immutable event ตามกฎฐานข้อมูล สร้าง check constraint ให้ end > start และนัดยาว 45 นาที; partial unique index ของนัดเปิดต้องมี migration และ integration test กำกับ

แยกบริการ: eligibility, availability, schedule, appointment lifecycle, public link และ query/read model ทั้ง staff และ public controller เรียกกติกาชุดเดียวกัน

API กลุ่ม staff: ตารางรับนัด, eligibility, availability, list/detail, create, reschedule, reassign, status transitions และ issue/revoke link. API กลุ่ม public: อ่านบริบทลิงก์/นัดของตน, availability, create, reschedule, cancel. Public ไม่มี endpoint ที่ค้นลูกค้าอื่นหรือเปลี่ยนสถานะหน้าร้าน

## 9. สิทธิ์และลิงก์ลูกค้า

- OWNER จัดการสาขา SHOP ที่มี company grant; BRANCH_MANAGER จัดตารางและนัดในสาขาตน; SALES ดูและจัดการนัดในสาขาที่ได้รับสิทธิ์ แต่แก้ตารางพนักงานไม่ได้
- ทุก endpoint staff ใช้ auth/roles/company/branch scope เดิม และตรวจขอบเขต entity ใน service แม้ route มีแค่ ID
- ลิงก์ใช้ token สุ่ม 256-bit เก็บ SHA-256 hash เท่านั้น token ดิบคืนครั้งเดียวเมื่อสร้าง ไม่ใส่ใน audit, log, analytics หรือ Sentry
- หน้า public ใช้ URL fragment รับ token และส่ง token ใน header เฉพาะคำขอ API; ไม่เก็บใน localStorage/sessionStorage ไม่โหลด analytics ของบุคคลที่สาม ตั้ง no-referrer/noindex/no-store ตามความเหมาะสม
- Public controller แยกจาก staff ใช้ token guard, validation, rate limit และ response allow-list เปิดข้อยกเว้น CSRF เฉพาะ endpoint ที่ใช้ capability token โดยไม่มี cookie authentication ตาม pattern public share เดิม ไม่ปิด global guard
- แยกการตรวจสิทธิ์ตามการกระทำ: สร้างนัดต้องยังไม่ถึง bookingExpiresAt; ดู/เลื่อน/ยกเลิกนัดที่ผูกต้องมี AppointmentLinkAccess ที่ยังไม่ถึง manageExpiresAt และอยู่ในขอบเขตสาขา เวลาที่อนุญาตให้เลื่อน/ยกเลิกยังเป็นก่อนเริ่มและก่อนเช็กอินตาม §2; หลังจบหรือยกเลิกดูได้อย่างเดียวภายในอายุสิทธิ์
- เมื่อจองสำเร็จ ผูก AppointmentLinkAccess ใน transaction เดียวกับนัดด้วย manageExpiresAt = endsAt + 24 ชั่วโมง ใช้ token เดิมต่อได้ ไม่ต้องรับ token ใหม่หลังยืนยัน การเลื่อนสำเร็จทั้งจาก staff/public ปรับอายุ access ที่ยังไม่ถูกเพิกถอนให้ตรงวันนัดใหม่ใน transaction เดียว การเลื่อนล้มเหลวคงนัดและอายุเดิม
- ตัวอย่าง: ออกลิงก์วันแรก → วันที่ 29 จองนัดวันที่ 39 → สิทธิ์สร้างนัดหมดวันที่ 30 แต่ลิงก์เดิมยังดูและจัดการนัดที่ผูกได้ถึง 24 ชั่วโมงหลังนัดวันที่ 39 การขยายสิทธิ์จัดการไม่ขยายสิทธิ์สร้างนัดใหม่และไม่คืนชีพลิงก์ที่เพิกถอน
- ลิงก์เพิกถอน/ไม่ถูกต้อง หรือไม่มี capability ที่ยังใช้ได้ให้ข้อความทั่วไปเดียวกัน ถ้ามีสิทธิ์จัดการนัดเหลือแต่สิทธิ์สร้างหมด ให้เปิดนัดเดิมและซ่อนการสร้างใหม่ มีหน้า retry เมื่อเครือข่ายขัดข้อง
- ตรวจสาขาที่ผู้ออกมีสิทธิ์ในขณะออกลิงก์ ห้ามรับ allowedBranchIds จาก client โดยไม่ตรวจ หลังออกแล้ว capability เป็นสิทธิ์ของลูกค้าภายในขอบเขตนั้น การปิดบัญชีหรือย้ายสาขาของผู้ออกไม่ทำให้ลิงก์ลูกค้าเสียสิทธิ์ตามไปด้วย; ผู้มีสิทธิ์สามารถเพิกถอนลิงก์โดยตรงได้
- สาขาที่ปิดไม่รับการจอง/เลื่อนเข้ามาใหม่ แต่ลูกค้ายังดูหรือยกเลิกนัดเดิมได้ตามกำหนด และระบบแสดงให้ติดต่อร้าน
- การออกลิงก์ทดแทนเพิกถอนลิงก์ที่ระบุและผูกนัดเดิมใน transaction เดียว ผู้ออกต้องมีสิทธิ์ครบทั้งขอบเขตลิงก์เดิมและนัดนั้น ห้ามพนักงานต่างสาขาเพิกถอนทุกลิงก์ของลูกค้าผ่านคำสั่งออกลิงก์ใหม่ เมื่อออกลิงก์เพื่อจัดการนัดที่พนักงานจองไว้ ให้ผูก access ให้ทันทีหลังตรวจสิทธิ์ ไม่ยกเลิกหรือสร้างนัดซ้ำ
- ข้อมูลลูกค้าใน public response มีเท่าที่จำเป็นสำหรับนัด ชื่อปกปิดบางส่วน ไม่มีเลขบัตร statement คะแนนเครดิต หรือชื่อพนักงานทั้งสาขา

## 10. การเชื่อมหน้าเดิมและข้อจำกัดรุ่นแรก

เพิ่มเมนูใน SHOP ตาม navigation rule เดิม เชื่อมจากหน้าลูกค้าและ RoomDossier แสดงนัดจากโมดูลกลาง ไม่เขียนนัดซ้ำเป็น Todo การเลือกห้องต้องตรวจสิทธิ์เข้าห้องและความสัมพันธ์กับลูกค้าก่อนเสมอ

กำหนด read model ร่วมที่ระบุ `kind: FOLLOW_UP | STORE_APPOINTMENT`, ID, วันเวลา, สถานะ และ action ที่อนุญาตอย่างชัดเจน แหล่งข้อมูลยังแยกกัน แต่ทุกจุดแสดงผลใช้ชนิดนี้เลือก endpoint ไม่ส่งรหัส StoreAppointment ไปแก้ Todo:

| จุดเชื่อมจริง | สิ่งที่ต้องแก้และตรวจรับ |
| --- | --- |
| RoomDossier / ChatSalesContext / ฟอร์มจากปุ่มตั้งนัด | แยก “ติดตามลูกค้า” ซึ่งใช้ Todo เดิม กับ “นัดเข้าร้าน” ซึ่งเปิดตัวเลือกเวลาจากโมดูลกลาง แสดงนัดที่ยังเปิดของลูกค้าที่ผูกห้อง แม้นัดถูกสร้างจากหน้าลูกค้าหรือลิงก์และไม่มี sourceRoomId |
| `room-manager.service.ts` — ROOM_NEXT_APPOINTMENT และ include ห้องทุกเส้นทาง | โหลดสรุปนัดกลางตาม customerId ของห้องใน batch ร่วมกับงานติดตาม ตรวจสิทธิ์สาขา/บริษัท/ห้องก่อนส่ง ไม่อาศัย Todo include เดิมเพียงอย่างเดียวและไม่เพิ่ม query ต่อห้อง |
| ConversationItem, ChatPanel และการจัดลำดับห้องใน UnifiedInboxPage | ป้ายนัด/หัวห้อง/การเรียงใกล้ถึงนัดอ่าน read model เดียวกัน ระบุประเภทนัดไม่ให้สับสนกับกำหนดติดตาม |
| `staff-chat/appointments/due` และ AppointmentAlertBar | รวมรายการถึงเวลาที่ผู้ใช้มีสิทธิ์ พร้อมชนิดรายการ; Todo ใช้ action เดิม ส่วนนัดเข้าร้านใช้เช็กอิน/เปิดนัดตาม lifecycle ไม่ใช้ PATCH /todos/:id DONE แทนมาตามนัด |
| CustomerDetail และ customer-journey | เพิ่มแหล่งอ่าน StoreAppointmentEvent สำหรับจอง/เลื่อน/ยกเลิก/เช็กอิน/เสร็จงาน; “มาตามนัด” เกิดจาก CHECKED_IN ไม่ใช่ปิด Todo กรองด้วยสิทธิ์และใช้ event ID คงที่เพื่อไม่แสดงซ้ำจากหลายห้อง |
| Query cache และการเปิดจอค้างไว้ | เมื่อ mutation สำเร็จ invalidate ตาราง/รายละเอียดลูกค้า/ห้อง/แถบถึงเวลา/ประวัติที่เกี่ยวข้อง และ polling สูงสุดทุก 60 วินาทีสำหรับรายการนัดเปิด เพื่อให้การจองจาก public หรือการปิดบัญชีพนักงานสะท้อนบนจอ staff โดยไม่ต้อง refresh เอง |

Todo เดิมคงข้อมูลและ action เดิม ไม่ถือเป็นการจองเวลารับบริการและไม่กันคิวพนักงาน ไม่แปลงอัตโนมัติ หากต้องย้ายรายการติดตามเดิมมาเป็นนัดเข้าร้าน พนักงานสร้างผ่านกติกาใหม่และปิดงานติดตามเดิมเอง

ยังไม่มีการส่ง LINE/SMS/email อัตโนมัติ รุ่นแรกสร้างและคัดลอกลิงก์ รวมทั้งแสดงใบยืนยันนัดในเว็บ พนักงานเป็นผู้ส่งลิงก์ ไม่มีการส่งข้อความจริงระหว่างพัฒนาและทดสอบ

ไม่รวมระบบลงเวลางาน HR, การลา, เงินเดือน, walk-in queue, waitlist, นัดกลุ่ม, มัดจำ, สำรองเครื่อง, ปรับเงื่อนไขทำสัญญา และการส่งข้อความเตือนอัตโนมัติออกนอกแอป แถบเตือนภายในแอปเดิมยังเชื่อมนัดใหม่ตามตารางด้านบน ผู้จัดการสะท้อนวันลา/พักโดยแก้ช่วงรับนัดและจัดการนัดที่ได้รับผลกระทบ

## 11. เกณฑ์ตรวจรับ

1. สร้างผลผ่านจาก endpoint จริงที่ได้ FULL โดยไม่มี CreditApproval แล้วจองได้ เปิด FULL/PENDING รอบใหม่แล้วยังใช้ผลผ่านเดิมได้; ผลปฏิเสธใหม่บล็อกผลผ่านเก่า การ reset แถวเดิมไม่ล้างผลตัดสินที่บันทึกไว้ และ UNKNOWN ไม่ถูกเดาว่าผ่าน ทดสอบ PRE เพื่อความเข้ากันได้ได้ แต่ห้ามใช้ PRE fixture เพียงอย่างเดียว
2. พนักงานว่าง 3 คนในเวลาเดียวกันรับได้ 3 นัด คำขอที่ 4 ไม่สำเร็จแม้ยิงพร้อมกันจาก staff และ public
3. นัดต่างเวลาเริ่มที่ทับกันบนพนักงานคนเดียวกันถูกปฏิเสธ นัดต่อกันพอดีรับได้
4. เวลาใกล้พัก/ปิดที่เหลือไม่ครบ 45 นาทีไม่แสดง วันไม่มีตารางไม่มีเวลาจอง วันที่และเวลาตรงกับกรุงเทพฯ ใกล้เที่ยงคืนด้วย
5. กดซ้ำหรือ retry ไม่เกิดสองนัด ลูกค้าคนเดียวจองพร้อมกันต่างสาขายังมีนัดเปิดได้เพียงหนึ่ง
6. เลื่อนนัดสำเร็จแล้วเวลาเก่าคืน เลื่อนล้มเหลวคงนัดเดิม; เปลี่ยนพนักงานและแก้ตารางพร้อมกับจองไม่ทำให้เกิดนัดเกิน
7. การแก้ตารางตามปกติป้องกันนัดหลุด แต่การปิดผู้ใช้ผ่าน update และ updateFull รวมทั้งย้ายสาขา/ถอนสิทธิ์สำเร็จได้แม้มีนัด: session ถูกเพิกถอนตามเดิม ไม่เปิดเวลาของคนนั้นเพิ่ม นัดเดิมเข้ากลุ่มต้องจัดพนักงานใหม่ ผู้จัดการโอนนัดได้โดยไม่ทับคิว ทดสอบ race จองพร้อมปิดบัญชีทั้งสองลำดับ commit และรับช่วง IN_SERVICE
8. สถานะเปลี่ยนได้เฉพาะทางที่กำหนด มีประวัติ actor และเวลา; public เปลี่ยนสถานะหน้าร้านไม่ได้
9. สิทธิ์สร้างหมดอายุไม่อนุญาตสร้างใหม่ แต่ access ของนัดที่ผูกยังใช้งานได้ถึง endsAt + 24 ชั่วโมง; ลิงก์ถูกเพิกถอนใช้ไม่ได้ทุก capability แก้ customerId/branchId/appointmentId หรืออ่านนัดที่ไม่ผูกไม่สำเร็จ ไม่มีข้อมูลส่วนตัวหรือ token ใน log
10. จองจาก staff/public แล้วแสดงในตาราง หน้าลูกค้า แผงแชท ป้ายรายชื่อ หัวห้อง แถบถึงเวลา และ customer journey ตามสิทธิ์ การเช็กอินเขียนนัดกลางและประวัติจริง ไม่ PATCH Todo; นัดไม่มี sourceRoomId ยังแสดงตามลูกค้าได้ และข้อมูลเดียวไม่ซ้ำเมื่อมีหลายห้อง Todo และใบจองมัดจำเดิมยังทำงานตามเดิม
11. เครดิตเปลี่ยนเป็นไม่ผ่านหลังจอง: นัดเดิมยังอยู่ มีคำเตือนให้พนักงานทบทวน ลูกค้ายกเลิกได้แต่สร้าง/เลื่อนตามสิทธิ์ใหม่ไม่ได้
12. ทดสอบ flow จริงใน local ทั้งหน้าจอ desktop/mobile และ PostgreSQL แยกสำหรับทดสอบ พร้อม API backend ที่สร้างใหม่หลังเปลี่ยน schema
13. ออกลิงก์แล้ววันที่ 29 จองนัดวันที่ 39: วันที่ 31 ลิงก์เดิมดู/เลื่อน/ยกเลิกนัดนั้นได้ตามกติกา แต่สร้างใหม่ไม่ได้; เลื่อนโดย staff/public ปรับอายุจัดการตามนัดใหม่ ข้อผิดพลาด/rollback ไม่เปลี่ยนอายุ และการปิดบัญชีผู้ออกไม่ทำให้ลูกค้าสูญเสียสิทธิ์จัดการ
14. เครดิตเปลี่ยนพร้อมคำขอจอง/เลื่อน: ผู้เขียนเครดิตทุกเส้นทางและการจองใช้ lock ร่วมกัน ผลตัดสินกับ lastAppointmentDecision commit พร้อมกัน; migration ของแถวเก่า APPROVED/REJECTED/PENDING/MANUAL_REVIEW เป็นไปตาม §5 โดยไม่อาศัย log หลัง commit ที่อาจขาด

ชุดทดสอบ: unit สำหรับ eligibility/เวลา/state machine; database integration สำหรับ race, rollback, uniqueness และ locks; API authorization/token/idempotency; browser flow ผู้จัดการลงตาราง → พนักงานจอง/ออกลิงก์ → ลูกค้าจอง/เลื่อน/ยกเลิก → หน้าร้านเช็กอิน/ปิดงาน

หลังพัฒนารัน `npm run local:check` และเพิ่มการทดสอบนัดจริงบน backend ของ checkout นี้ เพราะ managed preview เดิมไม่ได้ยืนยันระบบนัดใหม่ ตรวจ migration กับฐานข้อมูลทดสอบเท่านั้น และคง local server ที่ตรวจแล้วไว้ให้เจ้าของทดลอง

## 12. สถานะส่งมอบเอกสาร

ฉบับนี้ปรับตาม scrutinize ครบ 4 ประเด็น: ใช้ผลผ่านจากเส้นทางเครดิตจริงและเก็บผลตัดสินระหว่างตรวจซ้ำ; ปิดบัญชีพนักงานได้ทันทีพร้อมจัดการนัดที่ต้องหาคนแทน; แยกอายุสิทธิ์สร้างนัดจากสิทธิ์จัดการนัด; และเชื่อมแชท/ประวัติทุกจุดที่อ่าน Todo เดิม พร้อมเกณฑ์ตรวจรับข้อ 1, 7, 9, 10, 13, 14

ยังไม่มีการแก้ product code, schema หรือฐานข้อมูล และยังไม่มีผลทดสอบระบบนัด การตรวจรอบนี้เป็นการตรวจเอกสารเทียบเส้นทางโค้ดจริง หลังเจ้าของตรวจเอกสารฉบับปรับแล้ว ขั้นถัดไปคือเขียนแผนพัฒนาเป็นงานย่อยพร้อมลำดับ migration/API/UI/integration และตรวจรับแผนก่อนเริ่มลงมือ
