| ทาง | ความถูกต้องขึ้นกับ | ตรวจสอบยังไง |
|---|---|---|

## ข้อเท็จจริงที่ตรวจแล้ว (ไม่ใช่การเดา)

### 1. `TRUNCATE` ผ่าน trigger กันลบของ `audit_logs` ได้

`audit_logs` และ `bad_debt_write_off_audit_logs` มี trigger กัน DELETE:

```sql
-- migration 20260520300000_audit_log_archive_immutable
CREATE TRIGGER audit_logs_no_delete
BEFORE DELETE ON "audit_logs"
FOR EACH ROW                       -- ← row-level
EXECUTE FUNCTION audit_logs_block_delete();
```

PostgreSQL **ไม่จุด row-level trigger ตอน TRUNCATE** และ grep แล้วไม่มี
`BEFORE TRUNCATE` / `FOR EACH STATEMENT` ที่ไหนเลย ⇒

- `DELETE FROM audit_logs` → ❌ `RAISE EXCEPTION`
- `TRUNCATE audit_logs` → ✅ ผ่าน

**ไม่ต้อง drop trigger** — ซึ่งดีมาก เพราะ drop แล้วลืมสร้างกลับ = เกราะกันแก้หลักฐานหายถาวร

> **ข้อค้นพบด้านความปลอดภัย (แยกเรื่อง):** คอมเมนต์ใน migration เขียนว่า *"Any code path
> (ORM, raw SQL, migration) that attempts DELETE will raise"* แต่ **TRUNCATE ไม่ใช่ DELETE**
> ⇒ ใครมีสิทธิ์ TRUNCATE ลบ audit trail ได้ทั้งตาราง · ถ้าต้องการปิดช่องนี้ ให้เพิ่ม
> `BEFORE TRUNCATE ... FOR EACH STATEMENT` **หลังล้างเสร็จ** (ใส่ก่อนจะบล็อกงานนี้เอง)

### 2. ชุดที่เก็บปิดตัวเอง — CASCADE ลามเข้ามาไม่ได้

```
users → branches → company_info → (จบ ไม่อ้างใครต่อ)
```

ไม่มีตารางที่เก็บตัวไหนมี FK ชี้ไปตารางที่จะล้าง ⇒ `TRUNCATE ... CASCADE` ลามเข้ามาไม่ได้

**สคริปต์ตรวจข้อนี้สดทุกครั้งที่รัน** (ไม่พึ่งการตรวจครั้งเดียว) — ถ้าวันหลังมีคนเพิ่ม FK
เช่น `User.employeeProfileId` สคริปต์จะหยุดพร้อมบอกว่า FK ตัวไหนเป็นปัญหา

### 3. `_prisma_migrations` ต้องเก็บ

ล้างแล้ว `migrate deploy` ครั้งถัดไปจะพยายามรัน migration ทั้งหมดซ้ำบน schema ที่มีตารางอยู่แล้ว

## ขั้นตอน

### ① ก่อนเริ่ม — ยืนยันจุดกู้คืน ⚠️ ห้ามข้าม

Cloud SQL มี automated backup + PITR (`.claude/CLAUDE.md`) — **ยืนยันว่ามีจุดกู้คืนที่ใช้ได้จริง
ก่อนรันอะไรทั้งสิ้น** ถ้าล้างผิดแล้วไม่มี backup คือจบ

### ② ดูก่อนว่าจะลบอะไร (ไม่เขียนอะไรเลย)

```bash
cloud-sql-proxy --gcloud-auth --port 5432 bestchoice-prod:asia-southeast1:bestchoice-db

DRY_RUN=1 EXPECTED_DB_NAME=bestchoice \
  DATABASE_URL="postgresql://<user>@127.0.0.1:5432/bestchoice" \
  npm --prefix apps/api run factory:reset
```

จะพิมพ์: จำนวนตารางทั้งหมด · ตารางที่เก็บพร้อมจำนวนแถว · ตารางที่จะล้างเรียงจากมากไปน้อย · ยอดรวมแถว

**ตรวจตรงนี้ว่า `users` / `branches` / `company_info` มีแถวตามที่ควรจะเป็น** ถ้าเป็น 0
แปลว่ามีอะไรผิด — อย่ารันต่อ

### ③ รันจริง

```bash
CONFIRM_FACTORY_RESET=YES_I_AM_SURE \
  ALLOW_PROD_RESET=YES_I_AM_SURE \
  NODE_ENV=production \
  EXPECTED_DB_NAME=bestchoice \
  DATABASE_URL="postgresql://<user>@127.0.0.1:5432/bestchoice" \
  npm --prefix apps/api run factory:reset
```

มี **หน่วง 10 วินาที** ให้กด Ctrl+C ยกเลิกได้ · สคริปต์ตรวจผลเองว่าทุกตารางเป็น 0 จริง

### ④ หลังล้าง — จำเป็นทั้งหมด ไม่ทำแล้วใช้งานไม่ได้

| # | ทำอะไร | ไม่ทำแล้วเกิดอะไร |
|---|---|---|
| 1 | `npm --prefix apps/api run seed:coa` | `chart_of_accounts` ว่าง ⇒ โพสต์ JE ไม่ได้เลย |
| 2 | ตั้ง `Branch.shopCashAccountCode` ทุกสาขา | **ขายสดไม่ได้** — `ShopAccountResolver` fail-closed |
| 3 | ตั้ง `User.defaultCashAccountCode` ทุกคน | บันทึกรับชำระไม่สะดวก (ต้องเลือกเองทุกครั้ง) |
| 4 | ตั้งค่าดอกเบี้ย / ค่าคอม / เปิดงวดบัญชี | เปิดสัญญาผ่อนไม่ได้ / โพสต์ JE ติดด่านงวดปิด |
| 5 | รัน `docs/accounting/shop-books-preflight-2026-08.sql` | ไม่รู้ว่าตั้งค่าครบหรือยัง |

> ขั้น 2-4 มี checklist อยู่แล้วใน preflight หัวข้อ
> **"4. ความพร้อมตั้งค่า — ตัวที่ทำให้ 'ขายไม่ได้' ถ้าไม่ตั้ง"**

### ⑤ ตรวจรับ

รัน preflight อีกรอบ ต้องได้:

- ผัง SHOP + FINANCE ครบ (รวมบัญชีใหม่ `S41-1203`; และ `S11-3101`/`S51-1106` ถ้าผู้สอบอนุมัติแล้ว)
- งบทดลองทั้งสองฝั่งเป็น 0 (ยังไม่มีรายการ)
- ไม่มี JE ลงผิดสมุด
- ทุกสาขาตั้งบัญชีเงินสดแล้ว

## สิ่งที่ **ไม่** ถูกล้าง (อยู่นอก DB)

สคริปต์นี้แตะเฉพาะฐานข้อมูล — ของพวกนี้ต้องจัดการแยกถ้าต้องการ:

- **ไฟล์ใน S3** (สลิป รูปสินค้า เอกสารสัญญา ลายเซ็น) — แถวใน DB หายแต่ไฟล์ยังอยู่
- **ข้อความ LINE ที่ส่งไปแล้ว** — ลูกค้ายังเห็นในแชท
- **เอกสารที่พิมพ์ออกไปแล้ว** (ใบเสร็จ ใบกำกับภาษี สัญญา)
- **แบบภาษีที่ยื่นไปแล้ว** ถ้าเคยยื่น

> ⚠️ **ถ้าเคยยื่น ภ.พ.30 หรือออกใบกำกับภาษีจากข้อมูลชุดนี้** ต้องปรึกษาผู้สอบก่อน —
> พ.ร.บ.การบัญชี กำหนดให้เก็บเอกสาร ≥ 5 ปี · ผู้สอบยืนยันแล้วว่าข้อมูลชุดนี้เป็น
> การทดสอบโปรแกรม แต่ถ้ามีการยื่นแบบจริงเกิดขึ้น ต้องแจ้งผู้สอบก่อนล้าง

## ถ้าล้างผิด

1. หยุดใช้งานระบบทันที (ยิ่งเขียนข้อมูลใหม่ ยิ่งกู้ยาก)
2. กู้ผ่าน **Cloud SQL PITR** ไปยังเวลาก่อนรันสคริปต์
3. ตรวจว่าข้อมูลกลับครบก่อนเปิดใช้งาน

**สคริปต์ไม่มีปุ่ม undo** — จุดกู้คืนใน ① คือทางเดียว
