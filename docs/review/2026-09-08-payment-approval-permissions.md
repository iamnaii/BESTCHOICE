# สิทธิ์อนุมัติรายการรับชำระ — 8 กันยายน 2026

## พฤติกรรมที่ตกลง

- รับเงินตามปกติและแบ่งชำระ: ผู้มีสิทธิรับชำระบันทึกได้ทันที
- อนุโลมค่าปรับ, ยอมรับส่วนต่าง, ยกเลิกใบเสร็จ และปิดสัญญา: ส่งคำขอโดยยังไม่ลงบัญชี ผู้มีสิทธิอีกบัญชีตรวจและกดอนุมัติ
- OWNER อนุมัติคำขอของตนเองได้เมื่อระบุเหตุผล มีหลักฐานผู้ทำรายการ ผู้อนุมัติ เวลา และเหตุผล
- OWNER กำหนดสิทธิแยกรายบุคคลที่ตั้งค่า → ผู้ใช้และสิทธิ์ การเป็นผู้จัดการไม่ได้ให้สิทธิอนุมัติโดยอัตโนมัติ
- คิวคืนเงินเดิมใช้สิทธิ REFUND และบัญชีผู้อนุมัติจริง การยืนยันผลจากธนาคารยังจำกัด OWNER/FINANCE_MANAGER

## การทำงาน

`PaymentApprovalRequest` เก็บ payload, ยอดที่ให้ตรวจ และ snapshot ของสัญญา/งวด/ใบเสร็จ/นโยบาย ณ เวลาส่งคำขอ ยอดปิดสัญญาคำนวณที่เซิร์ฟเวอร์ใน transaction และตรวจซ้ำก่อนลงบัญชี

ทุก financial handler ตรวจสิทธิ สาขา สถานะผู้ใช้ ผู้ขอ และ snapshot ภายใน transaction เดียวกับการลงบัญชีและใช้คำขอ อนุมัติซ้ำได้เพียงครั้งเดียว หากยอดเปลี่ยนต้องยกเลิกคำขอเก่าและส่งใหม่ การส่งชื่อผู้อนุมัติมาทาง endpoint เก่าไม่ใช่อำนาจอนุมัติ

UI ไม่มีช่องเลือกชื่อผู้อนุมัติ ผู้อนุมัติตรวจยอดและเปิดหลักฐานจากคำขอได้ การส่งคำขอไม่สร้างใบเสร็จหรือย้ายเงิน คำขอที่อนุมัติแล้วใช้บัญชีผู้ขอเป็นผู้บันทึก และบันทึกบัญชีผู้อนุมัติจริงแยกกัน

ส่วนต่างขาดที่ได้รับอนุมัติใช้ปิดสถานะงวดได้ ยอด `amountPaid` รวมเครดิตที่ใช้ชำระ ส่วน `Receipt.amount` เก็บเงินที่รับจริง การรับเกินหลังแบ่งชำระรักษายอดสะสมเดิมและพักเฉพาะส่วนเกิน ค่าปรับที่เก็บไปกับใบแรกไม่คิดซ้ำในใบถัดไป ยกเว้นค่าปรับที่พนักงานเพิ่มชัดเจน

การคืนเงินอ้างอิงเงินรับจริงจากใบเสร็จ จึงไม่คืนเครดิตส่วนต่างเป็นเงินสดเพิ่ม และตรวจความเปลี่ยนแปลงอีกครั้งก่อนอนุมัติ/ยืนยันผลธนาคาร

รายการคืนเงินที่ผสมเครดิต/เงินล่วงหน้าถูกปฏิเสธและให้ใช้คำขอยกเลิกใบเสร็จแทน เพื่อให้คืนยอด balance ครบตาม workflow ที่รองรับอยู่

## ตรวจสอบ

- TypeScript และ production build ของ API/Web
- Web regression suite รวมถึงคิวอนุมัติ การเปิดหลักฐาน และ ReceiptVoidDialog
- API unit tests: สิทธิรายบุคคล, settings, รับชำระ, waiver, void, refund และ early payoff
- PostgreSQL แยก: `payment-approval-record.e2e-spec.ts`, `recordpayment-manual-late-fee.e2e-spec.ts`, `multireceipt-reversal.e2e-spec.ts` และชุด integration ของ void/park/early payoff/shop collection
- ทดสอบ browser กับหน้าจอจริงและ services จริงในฐานข้อมูลจำลอง: รับเงินปกติ, ส่งคำขอ, ผู้ไม่มีสิทธิถูกปฏิเสธ, SALES ที่ได้รับสิทธิอนุมัติได้, OWNER อนุมัติตนเองพร้อมเหตุผล, บันทึก/ถอนสิทธิ, ยกเลิกใบเสร็จหลายใบ และยกเว้นค่าปรับ

Local preview: http://localhost:5197/payments จาก checkout นี้ ใช้ฐานข้อมูล PostgreSQL แยก ข้อมูลและการเข้าสู่ระบบจำลอง งดการส่ง LINE/MDM และผลข้างเคียงภายนอก มีแถบสลับผู้ใช้ทดสอบและลิงก์ตั้งค่าสิทธิ

ผลตรวจรายกรณีอยู่ใน `.tmp/payment-preview/check-approvals.json` และ `.tmp/payment-preview/check-approval-special.json`; log การตรวจอยู่ใน `.tmp/payment-approval/` งานนี้ไม่ได้ deploy หรือเขียนฐานข้อมูล production

## ประเด็นเดิมที่พบระหว่างตรวจปิดสัญญา

ข้อมูลจำลอง `TEST-APPROVAL-PAYOFF` แสดงยอดปิดสัญญาที่เก็บในคำขอและใบเสร็จ 39,062.77 บาท แต่ JP4 debit บัญชีธนาคาร 11-1201 เป็น 39,061.36 บาท (ต่าง 1.41 บาท) ส่วนลดตาม quote 9,569.23 บาท เทียบกับส่วนลดใน JE 9,568.00 บาท ผลรวม Dr/Cr ของ JE เท่ากันที่ 70,946.72 บาท

สาเหตุอยู่ในสูตรเดิมที่ `ContractPaymentService.earlyPayoff` ระบุไว้ว่า quote ใช้ฐานยอดเรียกเก็บ ขณะที่ JE ใช้ฐานแยกเงินต้น/ดอกเบี้ย งานนี้ตรวจการเก็บ quote และตัวตนผู้อนุมัติ แต่ไม่ได้เปลี่ยนนโยบายสูตรปิดสัญญา จึงไม่ถือว่าผ่านความตรงกันของยอดเงินสดสำหรับกรณีนี้ ต้องแก้ประเด็นดังกล่าวก่อนอ้างว่า early payoff ถูกต้องครบทุกกรณี
