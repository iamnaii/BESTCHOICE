# คำรับรองผู้ขายรับซื้อ/เทิร์นเครื่อง — 8 กันยายน 2026

เพิ่มคำรับรอง 5 ข้อให้ผู้ขายอ่านก่อนยอมรับและลงนาม ทั้งหน้ารับซื้อด่วนและรับเครื่องหลังประเมิน เพื่อบันทึกคำยืนยันเรื่องสิทธิในการขาย ที่มาเครื่อง ภาระและสิทธิบุคคลอื่น ความถูกต้องของข้อมูล การให้ความร่วมมือตรวจสอบ และการคืนประโยชน์/ชดใช้ความเสียหายจริงตามกฎหมาย ข้อความฉบับเต็มอยู่ `packages/shared/src/trade-in-declaration.ts` รุ่น `2026-09-08.1`

## ขอบเขตกฎหมายและการตรวจรับ

คำรับรองเป็นส่วนหนึ่งของหลักฐาน ไม่ใช่ข้อยกเว้นความผิดรับของโจร และไม่ผูกพันเจ้าของที่แท้จริงให้หมดสิทธิ การพิจารณาต้องดูข้อเท็จจริง ความรู้ และพฤติการณ์ตามประมวลกฎหมายอาญา มาตรา 59 และ 357; การรับไว้เพื่อค้ากำไรมีบทเฉพาะ จึงไม่ใช้ข้อความว่าผู้ขายรับผิดฝ่ายเดียวหรือบริษัทพ้นผิดทุกกรณี

แหล่งกฎหมาย: [ประมวลกฎหมายอาญา — กรมเจ้าท่า](https://laws.md.go.th/laws-implement/home/detail/9/?sID=9) และ [ความผิดทรัพย์คดีอาญา — ศูนย์บริการข้อมูลภาครัฐ](https://gcc.go.th/2023/10/31/ความผิดทรัพย์คดีอาญา/) ตรวจเมื่อ 8 กันยายน 2026 ข้อความนี้เป็นร่างสำหรับให้ทนายตรวจความเหมาะสมก่อนใช้งานจริง

การปฏิบัติของพนักงานยังจำเป็น:

- เทียบบัตรตัวจริงกับผู้ขาย ตรวจข้อมูลผู้ติดต่อ และตรวจหนังสือมอบอำนาจ/หลักฐานเจ้าของเมื่อไม่ได้ขายด้วยตนเอง
- เทียบ IMEI/Serial ที่ตัวเครื่องกับระบบและหลักฐานซื้อหรือที่มาเครื่อง พร้อมบันทึกวิธีตรวจและผู้ตรวจ
- ตรวจสถานะล็อกบัญชี ระบบจัดการเครื่อง ภาระติดค้าง และข้อพิรุธ เช่น ราคาผิดปกติหรือคำอธิบายที่มาไม่สอดคล้อง หากสงสัยให้หยุดรับซื้อและส่งผู้รับผิดชอบตรวจสอบ
- เก็บหลักฐานที่จำเป็นอย่างเหมาะสมตามกฎหมายและนโยบายข้อมูลส่วนบุคคล รวมถึงปฏิบัติตามหน้าที่ของผู้ค้าของเก่าที่ใช้กับกิจการ

รายการข้างต้นเป็นแนวทางการตรวจรับ ไม่ใช่ฟีเจอร์อัตโนมัติที่เพิ่มในรอบนี้ ระบบไม่ได้ตรวจฐานเครื่องหายของตำรวจหรือรับรองใบอนุญาต/สมุดทะเบียนค้าของเก่า และลายเซ็นบน canvas ไม่ใช่การยืนยันตัวตนทางชีวมิติ

## พฤติกรรมและหลักฐาน

- หน้าจอแสดงข้อความเต็มทั้งห้าข้อก่อน checkbox และลายเซ็น ไม่ซ่อนในลิงก์
- API รับรุ่นของคำรับรองที่แสดงและตรวจว่าตรงฉบับปัจจุบัน ต้องมีการยืนยันตรวจบัตร ยอมรับคำรับรอง และลายเซ็นที่ไม่ว่าง เซิร์ฟเวอร์เป็นผู้กำหนดข้อความเอง
- เก็บ `sellerDeclarationSnapshot` พร้อมข้อความ รุ่น เวลา และผู้บันทึกในธุรกรรมเดียวกับลายเซ็น การเปลี่ยนเงื่อนไขในอนาคตต้องออกรุ่นใหม่
- PDF ใช้ข้อความที่บันทึกไว้กับรายการนั้น รายการเก่าที่ไม่มี snapshot ยังคงคำรับรองเดิม; หากมี snapshot แต่ข้อความเสียหายจะไม่ออกเอกสารแทนด้วยเงื่อนไขใหม่
- ป้องกันการรับเครื่องซ้ำและการเขียนทับหลักฐานเดิม แม้สถานะถูกนำกลับไปประเมินใหม่ คำขอพร้อมกันสำเร็จเพียงครั้งเดียว อีกคำขอตอบ 400 และ rollback ข้อมูลสินค้า/บัญชีในธุรกรรมนั้น
- แก้ SignaturePadFull ที่เคยส่งภาพ canvas ว่างจาก mouseleave/การคลิกโดยไม่วาด และล้างการตรวจบัตร/ยอมรับ/ลายเซ็นเมื่อย้อนกลับแก้ข้อมูลรับซื้อ
- ไม่เปลี่ยนสูตรราคา ยอดจ่าย หรือการใช้เครดิตเทิร์น ไม่อ้างว่าตรวจความไม่เปลี่ยนแปลงของข้อมูลย้อนหลังทุกช่องทั้งระบบ

## Migration และการนำขึ้นใช้งาน

เพิ่มคอลัมน์ JSONB nullable ใน SHOP ด้วย `20260908100000_trade_in_seller_declaration` ไม่มี default และไม่มี backfill; FINANCE ไม่มีโมเดล TradeIn จึงไม่เพิ่มคอลัมน์ที่นั่น ต้องใช้ migration นี้เมื่อปล่อย backend ใหม่และปล่อย web ที่ส่งรุ่นคำรับรองพร้อมกัน หน้าจอเก่าที่เปิดค้างจะถูกขอให้รีเฟรช อ่านเงื่อนไข และลงนามใหม่ ไม่เพิ่มเงื่อนไขลงในหลักฐานเก่าอัตโนมัติ

รอบนี้ใช้ migration กับฐานทดสอบ/preview แยกเท่านั้น ยังไม่ deploy หรือแก้ฐานจริง
