## 4. นิยาม "ทุกเหตุการณ์ที่อาจเกิดขึ้น"

ทุกหน้าจอต้องไล่ครบ 13 มุม (มุมไหนไม่มีจริงให้เขียน "ไม่มี" อย่าข้ามเงียบ)

1. **Happy path**
2. **Validation** — เว้นว่าง · ติดลบ · 0 · ตัวอักษรในช่องตัวเลข · เกิน max length · วันที่ย้อนหลัง/อนาคตเกินเหตุ · อีเมล/เบอร์/เลขบัตรผิดรูปแบบ · IMEI ซ้ำ
3. **ค่าขอบ** — ส่วนต่าง ±1 บาท (tolerance) · งวดสุดท้าย · งวดเดียว · ยอด 0 · จ่ายเกิน · ขาด 1 สตางค์ · ทศนิยม 3 ตำแหน่ง
4. **สิทธิ์ 5 role** — OWNER / BRANCH_MANAGER / FINANCE_MANAGER / ACCOUNTANT / SALES: ใครเห็นเมนู ใครกดปุ่มได้ ใครต้องโดน 403 และ **BM ต้องข้ามสาขาไม่ได้**
5. **สถานะว่าง** — ยังไม่มีข้อมูล · ค้นหาไม่เจอ · ตัวกรองไม่เหลือผลลัพธ์
6. **กดซ้ำ / double-submit** — กดยืนยันรัวๆ ต้องไม่เกิดเอกสารซ้ำ ไม่เกิด JE ซ้ำ
7. **ยกเลิกกลางคัน** — ปิด dialog · กด back · refresh กลางฟอร์ม · ปิดแท็บ แล้วเข้าใหม่ (มี draft auto-save ไหม)
8. **State machine** — ไล่ทุก transition ทั้งที่**ควรผ่าน**และที่**ต้องถูกปฏิเสธ** เช่น ยึดเครื่องสัญญาที่ยังไม่ TERMINATED · post เอกสารในงวดที่ปิดแล้ว · approve รอบจ่ายที่ยัง DRAFT · void ใบเสร็จที่ void ไปแล้ว
9. **ยกเลิก/กลับรายการ** — ทุกปุ่ม void / reverse / cancel + ตรวจว่า GL กลับเป็นศูนย์จริง (รวม **ยกเลิกใบขาย** ตามสเปก `2026-08-22-void-sale-design.md`)
10. **ผลข้างเคียงข้ามโมดูล** — ขายแล้ว stock ตัดไหม · ค่าคอมขึ้นไหม · JE ลงบัญชีถูกตัวไหม · Dashboard/รายงานขยับไหม · audit log บันทึกไหม · แจ้งเตือนเด้งไหม
11. **งานกลางคืน (cron)** — 2A ดอกเบี้ยค้างรับ 00:01 · ECL 00:30 · VAT 60 วัน 02:00 · หนังสือทวง 09:15 · promise resolution · no-promise MDM lock · retention → เขียนเป็นเคส "รอข้ามคืนแล้วกลับมาเช็คอะไร"
12. **กระทบยอดรายงาน** — งบทดลอง (`scope=FINANCE` / `SHOP` / `ALL` ต้อง balance แยกกันทั้งคู่) · P&L · งบดุล · ECL · ภ.พ.30 preview · `/financial-audit`
13. **พร้อมกัน 2 หน้าจอ** — เปิด 2 แท็บทำรายการเดียวกันชนกัน (รับชำระงวดเดียวกัน · approve รอบจ่ายพร้อมกัน)

## 5. ข้อห้ามเด็ดขาด (พิมพ์ไว้หน้าแรกของคู่มือ ตัวหนา)

1. **ห้ามแตะข้อมูลจริงที่นำเข้าจากระบบเดิม** — สินค้า `TTFY-*` และตาราง `imported_sales` (3,403 รายการ) ล้างแล้วต้องนำเข้าใหม่ทั้งหมด
2. **ห้ามรับชำระผ่าน QR PaySolutions จริง** — เงินจริงจะวิ่ง ให้บันทึกเงินสด/โอนแทน
3. **ห้าม approve รอบจ่าย INTER-CO ที่มีสัญญาเทสปน** — JE รอบจ่าย stamp `metadata.items[]` ไม่ใช่ `contractId` → cleanup ตามลบไม่ได้ (ถ้าพลาด: reverse ผ่านหน้าจอก่อน)
4. **ห้ามผูก/สั่ง MDM lock กับสัญญาเทส** — ไม่มีเครื่องจริง
5. **ห้ามปิดงวดบัญชี ห้ามยื่น ภ.พ.30 / ภ.ง.ด. ห้ามปิดปีบัญชี** ระหว่างมีข้อมูลเทสค้าง
6. **ห้ามแก้ค่าใดๆ ใน `/settings`**
7. **ห้ามส่ง LINE/SMS/อีเมล broadcast ออกหาลูกค้าจริง** — เทสเฉพาะกับลูกค้าเทส และคาดหวังว่าจะ fail (ลูกค้าเทสไม่มี LINE) ซึ่งคือได้เทส error path
8. **สร้างเครื่อง/รับซื้อ/trade-in ต้องกรอก IMEI ขึ้นต้น `TEST-` เสมอ** — เป็นเส้นแบ่งเดียวที่กันสินค้าเทสออกจากสินค้าจริง
9. **ห้ามรัน `factory:reset` เองระหว่างเทส** — เป็นคำสั่งของเจ้าของเท่านั้น

## 6. ข้อกำหนดพิเศษ — ตารางวิธีกลบคืน

ตอนนี้มีเครื่องมือลบ **3 ตัว ระดับความแรงต่างกัน** ต้องเข้าใจก่อนว่าตัวไหนเก็บอะไรไม่เก็บอะไร

| เครื่องมือ | ลบอะไร | เหลืออะไร |
|---|---|---|
| `cleanup:test-contracts` | สายสัญญาเทสเท่านั้น (สัญญา งวด ใบเสร็จ ใบขาย ค่าคอม trade-in หนังสือทวง รายการยึด + hard-delete JE ผ่าน `metadata.contractId`) | ทุกอย่างที่ไม่ผูกสัญญาเทส |
| `wipe:test-stock` | soft-delete `products` ที่ **ไม่ใช่** `TTFY-*` | สินค้าจริงจาก Tooltify |
| `factory:reset` | 131 ตาราง = รายการเคลื่อนไหวทั้งระบบ (รวม `audit_logs`) | ~65 ตาราง = ตั้งค่า เทมเพลต ผังบัญชี งวด **ลูกค้า สินค้า คู่ค้า PO ผลตรวจ QC ประวัติแชท `imported_sales`** |

**จุดที่คนพลาดบ่อย:** `factory:reset` **เก็บ** `customers` `products` `purchase_orders` `po_items`
`inspections` ⇒ ลูกค้าเทส / เครื่องเทส / ใบสั่งซื้อเทส / ผลตรวจ QC เทส ที่สร้างระหว่างทดสอบ
**รอดจาก factory reset** ต้องตามลบแยกด้วย `wipe:test-stock` (สินค้า) และ soft-delete ลูกค้า/PO เอง

**ให้ทำตารางนี้ต่อท้ายคู่มือ ครบทุกโมดูลที่แตะ:**

| โมดูล/หน้าจอ | สร้างอะไรค้างไว้ | ตารางไหน | อยู่ใน KEEP หรือ WIPE | วิธีกลบ |
|---|---|---|---|---|
| ... | ... | ... | KEEP / WIPE | cleanup CLI ตัวไหน / void ผ่านหน้าจอ / soft-delete เอง / ยอมค้าง (ระบุเหตุผล) |

อ่าน `factory-reset-tables.ts` เพื่อเช็คว่าตารางของแต่ละโมดูลอยู่ฝั่ง KEEP หรือ WIPE
**ทุกแถวที่อยู่ KEEP ต้องมีวิธีกลบที่ทำผ่านหน้าจอได้จริง** ถ้าไม่มี ให้ขึ้นหัวข้อ
**"⚠️ เทสแล้วลบไม่ได้ — ตัดสินใจก่อนเทส"** พร้อมเสนอว่าควรข้ามเคสนั้นหรือควรเพิ่ม marker/CLI
(เสนอเฉยๆ **ห้ามลงมือเขียนโค้ด**)

**marker convention** ที่คนเทสต้องใช้กับทุกอย่างที่สร้างเองผ่านหน้าจอ — เขียนเป็นกฎข้อแรกของคู่มือ:

## 7. รูปแบบผลลัพธ์

ภาษาไทย บันทึกที่ `docs/guides/FULL-SYSTEM-TEST-CHECKLIST/` แยกไฟล์ตามโดเมน
พร้อม `README.md` เป็นสารบัญ + ภาพรวม + ข้อห้าม + ตาราง map กับใบงานหมวย&ป๊อป + ตารางกลบคืน

แต่ละเคสเป็นแถวในตาราง:

| # | หน้าจอ (route) | สิทธิ์ที่ใช้ | สิ่งที่ทำ | ข้อมูลที่ใช้ | ผลที่คาดหวัง | ผ่าน | หมายเหตุ |
|---|---|---|---|---|---|---|---|
| P-01 | `/payments` | ACCOUNTANT | บันทึกรับชำระงวดครบกำหนด เงินสด | สัญญา TEST-xxxx #1 | ใบเสร็จออก · งวด → PAID · JE 2B ลง Dr 11-1101 / Cr 11-2101+11-2103+21-2101 | ☐ | |

กติกา:
- รหัสเคสมี prefix ตามโดเมน (P=payments, C=contracts, S=stock, A=assets, F=finance, E=equity …)
- **"ผลที่คาดหวัง" ต้องเจาะจงและตรวจสอบได้** — เลขบัญชี · สถานะ · ข้อความ error ที่ควรเห็น **ห้ามเขียนลอยๆ ว่า "ทำงานถูกต้อง"**
- เคสที่ต้องรอ cron แยกหัวข้อ "เคสข้ามคืน" บอกว่ารอถึงกี่โมงแล้วกลับมาดูตรงไหน
- เรียงให้เทสไล่ได้ต่อเนื่องจริง (prerequisite มาก่อน)
- ปิดท้ายทุกไฟล์ด้วย "สิ่งที่ต้องกลบคืนหลังจบไฟล์นี้"

## 8. ขั้นตอนการทำงานของคุณ

1. อ่านทุกไฟล์ในข้อ 0–1 ให้จบ โดยเฉพาะใบงานหมวย&ป๊อป และ `factory-reset-tables.ts`
2. ดึง route ทั้งหมดจาก `App.tsx` มาทำ checklist ความครอบคลุม — **ทุก route ต้องถูกแตะ** ไม่ด้วยเคสเทสก็ด้วยเหตุผลว่าทำไมเทสไม่ได้
3. ทำตาราง map กับใบงานเดิม (ข้อ 3) ก่อนเขียนเคสใหม่ — กันเขียนซ้ำ
4. แต่ละโดเมน อ่าน service/controller ฝั่ง API ที่เกี่ยวข้อง เพื่อดึง **ข้อความ error จริง · เงื่อนไข guard จริง · JE จริง** มาใส่ "ผลที่คาดหวัง" — **ห้ามเดาจากชื่อฟังก์ชัน**
5. ฟีเจอร์ใหม่ 6 ตัวในข้อ 1 ให้อ่านสเปกแล้วออกแบบเคสจากสเปกโดยตรง (ยังไม่มีใครเทสมาก่อน)
6. เขียนไฟล์ทีละโดเมน
7. ตรวจซ้ำท้ายงาน: route ไหนยังไม่ถูกแตะ · มุมไหนใน 13 ข้อยังขาด · แถว KEEP ตัวไหนยังไม่มีวิธีกลบ
8. สรุปให้ผู้ใช้: จำนวนเคสทั้งหมด · เคสที่อ้างอิงใบงานเดิม vs เคสใหม่ · route ที่เทสไม่ได้พร้อมเหตุผล · config ที่ต้องขอให้เจ้าของเปิด · ความเสี่ยงที่เหลือ

## 9. เกณฑ์ว่าเสร็จ

- [ ] ทุก route ที่ไม่ใช่ `/settings/**` (182 หน้า) ถูกครอบคลุมหรือมีเหตุผลกำกับ
- [ ] ทุกหน้าจอไล่ครบ 13 มุมในข้อ 4 (มุมที่ไม่มีจริงเขียน "ไม่มี")
- [ ] มีตาราง map กับใบงานหมวย&ป๊อป และไม่มีเคสไหนเขียนซ้ำกับใบงานเดิม
- [ ] ฟีเจอร์ใหม่ 6 ตัว (equity · dividend · imported-sales · void-sale · reschedule fee park · device-swap netting · shop opening balance) มีเคสครบ
- [ ] ไม่มีขั้นตอนไหนสั่งให้แก้ค่าใน `/settings`
- [ ] ไม่มีขั้นตอนไหนแตะสินค้า `TTFY-*` หรือ `imported_sales`
- [ ] ตารางกลบคืนครบทุกโมดูล ระบุ KEEP/WIPE ถูกต้องตาม `factory-reset-tables.ts` และแถว KEEP ทุกแถวมีวิธีกลบ
- [ ] "ผลที่คาดหวัง" ทุกช่องตรวจสอบได้จริง (อ้างเลขบัญชี/สถานะ/ข้อความจริงจากโค้ด)
- [ ] มีลำดับการเทสที่ไล่ได้ต่อเนื่องตั้งแต่เตรียมข้อมูลจนถึงกลบคืน
