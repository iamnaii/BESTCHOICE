# BESTCHOICE — สิทธิ์พนักงานตามตำแหน่ง

วันที่: 2026-10-17 (Asia/Bangkok)

สถานะ: แบบเสนอฉบับรวมหลังตรวจความพร้อมสำหรับวางแผน ข้อตกลงที่เจ้าของยืนยันอยู่ในส่วนที่ 1 รายละเอียดหน้าจอและค่าเริ่มต้นที่ผู้ช่วยเสนอแยกระบุไว้ เอกสารนี้ยังไม่ได้เปลี่ยนระบบจริง

## 1. ข้อตกลงกับเจ้าของ

### ขอบเขตและผู้ดูแล

- ต้องควบคุมสิทธิ์ทั้งโปรแกรม BESTCHOICE
- เจ้าของเท่านั้นที่กำหนดหรือแก้สิทธิ์ และมอบตำแหน่งให้ username อื่น
- กำหนดสิทธิ์ตามตำแหน่ง พนักงานรับสิทธิ์ผ่านตำแหน่ง ไม่ตั้งสิทธิ์แต่ละรายการแยกรายคน
- หนึ่ง username มีได้หลายตำแหน่ง เพราะมีพนักงานทำงานควบหลายหน้าที่
- รองรับตำแหน่งต่างกันตามสาขา เช่น ผู้จัดการที่สาขา A และพนักงานขายที่สาขา B
- การเปลี่ยนชุดสิทธิ์ของตำแหน่งมีผลกับผู้ที่ได้รับตำแหน่งนั้น โดยขอบเขตสาขาของแต่ละคนยังคงจำกัดสิทธิ์

### ต้นทุนและรายงานกำไร

เจ้าของยืนยันว่าตารางนี้เป็น **ค่าเริ่มต้นที่เจ้าของปรับให้ตำแหน่งอื่นภายหลังได้** ไม่ใช่ข้อห้ามตายตัวตามชื่อตำแหน่ง

| ตำแหน่ง | ราคาซื้อ / ต้นทุนสินค้า | รายงานกำไร |
| --- | --- | --- |
| เจ้าของ | ดูได้ | ดูได้ |
| ฝ่ายบัญชี | ดูได้ | ดูได้ |
| ฝ่ายจัดซื้อ | ดูได้ | ดูไม่ได้ |
| ตำแหน่งอื่น รวมผู้จัดการสาขา | ดูไม่ได้ | ดูไม่ได้ |

- ขอบเขตงานและข้อมูลยังต้องผ่านการตรวจสิทธิ์ แม้ตำแหน่งนั้นมีสิทธิ์ดูต้นทุนหรือรายงานกำไร
- การเปลี่ยนสิทธิ์ข้อมูลสำคัญทำโดยเจ้าของผ่านชุดสิทธิ์ตำแหน่ง พร้อมแสดงผลกระทบและเก็บประวัติ การคัดลอกตำแหน่งไม่ยืนยันการเพิ่มสิทธิ์ข้อมูลสำคัญโดยอัตโนมัติ ต้องแสดงสิทธิ์ที่จะได้อย่างชัดเจนก่อนเจ้าของบันทึก
- ผู้ที่ไม่มีสิทธิ์ดูต้นทุนต้องไม่ได้ข้อมูลต้นทุน กำไร หรืออัตรากำไรที่เปิดเผยต้นทุน ผ่านหน้าจอ รายงาน หรือไฟล์ดาวน์โหลด
- สิทธิ์ดูรายงานกำไรรวมเป็นสิทธิ์ต่างหากจากสิทธิ์ดูต้นทุน: ผู้จัดซื้อที่เห็นทั้งราคาซื้อและราคาขายอาจคำนวณส่วนต่างของสินค้าเองได้ จึงไม่กล่าวอ้างว่าการซ่อนรายงานป้องกันการอนุมานทั้งหมด

### ส่วนลดการขาย — เจ้าของตอบรับแนวทางแล้ว

1. พนักงานขายใช้ราคาปกติและโปรโมชันที่เจ้าของตั้งไว้ได้ทันที
2. ส่วนลดนอกโปรทุกครั้งต้องผ่านผู้จัดการของสาขานั้น ภายในเพดานที่เจ้าของกำหนด
3. เกินเพดาน หรือราคาต่ำกว่าเกณฑ์ที่ระบบกำหนด ต้องส่งเจ้าของอนุมัติ
4. เพดานรองรับจำนวนบาทและเปอร์เซ็นต์ ต้องผ่านทั้งสองเงื่อนไข และตั้งแยกตามสินค้าหรือหมวดได้
5. ผู้จัดการเห็นราคาขาย ส่วนลดที่ขอ ราคาสุทธิ และเหตุผล ระบบตรวจเกณฑ์ที่อาศัยต้นทุนฝั่งเซิร์ฟเวอร์โดยไม่ส่งต้นทุนให้ผู้จัดการ
6. พนักงานไม่อนุมัติรายการตนเอง แม้มีหลายตำแหน่ง **ยกเว้นเจ้าของซึ่งเจ้าของยืนยันภายหลังให้อนุมัติส่วนลดของตนเองได้** โดยบังคับระบุเหตุผลและเก็บประวัติผู้สร้าง/ผู้อนุมัติว่าเป็นคนเดียวกัน ข้อยกเว้นนี้เฉพาะส่วนลดการขาย ไม่ขยายเป็นการอนุมัติตนเองทุกกระบวนการ
7. เก็บผู้ขอ ผู้อนุมัติ เหตุผล และราคาก่อน–หลัง
8. เปลี่ยนราคา จำนวนสินค้า หรือส่วนลดหลังอนุมัติ ต้องขออนุมัติใหม่
9. แยกส่วนลดสินค้าออกจากการลดดอกเบี้ยหรือยกเว้นค่าปรับ

ยังไม่ได้เลือกตัวเลขเพดาน จึงห้ามใส่วงเงินที่เดาขึ้นมาเป็นค่าที่เจ้าของอนุมัติ

### ยกเลิกการขาย / คืนเงิน

- เจ้าของเท่านั้นที่อนุมัติการยกเลิกการขายหรือคืนเงิน
- สิทธิ์อนุมัติส่วนลดไม่ให้สิทธิ์ยกเลิกการขายหรือคืนเงินโดยอัตโนมัติ
- เจ้าของยืนยันว่าหลังอนุมัติคืนเงิน พนักงานการเงินหรือเจ้าของบันทึกการคืนเงินจริงได้ เฉพาะยอดและรายการที่อนุมัติเท่านั้น
- สิทธิ์บันทึกคืนเงินไม่ใช่สิทธิ์อนุมัติคืนเงิน การเปลี่ยนยอดหรือรายการต้องกลับไปขออนุมัติใหม่ และต้องป้องกันการบันทึกจ่ายซ้ำ
- สิทธิ์ผู้สร้างคำขอเป็นรายละเอียดชุดสิทธิ์เริ่มต้นที่เสนอในส่วนที่ 5 การบันทึกคืนเงินจริงผ่านโปรแกรมไม่เท่ากับคำสั่งให้เพิ่มระบบโอนเงินธนาคารอัตโนมัติ
- ข้อตกลงนี้กล่าวถึงการขายและการคืนเงิน ไม่ได้ขยายไปเป็นนโยบายลบร่างหรือกลับรายการบัญชีทุกประเภทโดยอัตโนมัติ

### ลดดอกเบี้ย / ยกเว้นค่าปรับ

- เจ้าของยืนยันให้เจ้าของเท่านั้นที่อนุมัติการลดดอกเบี้ยหรือยกเว้นค่าปรับ
- ผู้จัดการการเงินไม่มีสิทธิ์อนุมัติสองเรื่องนี้ แม้เป็นรายการวงเงินต่ำ
- แยกสิทธิ์อนุมัติสองเรื่องนี้ออกจากการรับชำระตามปกติและการอนุมัติส่วนลดสินค้า
- การยืนยันนี้กำหนดผู้อนุมัติ ไม่ได้เปลี่ยนสูตรคำนวณดอกเบี้ยหรือค่าปรับ ส่วนผู้สร้างคำขอและรายละเอียดขั้นตอนหลังอนุมัติเป็นค่าเริ่มต้นที่ผู้ช่วยเสนอในส่วนที่ 5.3

### ประวัติการใช้งานทั้งโปรแกรม

- เจ้าของกำหนดว่า “ต้องเก็บประวัติทั้งหมด ใครทำอะไรในโปรแกรมบ้าง” ขอบเขตจึงครอบคลุมการใช้งานทั้งโปรแกรม ไม่จำกัดเฉพาะเปลี่ยนสิทธิ์หรืออนุมัติรายการ
- ต้องระบุผู้กระทำ การกระทำ วันเวลา และรายการที่เกี่ยวข้อง รวมการกระทำของเจ้าของเอง
- เจ้าของยืนยันให้พนักงานทุกคนเห็นประวัติว่าใครทำอะไร จึงเปิดสรุปประวัติการทำงานของทุกคนให้ username พนักงานที่เข้าใช้งานระบบได้ ไม่จำกัดเฉพาะเจ้าของ และไม่ใช่หน้าสาธารณะ
- รักษาข้อตกลงเรื่องข้อมูลสำคัญเดิม: การเห็นเหตุการณ์ไม่ได้เพิ่มสิทธิ์ดูค่าข้อมูลในเหตุการณ์ เช่น ทุกคนเห็นว่าฝ่ายจัดซื้อแก้ต้นทุน แต่เฉพาะผู้มีสิทธิ์ดูต้นทุนของรายการนั้นเห็นตัวเลขก่อน–หลัง
- ข้อเสนอการแสดงผล: สรุปเหตุการณ์แสดงวันเวลา ผู้กระทำ งาน/สาขา หมวด การกระทำ และผลลัพธ์ ส่วนข้อมูลลูกค้า เลขเอกสาร รายละเอียดรายการ และค่าก่อน–หลัง แสดงหรือเชื่อมไปเปิดได้ตามสิทธิ์ของผู้ดูต่อข้อมูลต้นทางนั้นเท่านั้น
- บังคับการปกปิดรายละเอียดที่ API และใช้กติกาเดียวกันกับการค้นหา ตัวกรอง สถิติ และไฟล์ส่งออก ไม่ส่งค่าที่ไม่มีสิทธิ์ไปซ่อนเฉพาะบนหน้าจอ สิทธิ์ดูประวัติไม่เพิ่มสิทธิ์แก้รายการต้นทางหรือส่งออกข้อมูลโดยอัตโนมัติ
- ประวัติต้องระบุเจ้าของที่อนุมัติส่วนลดของตนเองและเหตุผลให้ตรวจสอบได้ ตามข้อยกเว้นส่วนลดที่ยืนยันแยกไว้ข้างต้น

รายละเอียดที่เสนอเพื่อทำให้ตรวจสอบย้อนหลังได้:

| กลุ่มเหตุการณ์ | สิ่งที่ต้องครอบคลุม |
| --- | --- |
| บัญชีและการเข้าถึง | เข้าสู่ระบบ ออกจากระบบ ความพยายามเข้าที่ไม่สำเร็จ การเปลี่ยนรหัสผ่าน/รีเซ็ตรหัสผ่าน และการเข้าถึงที่ถูกปฏิเสธ |
| เปิดดูและค้นหา | เปิดหน้า เปิดรายการลูกค้า/สินค้า/สัญญา/รายงาน ดูข้อมูลสำคัญ และค้นหาข้อมูล โดยเก็บบริบทที่จำเป็นและปกปิดค่าค้นหาที่เป็นข้อมูลลับ |
| สร้างและแก้ไข | เพิ่ม แก้ไข ลบ/ปิดใช้งาน เปลี่ยนสถานะ นำเข้าข้อมูล และการทำรายการแบบกลุ่ม พร้อมค่าก่อน–หลังของข้อมูลที่เปลี่ยนซึ่งอนุญาตให้เก็บ |
| การเงินและอนุมัติ | ขาย รับชำระ ขอ/อนุมัติ/ปฏิเสธส่วนลด ยกเลิก คืนเงิน ลดดอกเบี้ย ยกเว้นค่าปรับ ลงบัญชีและกลับรายการ โดยเชื่อมผู้ขอ ผู้อนุมัติ และผู้ดำเนินการ |
| ข้อมูลออกจากระบบ | ขอส่งออก สร้างไฟล์ ดาวน์โหลด ขอพิมพ์หรือสร้างเอกสารสำหรับพิมพ์ แชร์เอกสาร และส่งข้อความ โดยระบุผลตามหลักฐานที่ระบบยืนยันได้ |
| สิทธิ์และตั้งค่า | เปลี่ยนตำแหน่ง ขอบเขตสาขา/งาน สิทธิ์ สถานะผู้ใช้ การตั้งค่า และการเชื่อมต่อ |
| การทำงานอัตโนมัติ | งานระบบ AI/bot integration และงานตั้งเวลา พร้อมผู้เริ่มคำสั่งถ้ามี ห้ามระบุว่าเป็นพนักงานผู้แก้ไขหากระบบเป็นผู้กระทำจริง |

- แต่ละเหตุการณ์ควรมี user ID ที่คงที่พร้อมชื่อ/username ณ เวลาทำรายการ ตำแหน่งและขอบเขตที่ใช้ งาน SHOP/FINANCE สาขาหรือบริบทส่วนกลาง เลขเอกสาร/รายการ ผลสำเร็จ/ล้มเหลว/ถูกปฏิเสธ เหตุผล และรหัสเชื่อมเหตุการณ์เดียวกัน บันทึกเวลาแน่นอนและแสดงเวลา Asia/Bangkok
- เก็บ IP และข้อมูลอุปกรณ์/เบราว์เซอร์เมื่อมี โดยไม่ถือว่า IP เพียงอย่างเดียวยืนยันตัวบุคคล
- ไม่เก็บรหัสผ่าน OTP access token หรือข้อมูลลับลงประวัติ การรีเซ็ตรหัสผ่านเก็บเหตุการณ์ ผู้กระทำ และเป้าหมาย แทนค่ารหัสผ่าน
- ก่อน–หลังต้องมาจากข้อมูลที่บันทึกสำเร็จจริง ไม่ใช้ request body เป็นหลักฐานว่าสถานะเปลี่ยนแล้วเมื่อรายการล้มเหลว
- ไม่อ้างว่าพิมพ์กระดาษสำเร็จหรือผู้รับอ่านข้อความแล้ว หากหลักฐานมีเพียงการขอพิมพ์/สร้างไฟล์/ส่งข้อความ
- แยกความตั้งใจของผู้ใช้จาก polling/retry ของระบบ และเชื่อมเหตุการณ์ซ้ำด้วยรหัสเดียวกัน การทำ bulk ต้องติดตามรายการย่อยที่ได้รับผลได้
- บันทึกการเปิดดู/ส่งออกประวัติด้วย แต่ไม่ให้การเขียน audit สร้าง audit ซ้ำต่อกันไม่จบ
- เสนอให้ประวัติเป็นแบบเพิ่มต่อท้าย: ไม่มีการแก้/ลบเนื้อหาเดิมผ่านโปรแกรม แม้เจ้าของ การแก้ความผิดพลาดเพิ่มเหตุการณ์อ้างอิงรายการเดิม พร้อมตรวจจับการเปลี่ยนแปลงโดยมิชอบ
- เสนอให้รายการเปลี่ยนเงิน สิทธิ์ หรือการอนุมัติสำเร็จได้ต่อเมื่อมีประวัติที่เก็บอย่างทนทานในธุรกรรมเดียวกันหรือคิวที่รับประกันการส่งต่อ ต้องออกแบบการตรวจช่องว่าง/ส่งซ้ำสำหรับเหตุการณ์ประเภทอื่น ห้ามถือการเรียกบันทึกแบบไม่รอผลว่ารับประกันครบทั้งหมด
- ผู้มีสิทธิ์ดูสรุปประวัติยืนยันแล้วว่าเป็นพนักงานทุกคน โดยรายละเอียดข้อมูลยังจำกัดตามสิทธิ์เดิม ข้อเสนอระยะนี้คือรักษานโยบายเก็บ/soft archive ที่ตั้งไว้เดิม พร้อมค้นประวัติที่ archive ได้ตามสิทธิ์ ไม่เพิ่มการลบประวัติหรือเปลี่ยนระยะเวลาเก็บโดยอัตโนมัติ รายละเอียดอยู่ในส่วนที่ 5

## 2. รายชื่อตำแหน่งที่เสนอ

เจ้าของ, ผู้จัดการสาขา, พนักงานขาย, พนักงานสต็อก, ฝ่ายจัดซื้อ, พนักงานการเงิน, ผู้จัดการการเงิน, พนักงานติดตามหนี้, ฝ่ายบัญชี

- แยกสต็อกกับจัดซื้อเพื่อกำหนดสิทธิ์ดูต้นทุนต่างกัน ผู้ทำงานควบรับทั้งสองตำแหน่งได้
- แอดมินตอบแชท ฝ่ายบุคคล และผู้ตรวจสอบแบบอ่านอย่างเดียว เป็นตำแหน่งเพิ่มเติมเมื่อมีความจำเป็น
- รายชื่อและรายละเอียดสิทธิ์เริ่มต้นในส่วนที่ 5 เป็นข้อเสนอสำหรับแบบฉบับรวม ไม่ใช่หลักฐานว่าได้เพิ่มสิทธิ์ให้บัญชีจริงแล้ว

## 3. หน้าจอที่เสนอ

หน้าศูนย์กลาง “พนักงานและสิทธิ์การใช้งาน” มีสามแท็บ:

1. **พนักงาน**: ค้นหาชื่อ/username ดูสถานะ ตำแหน่ง งาน และสาขา เลือกตำแหน่งพร้อมขอบเขตให้พนักงาน ดูสรุปสิทธิ์ที่ใช้จริง
2. **ตำแหน่งและสิทธิ์**: เพิ่มหรือคัดลอกตำแหน่ง ตั้งสิทธิ์เป็นหมวด ค้นหาสิทธิ์ด้วยคำไทย และดูจำนวนพนักงานที่ได้รับผลจากการแก้ไข
3. **ประวัติการใช้งาน**: ต่อยอดหน้าประวัติเดิมให้พนักงานทุกคนดูสรุปเหตุการณ์ทั้งโปรแกรมได้ กรองตามพนักงาน/username วันที่ งาน/สาขา หมวด การกระทำ และผลลัพธ์ เปิดรายละเอียดและค่าก่อน–หลังตามสิทธิ์ข้อมูล มีตัวกรองเฉพาะการเปลี่ยนสิทธิ์ เชื่อมไปยังประวัติรายพนักงานและรายเอกสารตามสิทธิ์

พนักงานเข้าหน้าประวัติได้โดยตรงโดยไม่ต้องได้รับสิทธิ์จัดการพนักงานหรือตำแหน่ง แท็บ/คำสั่งกำหนดสิทธิ์ยังคงเปิดให้เจ้าของเท่านั้น

ตัวแก้ไขตำแหน่งแบ่งหมวดตามงานจริง เช่น ขาย จอง รับซื้อ ลูกค้า แชท เครดิต สัญญา รับชำระ ติดตามหนี้ สต็อก จัดซื้อ หลังการขาย เอกสาร บัญชี ภาษี พนักงาน เงินเดือน รายงาน และตั้งค่า ต้องสำรวจเพิ่มเติมให้ครอบคลุมฟังก์ชันจริงทั้งโปรแกรม

แยกการดู สร้าง แก้ไข อนุมัติ ยกเลิก/กลับรายการ และส่งออกตามการทำงานที่มีจริง แยกสิทธิ์ข้อมูลสำคัญ เช่น ดูต้นทุน ดูกำไร และดูเงินเดือน ไม่ใช้ช่อง “จัดการทั้งหมด” แทนสิทธิ์เหล่านี้

ก่อนบันทึก แสดงสิทธิ์ที่เพิ่ม/ถอนและผู้ได้รับผล ไม่มีการเพิ่มสิทธิ์ให้ผู้ใช้คนอื่นเพียงเพราะมีชื่อหน้าที่คล้ายกัน

## 4. ข้อเสนอด้านระบบและข้อจำกัดจากโปรเจกต์

- ใช้เทคโนโลยีเดิมของ BESTCHOICE: React/TypeScript และ NestJS/Prisma/PostgreSQL
- รักษาความหมาย งานหน้าร้าน = SHOP และงานการเงิน = FINANCE และตัวเลือกงาน/บริษัทใน sidebar จุดเดียว
- FINANCE เป็นงานส่วนกลาง ไม่ควรสมมติว่าทุกข้อมูลมี branchId ต้องออกแบบขอบเขตข้อมูลส่วนกลางแยกจากการเลือกสาขาของ SHOP
- ผูกตำแหน่งกับขอบเขตในรายการมอบหมายเดียวกัน (ผู้ใช้, ตำแหน่ง, งาน/บริษัท, ขอบเขตข้อมูล) ห้ามรวมตำแหน่งกับสาขาเป็นคนละชุดแล้วสร้างสิทธิ์ข้ามทุกสาขาโดยไม่ตั้งใจ
- รวมสิทธิ์ได้เฉพาะรายการมอบหมายที่ตรงกับทรัพยากรและการทำงานครั้งนั้น ไม่ให้สิทธิ์ผู้จัดการสาขา A ไปใช้ในสาขา B
- สิทธิ์ต้นทุน/กำไรยังจำกัดด้วยขอบเขตของตำแหน่งที่ให้สิทธิ์นั้น เช่น บัญชีสาขา A + ขายสาขา B ไม่ได้สิทธิ์ดูต้นทุนสาขา B
- บังคับสิทธิ์ที่ API การค้นหา รายงาน ไฟล์ดาวน์โหลด และข้อมูลที่ตอบกลับ การซ่อนเมนูเป็นเพียงส่วนหนึ่งของประสบการณ์ใช้งาน
- ผู้ใช้ที่ไม่มีสิทธิ์ดูข้อมูลสำคัญต้องไม่ได้ค่าดังกล่าวใน response แม้เปิดเครื่องมือผู้พัฒนาของ browser
- สถานะ OWNER เป็นสิทธิ์ผู้ดูแลที่ต้องป้องกันแยกจากตำแหน่งทั่วไป ห้ามคัดลอกตำแหน่งแล้วได้อำนาจเจ้าของโดยอัตโนมัติ
- ตรวจสิทธิ์ล่าสุดเมื่อทำรายการหลังการแก้ไขสิทธิ์ และเก็บประวัติการเปลี่ยนแปลง
- ต้องสำรวจและย้ายการตรวจ role เดิม รวมทั้งสิทธิ์อนุมัติรายบุคคลที่มีอยู่ ให้เป็นแหล่งตัดสินสิทธิ์ร่วมกัน ห้ามอ้างว่าหน้าจอใหม่ควบคุมทั้งโปรแกรมหากเส้นทางเดิมยังข้ามกติกาได้
- การเปลี่ยนจากสิทธิ์เดิมต้องแสดงความต่างให้ตรวจ โดยเฉพาะ FINANCE_MANAGER ที่เดิมเข้าถึงข้อมูลการเงินบางประเภท และการยกเลิกขายที่เดิมผู้จัดการสาขาทำได้ ข้อกำหนดใหม่ของเจ้าของเป็นเป้าหมาย แต่ยังไม่มีการเปลี่ยน production
- มี `AuditLogsPage`, `AuditService`, audit interceptor และโครงสร้าง hash chain อยู่แล้ว ต้องต่อยอดและตรวจความครอบคลุม ไม่สร้างระบบประวัติแยกที่ตรวจสอบร่วมกันไม่ได้
- ตรวจโค้ด 2026-10-17: interceptor กลางข้าม GET/HEAD/OPTIONS และเรียกบันทึกโดยไม่รอผล; service ข้ามเหตุการณ์ที่ไม่มี userId และจับข้อผิดพลาดแล้วแจ้งเตือน ข้อมูลนี้ชี้จุดที่ต้องสำรวจเพิ่มเติม ไม่ได้แปลว่าไม่มีการบันทึกการอ่าน/เข้าสู่ระบบในส่วนเฉพาะทางอื่น
- โค้ด archive ปัจจุบันใช้ค่าเริ่มต้น 1825 วัน โดย config/environment override ได้ และเป็น soft archive ไม่ใช่การลบทิ้ง นี่คือข้อมูลจากโค้ด ไม่ใช่ค่าที่ตรวจจาก production หรือข้อสรุปทางกฎหมาย ต้องตรวจนโยบายจริงก่อนกำหนดระยะเวลาใหม่
- ต้องตรวจสิทธิ์การอ่านข้อมูลภายในประวัติด้วย เพื่อไม่ให้ต้นทุน/กำไร/ข้อมูลส่วนบุคคลรั่วผ่าน oldValue/newValue หรือไฟล์ export

## 5. รายละเอียดแบบเสนอและค่าเริ่มต้นที่ผู้ช่วยเลือก

ส่วนนี้เป็นข้อเสนอของผู้ช่วยเพื่อให้วางแผนพัฒนาได้ โดยไม่ต้องให้เจ้าของตัดสินรายละเอียดทุกปุ่ม ตัวเลขเพดานและการมอบตำแหน่งให้บัญชีจริงยังต้องตั้งก่อนเปิดใช้งานจริง

### 5.1 รูปแบบการจัดการ

- **หน้าพนักงาน**: ตารางชื่อ/username สถานะ ตำแหน่งพร้อมงาน/สาขา และปุ่มจัดการตำแหน่ง เมื่อเปิดพนักงานแสดงรายการมอบหมายหลายแถว แต่ละแถวระบุหนึ่งตำแหน่งพร้อมขอบเขต ผู้จัดการสาขา A และพนักงานขายสาขา B จึงเป็นคนละแถว
- **หน้าตำแหน่ง**: รายการตำแหน่งพร้อมจำนวนผู้ใช้งาน เลือกตำแหน่งแล้วแสดงหมวดงานทางซ้ายและสิทธิ์ทางขวา มีค้นหาด้วยคำไทย ใช้ค่าอนุญาต/ไม่อนุญาตต่อสิทธิ์ ไม่มี override ราย username
- **สิทธิ์ข้อมูลสำคัญ**: แยกสวิตช์ดูต้นทุน ดูรายงานกำไร และดูข้อมูลเงินเดือนออกจากสิทธิ์ทั่วไป การเปิดสิทธิ์อนุมัติไม่เปิดสิทธิ์เหล่านี้ตามไปด้วย
- **ดูสิทธิ์ที่ใช้จริง**: เจ้าของเลือก username และบริบทงาน/สาขาเพื่อดูสิ่งที่ทำได้ พร้อมบอกว่าได้รับจากตำแหน่งใด หากถอนสิทธิ์จากตำแหน่งหนึ่งแต่ยังมีจากอีกตำแหน่ง ต้องแสดงให้เห็น
- **ก่อนบันทึก**: สรุปสิทธิ์เพิ่ม/ถอน ขอบเขตที่เปลี่ยน และจำนวนผู้ได้รับผล บันทึกทั้งการเปลี่ยนตำแหน่งและการมอบหมายลงประวัติ
- **สิทธิ์สงวนของเจ้าของ**: จัดการผู้ใช้/ตำแหน่ง/สิทธิ์ และอนุมัติยกเลิกขาย คืนเงิน ลดดอกเบี้ย ยกเว้นค่าปรับ ยังสงวนตามข้อตกลง การแก้สิทธิ์ข้อมูลต้นทุน/กำไรได้ไม่ใช่การยกเลิกข้อจำกัดเหล่านี้
- ตำแหน่งที่ยังมีคนใช้อยู่ให้แสดงผู้ได้รับผลและให้เจ้าของย้ายการมอบหมายก่อนปิดตำแหน่ง ต้องรักษาเจ้าของที่ใช้งานได้อย่างน้อยหนึ่งบัญชี

### 5.2 แม่แบบตำแหน่งเริ่มต้น

สิทธิ์ด้านล่างใช้เฉพาะขอบเขตงาน/สาขาที่ได้รับมอบหมาย ต้องสำรวจรายการย่อยจากระบบจริงและจัดทำทะเบียนสิทธิ์ก่อนเชื่อมแต่ละหมวด สิทธิ์ที่ยังไม่ระบุไม่เปิดให้พนักงานโดยปริยาย

| ตำแหน่ง | งานหลักที่เสนอ | ข้อจำกัดหลัก |
| --- | --- | --- |
| เจ้าของ | ทุกงาน บริหารสิทธิ์ อนุมัติรายการสงวน | เก็บประวัติทุกการกระทำ ไม่แก้/ลบประวัติเดิมผ่านแอป |
| ผู้จัดการสาขา | ดูแลลูกค้า ยอดขาย งานหน้าร้าน สต็อกและทีมของสาขา อนุมัติส่วนลดภายในเพดาน | ไม่เห็นต้นทุน/กำไรตามค่าเริ่มต้น ไม่อนุมัติยกเลิก/คืนเงิน/ลดดอกเบี้ย/ยกเว้นค่าปรับ |
| พนักงานขาย | ลูกค้า แชทที่รับผิดชอบ จอง ขาย เตรียมสัญญา ดูสินค้าคงเหลือ ขอส่วนลดและขอยกเลิก/คืนเงิน | ไม่อนุมัติรายการตนเอง ไม่แก้ธุรกรรมที่เสร็จแล้วเพื่อเลี่ยงขั้นตอนอนุมัติ |
| พนักงานสต็อก | รับเข้า ตรวจนับ ส่ง/รับโอน ขอปรับจำนวน และติดตามสถานะสินค้า | ไม่เห็นต้นทุนตามค่าเริ่มต้น การปรับสต็อกที่ต้องอนุมัติคงขั้นตอนอนุมัติ ไม่เพิ่มสิทธิ์จ่ายเงิน |
| ฝ่ายจัดซื้อ | ผู้ขาย ใบสั่งซื้อ เอกสารรับเข้า ราคาซื้อและต้นทุน | ไม่เห็นรายงานกำไรรวมตามค่าเริ่มต้น ไม่ได้สิทธิ์อนุมัติจ่ายเงินจากตำแหน่งนี้ |
| พนักงานการเงิน | รับชำระตามปกติ ออกใบเสร็จ ตรวจยอด ขอคืนเงิน/ลดดอกเบี้ย/ยกเว้นค่าปรับ บันทึกคืนเงินตามอนุมัติ | ไม่อนุมัติข้อยกเว้นสงวนของเจ้าของ ไม่แก้ยอดคืนที่อนุมัติแล้ว |
| ผู้จัดการการเงิน | ตรวจเครดิต อนุมัติสัญญาตามกระบวนการเดิม ดูแลการรับชำระและงานติดตามในขอบเขต FINANCE ที่ได้รับ | ไม่ได้สิทธิ์ต้นทุน/กำไรหรือข้อยกเว้นสงวนโดยปริยาย การเข้าถึงส่วนกลางต้องมอบหมายชัดเจน |
| พนักงานติดตามหนี้ | ดูเคสที่ได้รับมอบหมาย บันทึกติดตาม นัดชำระ เอกสารติดตาม และขอลดดอกเบี้ย/ยกเว้นค่าปรับ | ไม่แก้ยอดหนี้/รับรองการลดหนี้เอง การส่งเอกสารหรือสั่งอุปกรณ์คงขั้นตอนอนุมัติของระบบเดิม |
| ฝ่ายบัญชี | เอกสารบัญชี บันทึกร่าง กระทบยอด ภาษี ดูต้นทุนและรายงานกำไร | การอนุมัติ ลงบัญชี กลับรายการ และปิดงวดแยกสิทธิ์ ไม่ให้ทั้งหมดเพียงเพราะเข้าหน้าบัญชีได้ |

- ทุกตำแหน่งดูสรุปประวัติกิจกรรมได้ตามข้อตกลง
- เงินเดือนและการตั้งค่าการเชื่อมต่อที่เป็นความลับเริ่มให้เจ้าของเท่านั้น ตำแหน่งบัญชีไม่ได้ข้อมูลเงินเดือนโดยอัตโนมัติ เจ้าของเปิดสิทธิ์ข้อมูลเงินเดือนให้ตำแหน่งที่รับผิดชอบได้ภายหลัง
- งานหลังการขายและเอกสารให้ตามหน้าที่ผู้รับเคสในสาขา ส่วนคำสั่งที่กระทบเงินต้องผ่านสิทธิ์ของการทำรายการนั้นอีกชั้น
- ฟังก์ชันเดิมที่ไม่ได้กำหนดไว้ในตารางต้องเข้า permission inventory ไม่อนุมานสิทธิ์จากชื่อตำแหน่ง และไม่เพิ่มให้พนักงานอัตโนมัติระหว่างย้ายระบบ

### 5.3 การขอ อนุมัติ และดำเนินรายการ

- ผู้ที่มีสิทธิ์ทำงานกับการขายและขอบเขตข้อมูลนั้นขอยกเลิก/คืนเงินได้ตามแม่แบบข้างต้น เจ้าของเป็นผู้อนุมัติ
- ผู้ที่มีสิทธิ์การเงิน/ติดตามหนี้ตามแม่แบบขอลดดอกเบี้ย/ยกเว้นค่าปรับได้ เจ้าของเป็นผู้อนุมัติ
- การอนุมัติผูกกับ snapshot ของรายการ ยอด รายการสินค้า/หนี้ และเหตุผลที่ขอ หากแก้ข้อมูลที่มีผลต่อการตัดสินใจ สถานะอนุมัติเดิมใช้ไม่ได้
- การอนุมัติลดดอกเบี้ย/ยกเว้นค่าปรับให้ระบบใช้ค่าที่อนุมัติตามกระบวนการบัญชีเดิม ไม่เปิดช่องให้พนักงานเลือกยอดใหม่หลังอนุมัติ
- คืนเงินแยกสถานะได้รับอนุมัติกับบันทึกคืนเงินจริง พนักงานการเงิน/เจ้าของบันทึกการคืนตามวิธีและยอดที่อนุมัติ มีหลักฐานตามที่ระบบเดิมต้องใช้ และแสดงยอดที่ยังไม่ดำเนินการ
- ข้อเสนอระยะแรก: หนึ่งคำขอคืนเงินดำเนินการหนึ่งครั้งเต็มยอดที่อนุมัติ รองรับการคืนบางส่วนด้วยคำขอแยกที่ระบุยอดชัดเจน รวมยอดต้องไม่เกินยอดคืนได้ของรายการต้นทาง หากระบบเดิมมีการทยอยคืนต้องรักษาข้อมูลเดิมและเทียบพฤติกรรมก่อนย้าย
- ตรวจสิทธิ์อีกครั้งตอนอนุมัติและตอนดำเนินรายการ ป้องกันการกดซ้ำ/คำขอซ้ำในธุรกรรมเดียวกัน และอัปเดตเอกสาร/บัญชีพร้อมประวัติตามขั้นตอนเดิม
- ไม่เปลี่ยนสูตรคำนวณดอกเบี้ย ค่าปรับ ภาษี หรือการลงบัญชีเพียงเพราะเพิ่มสิทธิ์ และไม่สร้างการโอนเงินจริงอัตโนมัติไปบริการภายนอกในงานนี้

### 5.4 เพดานส่วนลด

- ไม่มีตัวเลขเพดานที่เจ้าของยืนยัน จึงเริ่มสถานะ “ยังไม่ได้กำหนด” ส่วนลดนอกโปรที่ไม่มีเกณฑ์อนุมัติครบส่งให้เจ้าของ ไม่ถือค่าว่างเป็นอนุมัติได้ไม่จำกัด
- ใช้ราคาขายสุทธิหลังโปรที่ระบบคำนวณถูกต้องเป็นฐานของส่วนลดพิเศษ แล้วตรวจทั้งบาทและเปอร์เซ็นต์ ไม่เปลี่ยนกติกาซ้อนโปรของระบบเดิม
- ข้อเสนอเมื่อมีหลายเกณฑ์: ใช้เพดานที่เข้มที่สุดของเกณฑ์ที่มีผลกับสินค้า/หมวด/รายการนั้น ส่วนลดระดับทั้งใบต้องจัดสรรกลับแต่ละรายการเพื่อป้องกันเลี่ยงเพดานสินค้า การกำหนดจำนวนเงินและเปอร์เซ็นต์เป็น Decimal
- ราคาขั้นต่ำที่อาศัยต้นทุนตรวจเฉพาะฝั่งเซิร์ฟเวอร์ ผู้ไม่มีสิทธิ์ต้นทุนเห็นเพียงว่าต้องส่งเจ้าของ ไม่เห็นต้นทุน/กำไร/เกณฑ์ลับจากข้อความผิดพลาดหรือผลคำนวณ
- เลือกสินค้า เปลี่ยนจำนวน ราคา ส่วนลด หรือเงื่อนไขโปรที่มีผลแล้วต้องประเมินเส้นทางอนุมัติใหม่ ไม่ใช้ approval เก่ากับรายการใหม่
- ค่าเริ่มต้นเหล่านี้เป็นข้อเสนอของผู้ช่วย การตั้งเพดานจริงให้เจ้าของดำเนินการผ่านหน้าตั้งค่าและมีประวัติ ไม่มีการใส่ค่าที่เดาขึ้นในบัญชีจริง

### 5.5 ขอบเขต FINANCE และข้อมูลที่ใช้ร่วมกัน

- ให้มีขอบเขต “เฉพาะเคสที่ได้รับมอบหมาย”, “ข้อมูลที่เกี่ยวข้องกับสาขาที่เลือก” เมื่อทรัพยากรนั้นผูกสาขาได้ และ “ส่วนกลาง/ทั้งงาน FINANCE” ที่เจ้าของมอบหมายชัดเจน
- ไม่มี branchId ไม่ได้แปลว่าเปิดให้ทุกสาขา และตำแหน่งผู้จัดการการเงินหรือบัญชีไม่ได้สิทธิ์ส่วนกลางทุกข้อมูลจากชื่อตำแหน่งเพียงอย่างเดียว
- ข้อมูลลูกค้าที่ใช้ร่วมกันตรวจความสัมพันธ์กับรายการที่ผู้ใช้เข้าถึงได้ การเห็นรายการหนึ่งไม่เปิดข้อมูลทุกงาน/ทุกสาขาของลูกค้าคนนั้น
- รายงานรวมและการเปรียบเทียบต้องตรวจสิทธิ์ทุกชุดข้อมูลที่นำมารวม แยกสิทธิ์ดูยอดขาย/รายงานกำไร/ส่งออกออกจากกัน
- งานโอนสินค้าตรวจสิทธิ์ต้นทางและปลายทางตามขั้นตอนส่ง/รับ ไม่ใช้สิทธิ์สาขาใดสาขาหนึ่งเป็นทางลัดแก้ได้ทั้งสองฝั่ง

### 5.6 ประวัติและการรักษาข้อมูลเดิม

- รักษาค่าการเก็บ/soft archive เดิมในรอบนี้ ไม่เพิ่มคำสั่งลบประวัติอัตโนมัติ ไม่สรุปว่าค่าเริ่มต้นจากโค้ดคือค่าจริงใน production
- เพิ่มตัวเลือกค้นรวมประวัติที่ archive แล้ว โดยใช้สิทธิ์และการปกปิดแบบเดียวกับประวัติปัจจุบัน การเปลี่ยนระยะเวลาเก็บหรือเส้นทางทำลายข้อมูลเป็นการตั้งนโยบายแยกที่ยังไม่ได้อนุมัติ
- ตรวจสิทธิ์รายละเอียดด้วยสิทธิ์ปัจจุบันของผู้ดูและขอบเขตของเหตุการณ์ ณ เวลานั้น ต้องตรวจย้อนหลังได้แม้รายการต้นทางถูกปิดใช้งาน/ย้าย/ลบตามขั้นตอน โดยไม่ใช้เหตุผลว่าไม่มีรายการแล้วจึงเปิด raw payload ให้ทุกคน
- ผู้ไม่มีสิทธิ์ข้อมูลสำคัญเห็นข้อความสรุปที่ปลอดภัย ไม่มีค่าจากชื่อเหตุการณ์ เหตุผลอิสระ ผลค้นหา สถิติหรือ URL ที่ทำให้ข้อมูลสำคัญรั่วออกมา
- ผูกหลักฐานสำเร็จของการเปลี่ยนเงินและสิทธิ์กับการเขียนเหตุการณ์ที่ทนทาน การเปิดดู/ดาวน์โหลดต้องมีร่องรอยจากฝั่งเซิร์ฟเวอร์ การเปลี่ยนหน้าที่ไม่เรียกเซิร์ฟเวอร์อาจใช้เหตุการณ์จาก client แต่ระบุแหล่งที่มาและไม่ถือเป็นหลักฐานยืนยันการเปลี่ยนเงิน

## 6. ขอบเขตการพัฒนาและเกณฑ์ส่งมอบ

### สิ่งที่ต้องส่งมอบ

1. ทะเบียนสิทธิ์ครอบคลุมเมนู หน้า API คำสั่งงาน รายงาน เอกสาร export ช่องทาง real-time และงานอัตโนมัติที่กระทำแทนผู้ใช้ พร้อม mapping ว่าแต่ละจุดตรวจ permission และ scope ใด
2. โมเดลตำแหน่ง ชุดสิทธิ์ และการมอบหมายหลายตำแหน่งตามงาน/ขอบเขต พร้อมตัวตรวจสิทธิ์ที่ใช้ร่วมกัน ฝั่ง server เป็นผู้ตัดสิน
3. หน้าจัดการพนักงาน/ตำแหน่งสำหรับเจ้าของ และหน้าประวัติสำหรับพนักงานทุกคน โดยรายละเอียดปกปิดตามสิทธิ์
4. การบังคับข้อมูลต้นทุน/กำไร/เงินเดือน การอนุมัติตามนโยบาย และบันทึกคืนเงินตามอนุมัติ
5. การบันทึกกิจกรรมทั้งโปรแกรมและตรวจสอบความครบถ้วน โดยต่อยอดระบบประวัติเดิม
6. แผนย้ายจาก role/company/branch และสิทธิ์รายบุคคลเดิม พร้อมรายการความต่างและข้อมูลที่จะได้รับผล ไม่เปลี่ยนบัญชีจริงจากการเดาตำแหน่ง

### วิธีเปลี่ยนจากระบบเดิม

- สำรวจ effective access เดิมก่อน เพื่อแยกสิทธิ์ที่ต้องรักษาจากสิทธิ์ที่ต้องถอนตามนโยบายใหม่
- สร้าง mapping จาก role เดิม + company grants + สาขา + สิทธิ์เฉพาะราย ไปยังตำแหน่งและขอบเขตเสนอ ห้าม map พนักงานที่มีสิทธิ์พิเศษเป็นผู้จัดการทั้งหมดเพียงเพื่อรักษาสิทธิ์บางข้อ
- รายการที่มีสิทธิ์ต่างจากแม่แบบให้เสนอชุดตำแหน่งที่สื่อหน้าที่หรือการมอบหลายตำแหน่ง ไม่กลับไปเพิ่ม override ราย username
- รายงานผลต่างให้เจ้าของตรวจในหน้ามอบหมายก่อนเปิดใช้จริง รวมข้อจำกัดที่ตั้งใจถอนตามนโยบายใหม่ และสิทธิ์ที่ยังไม่กำหนด
- ทำเป็นช่วงตามหมวดได้ แต่เกณฑ์จบยังเป็นทั้งโปรแกรม ห้ามกล่าวว่าควบคุมครบหากหน้า/API/export ใดที่มีข้อมูลสำคัญยังใช้ทางผ่านเดิมที่ข้ามกติกา
- คงการยืนยันตัวตน CSRF rate limit และข้อกำหนดเฉพาะของ public/customer/integration endpoints ไม่เอา staff role guard ไปครอบ endpoint สาธารณะโดยไม่แยกบริบท

### ตัวอย่างเกณฑ์ทดสอบที่ต้องผ่าน

- ผู้ไม่ใช่เจ้าของเปิดหน้า URL หรือเรียก API จัดการสิทธิ์โดยตรงไม่ได้
- username ที่เป็นผู้จัดการ A และขาย B อนุมัติส่วนลดของ B ไม่ได้
- ผู้มีบัญชี A และขาย B เห็นต้นทุนเฉพาะ A แม้รวมหลายตำแหน่ง
- ปิดสิทธิ์/ถอนตำแหน่งแล้วคำขอถัดไปใช้สิทธิ์ล่าสุด การได้รับสิทธิ์เดียวกันจากอีกตำแหน่งแสดงเหตุผลได้
- พนักงานไม่อนุมัติส่วนลดตนเอง ส่วนเจ้าของทำได้ต่อเมื่อมีเหตุผลและประวัติครบ
- ส่วนลดเกินบาทหรือเปอร์เซ็นต์อย่างใดอย่างหนึ่งส่งเจ้าของ และค่าว่างไม่ทำให้ผ่านเพดาน
- แก้จำนวน/ราคา/ส่วนลดหลังอนุมัติไม่สามารถใช้ผลอนุมัติเดิม
- การเงินคืนเงินโดยไม่มี owner approval ไม่ได้ คืนเกินยอด/เปลี่ยนรายการ/กดซ้ำแล้วไม่เกิดการคืนซ้ำ
- การลดดอกเบี้ย/ยกเว้นค่าปรับและยกเลิกขายไม่ผ่านเพียงเพราะมีบทบาทผู้จัดการ
- พนักงานทุกคนเห็นสรุปกิจกรรม แต่ต้นทุน/กำไร/ข้อมูลส่วนบุคคลที่ไม่มีสิทธิ์ไม่รั่วใน response, export, query filters, search, statistics หรือรายละเอียด log
- ประวัติแสดงผู้กระทำจริงสำหรับพนักงาน เจ้าของ งานอัตโนมัติ และความพยายามเข้าที่ไม่สำเร็จ ไม่มีรหัสผ่าน/โทเคน
- เมื่อระบบบันทึกประวัติขัดข้อง ธุรกรรมสำคัญไม่สำเร็จโดยไร้หลักฐาน และมีทางตรวจ/ส่งซ้ำที่ไม่ทำธุรกรรมเงินจริงซ้ำ
- การลบ/แก้ข้อความประวัติผ่านสิทธิ์แอปทำไม่ได้ และการดูประวัติไม่สร้าง audit recursion
- ใช้ข้อมูลทดสอบและฐานข้อมูลแยกตามแนวทางโปรเจกต์ รัน local checks และทดสอบ API/หน้าจอจาก checkout เดียวกันก่อนส่งมอบโค้ด

## 7. ผลตรวจความพร้อมและรายการตั้งค่าก่อนเปิดใช้จริง

- ผ่านการอ่านโดยผู้ตรวจอิสระตามขั้นตอน builder check: จุดที่ผู้ตรวจถามเรื่องสิทธิ์ข้อมูลสำคัญ การอนุมัติส่วนลดของเจ้าของเอง และผู้ดำเนินการคืนเงินจริง ได้รับคำตอบจากเจ้าของและรวมไว้แล้ว
- ตารางตำแหน่งเริ่มต้น ขอบเขต FINANCE ผู้สร้างคำขอ และสูตรใช้เพดานเป็นข้อเสนอของผู้ช่วยที่ระบุชัดในส่วนที่ 5 ส่วนการเก็บประวัติรักษานโยบายเดิมแทนการเลือกอายุใหม่โดยไม่มีข้อมูล
- ผู้พัฒนาตัดสิน schema/API ชื่อ permission รายละเอียด cache/versioning วิธี transaction/outbox และการแบ่งลำดับงานได้ โดยต้องรักษาพฤติกรรมและเกณฑ์ส่งมอบข้างต้น
- ก่อนเปิดใช้จริงต้องมีทะเบียนสิทธิ์จากโค้ดครบทุกหมวด ตัวเลขเพดานที่เจ้าของตั้ง และ mapping ผู้ใช้จริงที่ผ่านการตรวจ ไม่จำเป็นต้องเลือกค่าตัวเลขหรือใช้ข้อมูลพนักงานจริงเพื่อวางแผนและสร้างหน้าจอ
- แบบฉบับนี้ยังไม่ใช่การเปิดสิทธิ์ โอนเงิน merge หรือ deploy ระบบจริง
