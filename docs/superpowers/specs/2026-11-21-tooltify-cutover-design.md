# ย้ายสต๊อกและประวัติขาย Tooltify มาใช้ BESTCHOICE เป็นระบบหลัก

วันที่: 2026-11-21 (Asia/Bangkok)
สถานะ: เจ้าของให้เดินหน้าจัดทำ implementation plan หลัง scrutinize (2026-11-21: “ครับผม สร้างแผนได้ลย”) — ยังไม่ได้สั่งดำเนินการนำเข้าจริง

## 1. เป้าหมายและสิ่งที่เจ้าของยืนยัน

เจ้าของต้องการย้ายสต๊อกและประวัติขายจาก Tooltify เข้า BESTCHOICE และยืนยันว่า **จะหยุดใช้ Tooltify** เมื่อย้ายสำเร็จ จึงใช้การย้ายครั้งเดียวพร้อมเวลาตัดระบบ ไม่สร้างงานซิงก์ต่อเนื่องสองระบบ

เจ้าของยืนยันเพิ่มว่า **barcode ของเครื่องคือ IMEI ของเครื่องนั้น**: จับคู่ `Tooltify.บาร์โค้ดสินค้า → Product.imeiSerial` โดยตรง เก็บเป็นข้อความรักษาเลขครบทุกหลัก ใช้ระบุตัวเครื่อง ไม่ใช่รหัสรุ่น และไม่ใช่รหัสเหตุการณ์ขาย

ผลสำเร็จคือสินค้าในคลังตรงกับของจริงและขายต่อได้ ประวัติขายค้นย้อนหลังได้ ยอดและจำนวนตรวจย้อนกลับถึงไฟล์ต้นทางได้ และพนักงานทำรายการใหม่ใน BESTCHOICE หลังเวลาที่กำหนด

สิ่งที่ยังไม่ได้ยืนยัน: วันเวลาเปิดใช้จริง ช่วงประวัติที่ต้องเก็บทั้งหมด และมีงานค้างที่อยู่เฉพาะ Tooltify หรือไม่ รายการเหล่านี้เป็นข้อมูลสำหรับตรวจความพร้อมก่อนย้าย ไม่ใช่ข้อเท็จจริงที่สมมติว่าตอบแล้ว

## 4. ขอบเขตที่เสนอ

### สต๊อกใช้งานจริง

รับเฉพาะของที่เป็นกรรมสิทธิ์และมีอยู่จริงตาม snapshot ณ เวลาตัดระบบ แยกสาขาและสถานะพร้อมขาย/จอง/ชำรุด/รอตรวจตามข้อมูลที่ยืนยัน ห้ามทำทุกแถวเป็นพร้อมขายโดยอัตโนมัติ

เครื่องที่เจ้าของระบุว่า barcode คือ IMEI ให้ตรวจราย IMEI: หนึ่งเลขเป็นเครื่องเดียวใน snapshot เดียวกัน รายการซ้ำแม้ต่างสาขาต้องพักตรวจ ไม่เลือกแถวล่าสุดเองและไม่เพิ่มเลขต่อท้าย IMEI ถ้าต้นทางระบุเป็น serial อย่างชัดเจนจึงใช้เส้นทาง serial แยก อุปกรณ์เสริมตรวจราย SKU และจำนวน โดยต้องพิสูจน์ความหมายจำนวนในรายงานจริงก่อนขยายเป็น Product รายชิ้น

IMEI เดิมปรากฏในหลายบิลได้เมื่อมีคืน/รับซื้อกลับ/ขายใหม่ จึงห้ามกันประวัติขายซ้ำด้วย IMEI เพียงตัวเดียว และห้ามตัดเครื่องออกจาก snapshot เพียงเพราะเคยขาย IMEI นั้นในอดีต ใช้ snapshot สุดท้ายยืนยันสถานะปัจจุบันและเก็บทุกเหตุการณ์ขายที่พิสูจน์ได้

จับคู่กับ Product เดิมทั้งหมดทั้ง active และ soft-deleted ไม่ตรวจแค่รหัส `TTFY-` และไม่คืนชีพสินค้าที่ขายแล้ว ถูกลบ หรือมีสัญญาอ้างอิงโดยอัตโนมัติ รายการชนหรือหาสาขาไม่ได้ต้องพักตรวจ ไม่มีการล้างคลังเดิมเป็นส่วนหนึ่งของการย้ายนี้

ราคา: ใช้รายการราคาปัจจุบันของ BESTCHOICE ที่ตรงรุ่น/สภาพและตรวจแล้ว หรือไฟล์ราคาจาก Tooltify ที่มีหลักฐานตรงสินค้า บันทึกที่มาทุกราคา ไม่อนุมานราคาปัจจุบันจากราคาขายในอดีต ไม่เติมศูนย์เงียบ ๆ; เครื่องที่ยังขาดราคาห้ามเปิดขายจนเติมครบ

วิธีต่อกับระบบจริง: ใช้ helper ราคาที่ `ProductsService.create()` ใช้อยู่ (`autofillProductPriceFromTemplate`, `fillFinancePriceFromTemplate`, `syncPriceRowsFromColumns`, `hasSellingPrice`) ภายใน transaction ของ importer ตามเงื่อนไขเดียวกับการสร้างสินค้า ไม่สมมติว่า Prisma `createMany` เรียก service เหล่านี้เอง ต้องมี `product_prices` ที่สอดคล้องกับคอลัมน์ราคาสำหรับผู้ใช้ข้อมูลเดิม ค่า missing/invalid ต้องคงเป็นข้อผิดพลาดหรือสถานะพัก ไม่ผ่าน `sanitizeMoney → 0` แล้วตั้ง IN_STOCK; ใช้ DTO/service validation ที่จำเป็นโดยไม่เรียกกระบวนการซื้อหรือโพสต์บัญชีซ้ำ

### ประวัติขาย

เสนอเก็บใน ImportedSale เพื่อค้นและรายงานย้อนหลังตามแนวทางเดิม พร้อมเลขบิล วันที่ สินค้า จำนวน ต้นทุน ราคาขาย กำไร ผู้ขายและช่องทางที่มีหลักฐาน ใช้เวลาไทยและ Decimal สำหรับเงิน

แยกจำนวนบิลกับจำนวนรายการ/ชิ้นให้ถูกต้อง แสดงช่วงวันที่ครอบคลุมและที่มาข้อมูลให้ชัด รายการขายเดิมไม่สร้าง Sale/สัญญา/รับเงิน/ค่าคอมใหม่ ไม่รวมยอดกับธุรกรรม BESTCHOICE เดิมอย่างอัตโนมัติจนพิสูจน์ว่าไม่ทับซ้อน

งานหน้าเว็บ/API ที่ต้องเพิ่มอย่างชัดเจน: ค้นด้วย IMEI/barcode และเลขบิลผ่าน DTO → service filter → query key/ช่องค้นบนหน้า ImportedSalesPage; เพิ่มช่วงวันที่บนหน้าเว็บ และแยก `billCount` จาก `lineCount` ใน API/ป้ายหน้าเว็บ ปัจจุบันหน้าเดิมมีตัวกรองช่องทางเท่านั้นและแสดง `rows.length` ใต้ป้าย “จำนวนบิล/รายการ” จึงยังไม่ผ่านเกณฑ์ค้นประวัติหลังเลิกใช้ Tooltify

ต้องสำรวจส่วนคืนสินค้า ยกเลิก เคลม เบิกซ่อม และตัดสต๊อกทำสัญญาที่อยู่ในรายงานด้วย ห้ามถือว่าตาราง “รายการขาย” แทนทุกเหตุการณ์ หากพบเหตุการณ์ที่มีผลต่อยอด ต้องแยกประเภทและผูกบิลเดิมก่อนรับรองรายงานสุทธิ; เก็บเอกสารส่วนที่ไม่นำเข้าปฏิบัติการไว้ค้นย้อนหลัง

### เงื่อนไขก่อนเลิกใช้ Tooltify

ประวัติสถิติไม่แทนลูกหนี้หรืองานค้าง สำรวจสัญญาที่ยังผ่อนอยู่ เงินจอง งานซ่อม/เคลม เครดิตลูกค้า และเอกสารรับประกัน หากอยู่เฉพาะ Tooltify ต้องมีแผนรับช่วงใน BESTCHOICE และตรวจยอดก่อนยกเลิกบริการ ขอบเขตนี้ยังไม่ได้รับคำตอบจากเจ้าของ จึงห้ามสรุปว่าปิด Tooltify ได้ทันทีหลังนำเข้าสองตาราง

การตั้งยอดเปิดบัญชีสินค้าคงเหลือเป็นอีกเกณฑ์ตรวจรับ: เทียบว่าทุนของที่จะนำเข้าเคยรับรู้ใน BESTCHOICE/ระบบบัญชีที่ใช้แล้วหรือไม่ ใช้กลไกยอดเปิดที่ตรวจสอบได้และให้ผู้รับผิดชอบบัญชีตรวจยอดก่อนเปิดขาย ไม่โพสต์รายการซื้อหรือเงินจ่ายซ้ำจากไฟล์สต๊อกโดยอัตโนมัติ

## 5. การเตรียมข้อมูลและการกันซ้ำ

1. ทำบัญชีไฟล์ต้นฉบับ: ชื่อ ขนาด checksum ช่วงรายงาน ช่วงวันที่จริง สาขา/ร้าน จำนวนบิล/แถว/ชิ้น และยอดเงิน เก็บต้นฉบับแบบไม่แก้ไขในพื้นที่จำกัดสิทธิ์ ไม่ใส่ข้อมูลลูกค้าใน Git หรือรายงานสาธารณะ
2. เลือกชุดไฟล์ขายที่ครอบคลุมต่อเนื่องจากข้อมูลเก่าสุดที่ดึงได้ถึงเวลาตัดระบบ; ถ้าช่วงใดไม่มีการขาย ต้องมีหลักฐานรายงานศูนย์ ไม่ถือว่าไฟล์หายเท่ากับยอดศูนย์
3. ไฟล์คงเหลือเลือกเพียง snapshot สุดท้ายต่อสาขา ไม่รวมหลาย snapshot เข้าด้วยกัน ประวัติรับเข้าใช้เติมรายละเอียดเท่านั้น
4. Parser หา section และชื่อคอลัมน์ ตรวจคอลัมน์บังคับและชนิดข้อมูลจริง รูปแบบไม่รู้จักต้องหยุดพร้อมเหตุผล ไม่ข้ามไฟล์ที่อ่านได้ 0 รายการเงียบ ๆ
5. ทุกแถวมีสถานะใหม่/จับคู่เดิม/ซ้ำที่พิสูจน์แล้ว/ต้องแก้ไข/ยกเว้นพร้อมเหตุผล ผลรวมทุกกลุ่มต้องเท่ากับต้นทาง
6. ประวัติขายใช้ source line ID ถ้าต้นทางมี หากไม่มี ให้เลือกชุดช่วงไม่ทับกันและสร้าง identity ที่คงที่ในชุด canonical โดยรักษาจำนวนรายการซ้ำจริงภายในบิลไว้ ชื่อไฟล์หรือเลขแถวเพียงอย่างเดียวไม่พอสำหรับกันไฟล์ export ซ้ำ การแก้บิลเดิมต้องปรากฏเป็น conflict ไม่ถูก skip เงียบ ๆ
7. แยก key ของตัวเครื่องจาก key ของเหตุการณ์ขาย เก็บ key เดิมของ ImportedSale ไว้ก่อนจนสำรวจพิสูจน์ข้อจำกัด; คู่ Accessories ซ้ำต้องเทียบบิลจริงก่อนตัดทิ้งหรือเพิ่ม quantity หากต้องแก้ schema ให้แก้ขั้นต่ำตามหลักฐานและไม่บังคับให้ IMEI เครื่อง unique ตลอดประวัติ ทดสอบหลายชิ้นในบิล ไฟล์ซ้ำ ไฟล์ทับช่วง บิลแก้ไข และเครื่องเดิมขายใหม่ต่างบิล
8. แต่ละรอบมี batch ID และ durable manifest ผูก checksum กับ source-row identity, target IDs และค่าก่อนเปลี่ยน การนำเข้าแต่ละช่วงบันทึกผลและ provenance ใน transaction เดียวกัน รองรับหยุดกลางทาง/รันต่อโดยไม่เพิ่มซ้ำ
9. Dry-run ต้องตรวจ DB เป้าหมายและ conflict จริง พร้อมยอดเงิน/จำนวนก่อนและหลัง ไม่ใช่เพียงนับแถว parser ห้ามแก้รูปแบบ/ข้อมูลต้นทางหลัง dry-run ผ่านโดยไม่ตรวจใหม่
10. ทางเข้า cutover รับชนิด `current-stock-snapshot` อย่าง explicit และปฏิเสธ flow report ไม่ใช้ fallback `imported−sold` หรือ flag ที่ลืมแล้วเปลี่ยนความหมายข้อมูลได้ ยืนยัน duplicate IMEI ก่อนสร้าง candidates ไม่เรียก reconstruction เดิมเพื่อเลือกแถวล่าสุดเงียบ ๆ
11. หมวดต้องเป็น mapping explicit รวมหมวดเครื่องนอกที่พบจริงและเก็บแหล่งที่มาให้ถูกต้อง หมวดไม่รู้จักหรือ barcode ไม่เข้ากับประเภทต้องพักตรวจ ห้ามใช้ fallback ACCESSORY/imeiSerial=null เพื่อทำให้แถวนำเข้าผ่าน

## 6. ลำดับดำเนินงานและจุดตรวจรับ

| ระยะ | ผลส่งมอบ | เงื่อนไขไปต่อ |
|---|---|---|
| A สำรวจ | บัญชีไฟล์ ช่วงข้อมูลที่ขาด ตารางงานค้าง และตารางจับคู่ข้อมูล | รู้ขอบเขตและแหล่งข้อมูลทุกกลุ่ม |
| B ปรับตัวนำเข้า | parser ตามหัวจริง การกันซ้ำ รายงานผิดพลาด batch manifest และคำสั่งย้อนคืน | ทดสอบกรณีสำคัญผ่าน |
| C ซ้อม | นำเข้าฐานทดสอบที่แยกจาก production ด้วยข้อมูลตัวแทนสภาพฐานจริง | ยอดตรง รันซ้ำไม่เพิ่ม ย้อนคืนได้ และไม่มีผลข้างเคียง |
| D เตรียมตัดระบบ | ตารางเวลาดำเนินงานจริงตามเวลาซ้อม ผู้รับผิดชอบแต่ละขั้น และไฟล์/รายงานตรวจยอด | ราคาพร้อม สาขาถูก งานค้างมีที่รับช่วง และสำรองกู้คืนได้ |
| E ย้ายรอบสุดท้าย | หยุดการเปลี่ยนข้อมูลที่เกี่ยวข้อง ดึงไฟล์สุดท้าย dry-run นำเข้า ตรวจยอด | ไม่มีส่วนต่างที่อธิบายไม่ได้ |
| F เปิดใช้และเลิกบริการเก่า | เปิดขาย BESTCHOICE ตรวจยอดวันแรกและสรุปหลัง 7 วัน | ค้นเอกสารเก่าได้ งานค้างรับช่วงครบ แล้วจึงยกเลิก Tooltify |

กำหนด T เป็นเวลาสุดท้ายที่ Tooltify รับรายการ และ G เป็นเวลาเปิด BESTCHOICE โดย T ≤ G เวลาทั้งสองใช้ Asia/Bangkok ประวัติและ snapshot ต้องตรงสถานะหลังธุรกรรมสุดท้ายที่ T

ช่วง T ถึง G พักการขาย/คืน/โอน/ปรับสต๊อกที่เกี่ยวข้องในทั้งสองระบบ ธุรกรรมที่หลีกเลี่ยงไม่ได้ให้ลงทะเบียนชั่วคราวพร้อมเลขอ้างอิง ผู้รับผิดชอบ และเวลา แล้วลง BESTCHOICE ครั้งเดียวหลัง G พร้อมตรวจยอด ห้ามบันทึกย้อนเข้า Tooltify โดยไม่มี reconciliation ใหม่

ก่อน T ซ้อมกระบวนการจริงและกำหนดเวลาหยุดสูงสุดจากเวลาที่วัดได้ หากนำเข้าหรือตรวจยอดเกินหน้าต่างดังกล่าว ให้ใช้แนวทางย้อนคืนก่อนเปิดใช้ ไม่สัญญาระยะเวลาจากจำนวนแถวเพียงอย่างเดียว

## 7. เกณฑ์ผ่าน

- มือถือ/แท็บเล็ต: IMEI/serial สาขา สถานะและต้นทุนตรง snapshot ที่นับจริง ไม่มีเครื่องซ้ำและไม่มีเครื่องขายแล้วกลับมาพร้อมขาย
- อุปกรณ์เสริม: จำนวนและต้นทุนราย SKU/สาขาตรง โดยแยกรายการที่ไม่ใช่สินค้าจริง เช่น คูปอง/บริการ ตามหลักฐาน ไม่ใช้ blacklist เดิมเงียบ ๆ
- ประวัติ: จำนวนบิล รายการ/ชิ้น ยอดขาย ต้นทุน กำไร และเหตุการณ์คืน/ยกเลิกตรงต้นทางแยกเดือน/ช่องทาง ส่วนต่างต้องเป็น 0 หรือมีรายการปรับที่เจ้าของรับทราบก่อนดำเนินการ
- ทดสอบขอบวัน/เดือนเวลาไทย ของแถมราคา 0 ราคาติดลบตามประเภทเหตุการณ์ คอลัมน์หาย และ IMEI ที่เก็บเป็นตัวเลข/ข้อความ
- ทดสอบ snapshot ที่มี IMEI เคยขายแล้วแต่คืนเข้าคลัง: ยังได้หนึ่งเครื่องตาม snapshot; snapshot IMEI ซ้ำต้อง fail; ประวัติ IMEI เดียวต่างบิลต้องเก็บครบ; หมวดเครื่องพร้อม barcode ผิดรูปแบบต้องพักตรวจ ไม่กลายเป็น accessory
- Integration test importer ต้องตรวจราคาคอลัมน์และ `product_prices` พร้อมกัน และยืนยันว่าไม่ปล่อยเครื่องข้อมูลราคาไม่ครบเป็น IN_STOCK; unit test parser เดิมที่ยอมแปลงค่าผิดเป็น 0 ไม่ใช่หลักฐานว่าพร้อมเปิดขาย
- เปิดหน้า Stock/POS และประวัติขายด้วยสิทธิ์ที่เกี่ยวข้องได้ ค้นสินค้าและเลขบิลตัวอย่างได้ รายการขาดราคาหรือพักตรวจขายไม่ได้
- ขายเครื่องที่นำเข้าได้ในฐานทดสอบ พร้อมตรวจผลสต๊อก/ต้นทุนตามระบบปัจจุบัน ไม่ใช้การขายปลอมใน production เพื่อทดสอบ
- นำเข้าไฟล์เดิมซ้ำไม่เพิ่มแถว/ยอด ไม่มี Sale, Contract, Payment หรือค่าคอมย้อนหลังถูกสร้างจากงานนำเข้าประวัติ
- ทดสอบ DB ด้วย isolated PostgreSQL harness ของโครงการ เมื่อมีการแก้โค้ดต้องผ่าน checks ตาม AGENTS.md รวม `npm run local:check` และทดสอบ flow นำเข้าเพิ่มเติม เพราะ preview มาตรฐานไม่ได้พิสูจน์ flow นี้ทั้งหมด

## 8. สำรองและย้อนคืน

สร้างสำรองฐานก่อนเขียนและพิสูจน์เส้นทางกู้คืนในฐานแยก เก็บไฟล์ export สุดท้าย รายงานตรวจยอด และ batch manifest ห้ามสมมติว่ามี PITR โดยไม่ตรวจสถานะจริงในวันดำเนินงาน

ก่อน G: ถ้าตรวจไม่ผ่าน ให้ปิดการเขียนส่วนที่เกี่ยวข้องและย้อนเฉพาะ batch ใช้ soft-delete สำหรับ Product ที่สร้างใหม่ตามกฎโครงการ และคืนค่าก่อนแก้เฉพาะแถวที่ยังไม่ถูกใช้งานหรือเปลี่ยนต่อ ไม่ลบสินค้าโดยเลือก prefix `TTFY-` ทั้งหมด ประวัติ imported_sales เป็น immutable import ตาม schema เดิม จึงย้อนคืนเฉพาะ target IDs ที่ batch นี้สร้างและพิสูจน์ provenance แล้ว

หลัง G: ถ้ามี Sale/Contract/โอนคลัง/ธุรกรรมใหม่อ้างอิงแล้ว ห้ามคืน backup ทั้งฐานทับรายการจริงหรือย้อน batch แบบอัตโนมัติ ให้ระงับเฉพาะสินค้าที่มีปัญหาและแก้ด้วยรายการปรับที่ตรวจสอบได้ การกลับไป Tooltify ต้องเป็นเหตุการณ์กู้คืนที่ตรวจธุรกรรมหลัง G ครบก่อนเปิดเขียนอีกครั้ง

ของเดิมที่ชน IMEI หรือถูกลบไม่ถูก restore โดยปริยาย แม้ CLI เก่าเคยทำเช่นนั้น; batch ที่ย้อนแล้วรันใหม่ต้องเป็นการดำเนินการ explicit ตาม provenance ไม่ตีความ soft-delete ว่าอนุญาตนำกลับมาขาย

## 9. สิ่งที่ให้ผู้พัฒนาตัดสินใจใน implementation plan

- รูปแบบจัดเก็บ batch/row provenance และขนาด transaction โดยต้องรองรับ crash/retry/rollback ตามข้อ 5 และ 8
- โครง parser และ schema migration ขั้นต่ำเพื่อเก็บ source identity/จำนวน/ประเภทเหตุการณ์ที่ตรวจพบจริง
- การจับคู่ราคาและหมวดกับเครื่องมือเดิม รวมถึงใช้สถานะพักที่มีอยู่หรือเพิ่มกลไกจำกัดการขาย โดยรักษาเงื่อนไขห้ามขายเมื่อข้อมูลยังไม่ครบ
- รายละเอียดชุดทดสอบและคำสั่ง runbook ที่ผูกกับ code revision และ database identity จริง ห้ามแสดงคำสั่งเขียน production เป็นคำสั่งพร้อมรันก่อนผ่าน rehearsal

## 10. เรื่องที่ต้องยืนยันก่อนลงมือย้ายจริง

1. งานค้างที่อยู่เฉพาะ Tooltify: มีประเภทใดบ้าง และใครรับช่วง (เปลี่ยนขอบเขตงานได้)
2. ช่วงประวัติทั้งหมดที่ต้องเก็บ: เสนอเก็บตั้งแต่เริ่มใช้งานจน T; ตรวจจากไฟล์และ export เพิ่มก่อนขอให้เจ้าของเติมข้อมูลที่หาไม่ได้
3. สาขา/ราคาปัจจุบัน/สถานะสต๊อก: พิสูจน์จากข้อมูลก่อน ขอเจ้าของตัดสินเฉพาะรายการที่จับคู่ไม่ได้
4. T, G และผู้ตรวจยอด/ผู้รับผิดชอบบัญชี: กำหนดหลังซ้อมและรู้เวลาที่ต้องใช้

เอกสารนี้เป็นการออกแบบและแผนเปลี่ยนระบบระดับงาน ยังไม่มีการแก้ product code นำเข้า ล้างฐาน หรือยกเลิกบริการใด ๆ
