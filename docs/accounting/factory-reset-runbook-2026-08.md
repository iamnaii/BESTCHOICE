## 🔴 ผลข้างเคียงที่เกิดจากขอบเขตใหม่ — ต้องรู้ก่อนตัดสินใจ

### สินค้าคงเหลือจะไม่มีมูลค่าในบัญชี

รอบแรกล้างสินค้าไปด้วย จึงไม่มีปัญหานี้ **รอบนี้สินค้ายังอยู่บนชั้นแต่รายการบัญชี
(`journal_entries` / `journal_lines`) ถูกล้างทั้งหมด** ⇒

```
ตารางสินค้า      : มีเครื่องอยู่ N เครื่อง  ✅
งบทดลอง S11-2001 : 0.00 บาท               ❌  ← ไม่ตรงกัน
```

**ต้องตั้งยอดยกมาสินค้าคงเหลือ** (`Dr S11-2001 สินค้าคงเหลือ / Cr ส่วนของเจ้าของ S32-1101`)
ก่อนเริ่มบันทึกรายการจริง ไม่งั้นตอนขายเครื่องเหล่านี้ ระบบจะตัดต้นทุนจากบัญชีที่ยอดเป็น 0
⇒ สินค้าคงเหลือติดลบ

เรื่องเดียวกันนี้ครอบถึง: **เงินสด/ธนาคารคงเหลือ · เจ้าหนี้การค้า · เงินมัดจำลูกค้าที่ยังไม่คืน**

> ⛔ **ยังลงมือไม่ได้** — `.claude/rules/accounting.md` หัวข้อ "ห้ามลง JV มือในบัญชีที่เลนส์
> inter-co อ่านต่อสัญญา" ระบุว่า `S11-2001` เป็นบัญชีที่ **ปลอดภัย** สำหรับ JV มือ ✅
> แต่ยอดตั้งต้นต้องมาจากการนับสต็อกจริง + ราคาทุนจริง ซึ่งเป็นงานของเจ้าของ/ผู้สอบ
> **ห้ามให้ระบบเดายอดให้เอง**

### สถานะสินค้าที่เคยขายตอนเทส

เครื่องที่ขายไปตอนเทสจะค้างสถานะ `SOLD_*` โดยไม่มีใบขายอยู่จริง สคริปต์คืนให้ **3 สถานะ**:

| สถานะ | ทำอะไร | เหตุผล |
|---|---|---|
| `SOLD_CASH` · `SOLD_INSTALLMENT` | → `IN_STOCK` อัตโนมัติ | คลาสเดียวกับ `SaleVoidService` (ยกเลิกใบขาย) — ตอนขายบังคับว่าต้องเป็น `IN_STOCK` มีราคาอยู่ก่อน และไม่มี flow ไหนแตะราคาระหว่างขาย ⇒ เครื่องกลับมาพร้อมราคาของตัวเอง |
| `RESERVED` | → `IN_STOCK` อัตโนมัติ | กติกาเรียกว่า "benign โดยโครงสร้าง" — การปลดจองคือคืนสภาพเดิม |
| `REPOSSESSED` · `REFURBISHED` · `SOLD_RESELL` | **ไม่แตะ** รายงานให้ดูอย่างเดียว | เครื่องยึด/เปลี่ยนเครื่องถือ **ราคาเครื่องใหม่** ติดตัวมา ต้องตีราคาใหม่ก่อนขาย — flip ให้เองคือการข้ามด่านราคาทั้งคลัง (`.claude/rules/database.md` → "ประตูเข้า IN_STOCK") |

กรรมสิทธิ์ (`ownedByCompanyId`) ที่ย้ายไป FINANCE ตอนเปิดสัญญา ถูกคืนให้ SHOP ทั้งหมด

## ทำไมเปลี่ยนจาก "เก็บรายการสั้น ที่เหลือล้างหมด" เป็น "จำแนกครบสองทาง"

รอบแรกใช้การกลับด้าน (ล้างทุกตารางที่ไม่อยู่ใน keep list) ซึ่ง**ถูกต้องสำหรับขอบเขตนั้น**:
ตารางที่ลืมจำแนก = ถูกล้าง = ตรงเจตนาอยู่แล้ว

ขอบเขตใหม่พลิกข้อนี้ — รายการที่เก็บโตเป็น 69 ตาราง และในนั้นมี **11 ตารางที่ seed อยู่ใน
migration เท่านั้น ไม่มี seed script ใด ๆ**:

```
account_role_map · payment_method_configs · sso_config · bank_accounts · reverse_reasons
notification_templates · template_categories · supplier_payment_methods
```

ล้างแล้ว **สร้างกลับไม่ได้** (ต้องไปรื้อ migration มารันมือ) ⇒ ผลของการ "ลืมจำแนก"
เปลี่ยนจาก *ปลอดภัย* เป็น *สูญหายถาวร*

ตอนนี้ทุกตารางถูกระบุครบสองทาง (`KEEP_TABLES` 72 + `WIPE_TABLES` 131 = 203) และสคริปต์
**หยุดพร้อมรายชื่อ** ถ้าเจอตารางที่ไม่อยู่ในลิสต์ไหนเลย (model ใหม่ที่เพิ่มวันหลัง)
แทนที่จะเดาแล้วล้างทิ้ง

## ข้อเท็จจริงที่ตรวจแล้ว (ไม่ใช่การเดา)

### 1. `TRUNCATE` ผ่าน trigger กันลบของ `audit_logs` ได้

```sql
-- migration 20260520300000_audit_log_archive_immutable
CREATE TRIGGER audit_logs_no_delete
BEFORE DELETE ON "audit_logs"
FOR EACH ROW                       -- ← row-level
EXECUTE FUNCTION audit_logs_block_delete();
```

PostgreSQL **ไม่จุด row-level trigger ตอน TRUNCATE** และ grep แล้วไม่มี
`BEFORE TRUNCATE` / `FOR EACH STATEMENT` ที่ไหนเลย ⇒ `DELETE` ถูกบล็อก แต่ `TRUNCATE` ผ่าน

**ไม่ต้อง drop trigger** — drop แล้วลืมสร้างกลับ = เกราะกันแก้หลักฐานหายถาวร

> **ข้อค้นพบด้านความปลอดภัย (แยกเรื่อง):** คอมเมนต์ใน migration เขียนว่า *"Any code path
> (ORM, raw SQL, migration) that attempts DELETE will raise"* แต่ **TRUNCATE ไม่ใช่ DELETE**
> ⇒ ใครมีสิทธิ์ TRUNCATE ลบ audit trail ได้ทั้งตาราง · ถ้าต้องการปิดช่องนี้ ให้เพิ่ม
> `BEFORE TRUNCATE ... FOR EACH STATEMENT` **หลังล้างเสร็จ** (ใส่ก่อนจะบล็อกงานนี้เอง)

### 2. 🔴 โซ่ที่เกือบทำประวัติแชทหายทั้งหมด

การตรวจ FK อัตโนมัติจับได้ 4 เคสที่ตาคนมองไม่เห็น — เคสร้ายที่สุด:

```
chat_rooms.attribution_id → ads_attributions.contract_id → contracts
                                                            ↑ ต้องล้าง
```

`ads_attributions` เก็บไม่ได้ (ชี้ต่อไปที่ `contracts`) แต่ถ้าปล่อยให้
`TRUNCATE ads_attributions CASCADE` ทำงาน มันจะลบ `chat_rooms` **และ `chat_messages`
(`onDelete: Cascade`)** ทั้งหมด = **ประวัติแชทที่เจ้าของสั่งให้เก็บหายเกลี้ยงแบบเงียบ ๆ**

#### ⛔ ทางแก้แรกที่คิดไว้ **ใช้ไม่ได้** — และอันตรายกว่าไม่ทำอะไรเลย

เวอร์ชันแรกใช้ `PRE_TRUNCATE_NULLIFY`: SET `chat_rooms.attribution_id = NULL` ก่อน TRUNCATE
ด้วยความเข้าใจว่า "ไม่มีแถวชี้แล้ว CASCADE ก็ลามไม่ได้" — **ผิด**

`TRUNCATE ... CASCADE` ลามตาม **การมีอยู่ของ FK constraint** ไม่สแกนแถวเลย
(เอกสาร PostgreSQL: *"Checking validity in such cases would require table scans,
and the whole point is not to do one"*)

พิสูจน์บน production จริง — สองคำสั่งใน `BEGIN ... ROLLBACK`:

```
BEGIN; TRUNCATE ads_attributions; ROLLBACK;
  ERROR: cannot truncate a table referenced in a foreign key constraint
  DETAIL: Table "chat_rooms" references "ads_attributions".

BEGIN; UPDATE chat_rooms SET attribution_id=NULL WHERE attribution_id IS NOT NULL;
       TRUNCATE ads_attributions; ROLLBACK;
  UPDATE 0                    ← เป็น NULL อยู่แล้วทุกแถวตั้งแต่แรก
  ERROR: (ข้อความเดิมเป๊ะ)
```

ร้ายที่สุด: **guard 3 ยกเว้น FK ที่อยู่ในลิสต์ NULLIFY** ⇒ "ทางแก้" ที่ไม่ทำงานไป**ปิดปาก
ด่านที่ควรหยุดก่อนเขียน** เหลือแค่ด่านตรวจหลัง commit = ชันสูตรหลังตาย · และ DRY_RUN
ก็ผ่านฉลุยพร้อมพิมพ์ `chat_rooms 7,551` ในคอลัมน์ "เก็บไว้" = ใบรับรองเท็จ

#### ✅ ทางแก้ที่ใช้จริง — `FK_DROP_RECREATE`

ถอด FK constraint จริงก่อน TRUNCATE แล้วสร้างกลับ **ในทรานแซกชันเดียวกัน**
(PostgreSQL ทำ DDL ใน transaction ได้ ⇒ พลาดกลางทาง constraint กลับมาเองครบ)
นิยาม constraint **อ่านสดจาก `pg_get_constraintdef()` ไม่ hardcode**

ทำไมทางอื่นไม่รอด: `ads_attributions.contract_id → contracts` ⇒ ต่อให้ย้าย
`ads_attributions` ไปฝั่งเก็บ หรือใช้ `DELETE` แทน `TRUNCATE` ก็ยังโดน
`TRUNCATE contracts CASCADE` ลามมาถึง `chat_rooms` อยู่ดี — **ถอด constraint คือทางเดียว**

อีก 3 เคสที่จับได้:

| FK | ผลถ้าไม่จับได้ | ทางแก้ที่ใช้ |
|---|---|---|
| `products → inspections` | ลบสินค้า**ทั้งคลัง** | เก็บ `inspections` (closure สะอาด ชี้ไป template/user ที่เก็บอยู่แล้ว) |
| `products → purchase_orders` | ลบสินค้า**ทั้งคลัง** | เก็บ `purchase_orders` + `po_items` (เป็นที่มาของสินค้าที่เก็บไว้) |
| `kyc_verifications → contracts` | — | **ล้าง** — FK บังคับ (ไม่ nullable) เก็บไม่ได้แม้อยากเก็บ |

ด่านนี้รัน **สดทุกครั้ง** ไม่พึ่งการตรวจครั้งเดียว — FK ใหม่ที่เพิ่มวันหลังจะเปิดช่องนี้ทันที

### ①.5 ปลดล็อกเครื่องที่ MDM + หยุด API ⚠️ ห้ามข้าม

**ก) ปลดล็อกเครื่องที่สั่งล็อกไว้ตอนทดสอบ — ทำ *ก่อน* ล้าง**

`mdm_lock_requests` เป็นบันทึกฝั่งเรา ส่วนคำสั่งล็อกจริงอยู่ที่ **PJ-Soft** ⇒ ล้างแล้ว
เครื่องยัง **ล็อกค้างอยู่ที่ผู้ให้บริการ** และระบบไม่มีบันทึกว่าเคยล็อกเครื่องไหนไว้
= ปลดไม่ได้ ตามไม่เจอ

```sql
-- ดูว่ามีเครื่องไหนถูกสั่งล็อกไปแล้วและยังไม่ปลด (รันก่อนล้าง)
-- EXECUTED_MANUAL / EXECUTED_API = ส่งคำสั่งไปที่ PJ-Soft แล้วจริง
-- (PENDING / APPROVED ยังไม่ได้ส่ง · REJECTED / FAILED / UNLOCKED ไม่ได้ล็อกอยู่)
SELECT m.id, c.contract_number, p.imei_serial, p.model, m.status, m.proposed_at
FROM mdm_lock_requests m
JOIN contracts c ON c.id = m.contract_id
LEFT JOIN products p ON p.id = c.product_id
WHERE m.status IN ('EXECUTED_MANUAL', 'EXECUTED_API')
  AND m.deleted_at IS NULL
ORDER BY m.proposed_at DESC;
```

มีแถว → ปลดล็อกผ่านหน้าจอ MDM (`/settings/integrations/mdm`) ให้หมดก่อน แล้วค่อยล้าง

> เก็บผลคิวรีนี้ไว้เป็นไฟล์ก่อนล้างด้วย — หลัง TRUNCATE ทั้ง `mdm_lock_requests`,
> `contracts` และเลข IMEI ที่ผูกกันจะหายพร้อมกัน ตามย้อนไม่ได้
