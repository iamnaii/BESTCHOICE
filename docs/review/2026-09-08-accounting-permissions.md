# สิทธิ์รายการบัญชีรายรับ–รายจ่าย

## พฤติกรรมที่เปลี่ยน

เดิมปุ่ม POST, อนุมัติ และกลับรายการใช้เงื่อนไขคนละชุด และช่องผู้อนุมัติรายจ่ายสามารถบันทึกชื่อที่ผู้กรอกเลือกเองลงเอกสารได้ เปลี่ยนเป็นสิทธิ์รายคนที่ OWNER กำหนดจาก **ตั้งค่า → ผู้ใช้ & สิทธิ์ → สิทธิ์รายการบัญชีรายรับ–รายจ่าย** (`/settings/access/accounting-permissions`)

| การทำรายการ | รายจ่าย | รายรับ |
| --- | --- | --- |
| POST โดยตรง | `EXPENSE_POST` | `INCOME_POST` |
| อนุมัติ | `EXPENSE_APPROVE` | `INCOME_APPROVE` |
| ยกเลิก / ลบร่าง / กลับรายการ | `EXPENSE_CANCEL` | `INCOME_CANCEL` |

- OWNER ที่ยังใช้งานมีสิทธิ์ทั้งหมด พนักงานอื่นต้องได้รับสิทธิ์เป็นรายคน ไม่มีสิทธิ์เริ่มต้นจากตำแหน่งหรือค่าตั้งค่า POST/ผู้อนุมัติ/กลับรายการแบบเก่า
- ผู้จัดการสาขารับสิทธิ์รายจ่ายได้เฉพาะสาขาที่ตนสังกัด รายรับยังอยู่ในขอบเขต OWNER / FINANCE_MANAGER / ACCOUNTANT
- สิทธิ์สร้างและแก้ไขร่างใช้ขอบเขตเดิม ผู้ไม่มีสิทธิ์ POST ยังบันทึกร่างได้ และส่งขออนุมัติได้เมื่อเปิด workflow เดิม ปุ่มออกจากฟอร์มไม่ใช่การยกเลิกเอกสาร
- สิทธิ์อนุมัติครอบคลุมการลงบัญชีอัตโนมัติที่เกิดจากการอนุมัติตามค่าตั้งค่าเดิม ไม่ต้องมีสิทธิ์ POST โดยตรงเพิ่ม ขั้นตอนแยกผู้สร้าง/ผู้อนุมัติรายรับยังบังคับเหมือนเดิม
- รายจ่ายไม่รับชื่อผู้อนุมัติจาก create/update อีกต่อไป การอนุมัติบันทึกผู้กดจริง; POST จากร่างเก่าล้างชื่อที่เคยเลือกไว้ และบันทึกผู้ POST ใน audit โดยแยกจากผู้อนุมัติจริง
- แสดงชื่อและประวัติการอนุมัติรายรับจาก event ที่เกิดขึ้นจริง ไม่ใช้ event POST แทน APPROVED; ผู้บันทึกใช้ชื่อผู้สร้างที่บันทึกในเอกสาร แม้ไม่มีประวัติ CREATED ไม่ใช้ชื่อผู้เปิดดูแทน

## การบังคับสิทธิ์

ใช้ SystemConfig `accounting_permissions` ผ่าน `GET/PUT /accounting-permissions` สำหรับ OWNER และ `GET /accounting-permissions/me` สำหรับสิทธิ์ของผู้ใช้งานปัจจุบัน การแก้ไขมี validation ผู้ใช้/สิทธิ์และ audit ใน transaction เดียวกัน ห้ามเขียนคีย์นี้ผ่าน generic settings endpoints

ทุก action ตรวจผู้ใช้ที่ยัง active และไม่ถูกลบจาก DB พร้อมสิทธิ์ปัจจุบันที่ service แม้เรียกข้าม controller หรือส่ง role เก่ามาก็ไม่ข้ามสิทธิ์ ตรวจสาขาจากเอกสารจริงสำหรับรายจ่าย เมื่อ config หายหรือผิดรูปแบบจะไม่ให้สิทธิ์พนักงาน

รายรับ POST ตรงไม่ได้เมื่อเปิด Maker-Checker; ใช้เงื่อนไขสถานะและ updatedAt ภายใน transaction ป้องกันข้อมูลร่างเปลี่ยนระหว่างอ่านกับ POST, POST/กลับรายการซ้ำ หรือคืนเอกสารที่ถูกดำเนินการแล้วกลับเป็นรออนุมัติ รายจ่ายใช้ lock เดียวกันสำหรับ POST/approve/void/delete/update

สิทธิ์กลับรายการสินทรัพย์ยังใช้ระบบเดิม แยกชื่อในหน้าตั้งค่าให้ชัดเจน ไม่มีการเปลี่ยนสูตรบัญชี VAT/WHT หรือเพิ่ม schema migration

## การตรวจสอบ

- API: 668 tests ผ่าน (53 suites); 1 suite / 3 tests ที่ข้ามเป็นรายการเดิมของชุดทดสอบ
- Web: 86 tests ผ่าน (11 files) รวมสิทธิ์จาก cache/เปลี่ยนผู้ใช้, การให้และถอนสิทธิ์, ผู้อนุมัติจริง และปุ่มกลับรายการ
- ทดสอบ API ใน PostgreSQL แยกสำหรับ integration เท่านั้น
- ตรวจพบระหว่าง browser QA ว่าฟอร์มรายรับส่งวันที่ optional เป็น `''` จน validation ปฏิเสธการบันทึก แก้ให้ CREATE ละค่าว่างของวันที่และ customerId ส่วน PATCH ส่ง null เมื่อตั้งใจล้างค่าและละ field เมื่อไม่แก้ไข พร้อม regression ฝั่ง serializer 3 tests และทดสอบบันทึก/ล้างค่ากับ DB จริง
- ทดสอบแข่งแก้ไข/POST และ POST/POST ด้วย transaction และ JE จริง ต้องมีเพียงหนึ่งคำสั่งสำเร็จ ยอดเอกสารและ JE ตรงกัน; mutation check ยืนยันว่าทดสอบจับการถอด updatedAt guard ได้
- แก้เลขอ้างอิง JE กลับรายการรายจ่ายเป็น `<documentId>:reversal` เพื่อไม่ชน unique key ของ JE เดิม โดยเก็บการเชื่อมเอกสารเดิมไว้ใน metadata และ audit
- API build แบบแยก output และ Web production build ผ่าน; scoped lint ไม่มี error
- การทดสอบหน้าจอใช้บริการและการลงบัญชีจริงบนข้อมูลจำลอง พร้อมการจำลองการส่งข้อมูลออกภายนอก ตรวจให้/ถอนสิทธิ์, บันทึกร่าง, POST, อนุมัติ และกลับรายการทั้งรายรับ–รายจ่ายจริง รวมตรวจ JE สมดุลและชื่อผู้ทำรายการ หลักฐานอยู่ใน `.tmp/payment-preview/check-accounting-permissions.json`, `check-accounting-form.json`, `check-accounting-clear.json` และ `accounting-preview-final-check.json` (ตรวจ source hash ตรงกัน 28 ไฟล์) ของ checkout นี้

ไม่มีการ deploy, เปลี่ยนสิทธิ์พนักงานจริง, ส่งข้อความภายนอก หรือแก้ข้อมูล production งานนี้ต้องกำหนดสิทธิ์พนักงานในหน้าตั้งค่าเมื่อเริ่มใช้พฤติกรรมใหม่

เปิดหน้าทดลอง: http://localhost:5197/settings/access/accounting-permissions — เลือกบัญชีทดสอบจากแถบด้านบนเพื่อดูสิทธิ์ของแต่ละคน มีเอกสารร่างและรออนุมัติสำรองไว้สำหรับตรวจด้วยตนเอง
