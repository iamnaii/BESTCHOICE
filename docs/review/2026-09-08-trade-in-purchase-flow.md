# รับซื้อเครื่อง / เทิร์นเครื่อง และการเตรียมสินค้าเข้าคลัง

ผู้ใช้อนุมัติให้ปรับ flow หลังทบทวน `/trade-in?zone=shop` เทียบกับ PO รับของทันที

## พฤติกรรมที่เปลี่ยน

- รับซื้อหน้าร้านยังใช้ 3 ขั้น: ผู้ขาย → ตรวจเครื่องและราคา → จ่ายเงินและลงนาม โดย API ระบุ `BUYBACK` เสมอ
- จ่ายเงินสดใช้บัญชีเงินสดของสาขา โอนใช้บัญชีจ่าย SHOP ตาม resolver เดิม ช่องธนาคารในฟอร์มเป็น **บัญชีผู้ขายที่รับเงิน** และไม่โหลดบัญชีของบริษัทมาปะปน
- ใช้ฟอร์มจ่ายเงินร่วมกันระหว่าง Quick Buy กับการยอมรับรายการที่ประเมินแล้ว ล็อกข้อมูลและลายเซ็นระหว่างบันทึก และเอาปุ่มยืนยันลายเซ็นซ้ำออก
- EXCHANGE ที่รับเครื่องใหม่บันทึก `TRADE_IN_CREDIT` ล้างข้อมูลผู้รับโอน และแสดงใบรับเครื่องเทิร์น ไม่กล่าวว่าเครดิตถูกนำไปหักยอดแล้ว
- เอกสารเก่าที่ยืนยัน CASH/TRANSFER ไว้ยังพิมพ์วิธีจ่ายเดิม แม้ `flow` เก่าจะเป็น EXCHANGE ไม่มีการเปลี่ยนประเภทรายการย้อนหลัง
- หลังรับเครื่องสำเร็จมีทางไป `/products/:id?zone=shop` พร้อมสถานะรอเตรียมขายและปุ่มเอกสาร จากหน้ารายละเอียดรายการก็เปิดสินค้าเดิมได้
- ใช้ `UsedDeviceDetailsFields` ร่วมระหว่าง PO และการแก้ข้อมูลสินค้า: แบตเตอรี่ กล่อง และประกัน ส่วนรูป 6 มุมและราคาขายใช้ workflow ของสินค้าเดิม
- พนักงานขายได้รับคำแนะนำให้ถ่ายรูปและให้ผู้จัดการตั้งราคา ตรงกับสิทธิ์จริงในหน้าสินค้า

## สาเหตุที่แก้

Quick Buy เดิมไม่ได้ระบุ flow เมื่อสร้าง TradeIn จึงได้ default `EXCHANGE` จาก Prisma แม้จ่าย CASH/TRANSFER จากนั้น `accept()` ข้าม journal ที่ทำเฉพาะ BUYBACK การออกเลขใบสำคัญภายหลังไม่ได้ลง journal ชดเชย

เทสต์ reproduction วิ่งผ่าน create → appraise → accept โดยจำลอง default ของฐานและพบ `EXCHANGE` ตามเดิมก่อนแก้ หลังแก้มีชุด PostgreSQL แยกตรวจ flow จริง สินค้า และ journal ของ SHOP ว่ามี Dr สินค้ามือสอง / Cr บัญชีจ่ายเพียงหนึ่งรายการ

ปฏิเสธราคารับซื้อที่ไม่เป็นบวกหรือมีทศนิยมเกิน 2 ตำแหน่งก่อนสร้าง record รวมถึง 0.001 ที่ฐานจะปัดเป็นศูนย์ ตรวจ consent ผู้รับโอน และบัญชีเงินสดสาขาก่อนเริ่มด้วย

Quick Buy ยังคงเรียกบริการแต่ละขั้นตามเดิม ถ้าขั้นประเมิน/รับเครื่อง/ออกเอกสารล้มเหลวหลังสร้างรายการ API คืน `tradeInId` เพื่อเปิดรายละเอียดเดิม ฟอร์มไม่ชวนบันทึกรายการใหม่ทันที กรณี API ปฏิเสธก่อนสร้างยังเก็บข้อมูลในฟอร์มไว้แก้

## การตรวจและ local

ผลรอบสุดท้าย: API trade-in 102 tests ผ่าน, isolated PostgreSQL 32 tests ผ่าน (9 กรณีรับซื้อ/เทิร์น), Web 1,695 tests ผ่าน, Shared 35 tests ผ่าน และ `local:check` ผ่านครบ 17 checks รวม browser 1440/390 px ไม่มี console error

- API unit regression ของ trade-in ทั้งชุด
- `bash tools/test-chat-credit.sh`: PostgreSQL ชั่วคราวที่สร้างและ migrate เอง ตรวจเงินสด/โอน เครดิตไม่รวมโบนัสในต้นทุน เอกสารเก่า ออกใบสำคัญซ้ำ รับเครื่องซ้ำ สาขาข้ามสิทธิ์ ราคาที่ไม่ถูกต้อง บัญชีจ่ายที่ขาด รายการค้าง และ gate รูป/ราคาก่อนเข้าคลัง
- Frontend ทดสอบ payload ผู้รับโอน การเปลี่ยนกลับเป็นเงินสด ฟอร์มเมื่อ API ปฏิเสธ เครดิตเทิร์น และลิงก์สินค้าตามสิทธิ์ รัน receiving tests เดิมของ PO ด้วย
- `npm run local:check` เพิ่มการใช้หน้าเว็บจริงที่ 1440/390 px: รับซื้อ → ลายเซ็น → เอกสาร PDF → หน้าสินค้า → ตั้งราคา → ถ่ายรูป 6 มุม → ยืนยันเข้าคลัง โดยใช้บริการจริงบนฐานข้อมูลตัวอย่าง
- ขยาย preview ให้รองรับ trade-in, contact picker, รายละเอียดสินค้า รูป ราคา และข้อมูลประกอบ ใช้ JSON limit 20 MB เท่ากับ production สำหรับรูปบัตร/ภาพ base64

ภาพล่าสุดและผลตรวจอยู่ `.tmp/local-preview/` โดยมี `trade-in-payment-*.png`, `trade-in-handoff-*.png`, `trade-in-stock-*.png` และ `check.json`

## ขอบเขตที่ต้องแยกให้ชัด

รับเครื่องสำเร็จยังเป็น `PHOTO_PENDING` จนรูปและราคาขายผ่าน gate เดิม การแชร์ช่องข้อมูลเครื่องไม่ใช่การสร้าง formal Inspection ของ PO

การนำเครดิตเทิร์นไปหัก POS/สัญญาอัตโนมัติยังไม่มีเส้นทางเชื่อมในระบบ จึงไม่แสดงปุ่มหรือสถานะว่าหักเครดิตสำเร็จ การแก้ครั้งนี้ไม่ backfill flow หรือ journal ย้อนหลัง และไม่เพิ่ม idempotency key สำหรับกรณีเครือข่ายขาดหลัง server บันทึกสำเร็จ

Local ใช้ข้อมูลตัวอย่างและ AI จำลอง ไม่ใช่ผล deploy หรือหลักฐานทดสอบกับพนักงานจริง
