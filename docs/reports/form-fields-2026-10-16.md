# ผลตรวจและแก้ฟิลด์ — 16 ตุลาคม 2026

รอบนี้ต่อจากงานหน้านัดเข้าร้าน โดยตรวจฟิลด์ของหน้าใช้งานหลักและคอมโพเนนต์ร่วม ไม่ใช่การรับรองว่าทุกหน้า/ทุกธุรกรรมของระบบผ่านครบแล้ว

## สิ่งที่แก้

| ส่วน | ก่อนแก้ | หลังแก้ |
|---|---|---|
| ลูกค้า — มือถือ | ชื่อเล่นกว้าง 28–40 px; ชื่อและข้อมูลติดต่อเบียดหลายคอลัมน์ | เรียงคอลัมน์ตามขนาดจอ รวมส่วนข้อมูลเพิ่มเติม/ที่อยู่/บุคคลอ้างอิง |
| ใบจอง | ลูกค้า 40 px แต่สาขา 34 px | ช่องข้อมูลหลักสูง 44 px เท่ากัน; preset บนมือถือมีพื้นที่แตะ 44 px |
| สินค้า | select 43 px กับ input 39 px; ข้อมูลมือสองยังแบ่งสามคอลัมน์บนมือถือ | ใช้มาตรฐาน 44 px; จัดคอลัมน์มือถือใหม่และเชื่อม label |
| สาขา/ผู้ใช้ | ช่องหลักกับช่องที่อยู่ขนาดต่างกัน และ label หลายจุดไม่เชื่อม control | มาตรฐานฟอร์มร่วมและ id ที่ไม่ซ้ำแต่ละ instance |
| แจ้งปัญหาเครื่อง | ช่อง IMEI ยุบเหลือ 25 px เมื่อ flex เปลี่ยนเป็นแนวตั้ง | คงความสูง 56 px และจำกัด flex-1 เฉพาะแนวนอน |
| เพิ่มค่าใช้จ่าย | OWNER ไม่มีสาขาประจำถูก redirect ระหว่าง query สาขายังโหลด | แยก loading/error/empty และเปิดฟอร์มหลังได้สาขา |
| ฟอร์มค่าใช้จ่าย — มือถือ | ผู้ขาย/จำนวน/ราคาเบียดหลายคอลัมน์; header/footer และ Quick Start ล้นภายใน modal | ช่องเต็มความกว้างบนมือถือ, footer แยกแถว, ปุ่มบันทึกอยู่ในจอ, ข้อความประเภทเอกสารอ่านเป็นภาษาไทย |
| สร้างผู้ใช้ | `/users/new` เป็น static route ไม่มี `id` แต่ component เข้าโหมดแก้ไข | เข้าโหมดสร้าง เปิดอีเมล/รหัสผ่านบังคับ และใช้ create API |
| ฟอร์มกลาง | label ไม่เชื่อม input; aria-invalid/ข้อความผิดพลาดอยู่ที่ div | ส่ง id และ aria ไปยัง control โดยตรง พร้อม error ID แยกแต่ละฟอร์ม |
| ช่องเลือกที่อยู่ | ใช้ลูกศร/Enter/Escape ไม่ได้ครบ และ Escape ปิด dialog ทั้งหน้า | เลือกด้วยคีย์บอร์ด, กลับมาเปิดด้วย pointer ได้, Escape ครั้งแรกปิดรายการ ครั้งถัดไปจึงปิด dialog |
| ตัวกรอง | ช่องค้นหา วันที่ สถานะ และเลขหน้าหลายจุดไม่มี accessible name | เพิ่มชื่อและเชื่อม label ในหน้าที่ตรวจ รวมชำระเงิน สัญญา ค่าใช้จ่าย เครดิต ผู้ติดต่อ |

มาตรฐาน `formControlClass` ใช้กับฟอร์มที่ปรับโดยเจาะจง ไม่เปลี่ยน compact controls ทั้งระบบหรือเอกสารพิมพ์ด้วย global CSS กฎธุรกิจ จำนวนเงิน ภาษี สิทธิ์ และ handlers บันทึกเดิมคงอยู่ ยกเว้นการแก้ mode ของเส้นทางสร้างผู้ใช้และสถานะรอโหลดสาขา

## ขอบเขตตรวจ

- Chromium กับ API ของ checkout นี้บน PostgreSQL แยก ใช้ข้อมูลสังเคราะห์และ outbound transports จำลอง
- 25 กรณี × 4 ขนาด (320/390/768/1440 px) × 2 ธีม = 200 observations
- ลูกค้า: รายการ/รายละเอียด/สร้าง/ขยายส่วนเพิ่มเติม; ใบจอง: รายการ/สร้าง; เครดิต; สัญญา: รายการ/ขั้นเลือกสินค้า; ชำระเงิน; ค่าใช้จ่าย: รายการ/สร้าง; สินค้า: รายการ/ใหม่/มือสอง/อุปกรณ์; POS; สาขา: รายการ/สร้าง; ผู้ใช้: บัญชี/บุคคล/HR; รับซื้อ; ผู้ติดต่อ; แจ้งปัญหาเครื่อง
- ตรวจ pathname และ heading/control ที่เจาะจงก่อนวัด เพื่อไม่ให้หน้า error หรือ redirect ผ่านแทนหน้าที่ต้องการ
- วัดฟอนต์ ความสูง ความกว้างขั้นต่ำมือถือ accessible name และขอบเขตช่อง/ปุ่ม; ตรวจภาพจริงประกอบเพื่อหาการบีบ/ตัดภายในหน้า
- ทดสอบกรอก/ล้าง, validation, label focus, ยกเลิก/เปิดใหม่, ที่อยู่ต่อเนื่อง, เปลี่ยนประเภทสินค้า, เพิ่ม/ลบรายการค่าใช้จ่าย และปุ่มค้นหา IMEI โดยไม่บันทึกธุรกรรมจริง
- เพิ่มทดสอบขยาย root font เป็น 20 px ที่ 1280 px ทั้งสองธีม (50 observations) แยกจากชุดหลัก

## ข้อจำกัดที่ยังต้องแยกตรวจ

- ไม่ใช่การทดสอบทุกเส้นทางของระบบ ทุกสิทธิ์ หรือการบันทึก/ลงบัญชีทุกประเภทเอกสาร
- ยังไม่มี staging และเครื่อง iPhone/Android จริงให้ทดสอบตามข้อมูลล่าสุดจากผู้ใช้
- ปัญหาสาขา production ที่ไม่ได้ผูกบริษัท ซึ่งทำให้หน้านัดเข้าร้านไม่มีสาขา เป็นปัญหาข้อมูลเดิมและไม่ได้แก้ข้อมูลจริงในรอบนี้
- งานนี้ยังอยู่ใน local checkout; ไม่ได้ commit/push/merge/deploy รอบใหม่
