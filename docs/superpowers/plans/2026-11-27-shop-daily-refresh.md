# แผน: build หน้าร้านใหม่ทุกวัน ให้ราคาและสต๊อกที่ Google เห็นสด (ผลตรวจ SEO ข้อ 10)

สถานะ: **ทำแล้ว — รอ merge และกดรันเองครั้งแรก** (หัวข้อ "ตรวจหลังทำ") · เจ้าของตัดสิน 2 ข้อแล้ว 28 พ.ย. 2569
ที่มา: `docs/reports/2026-11-27-web-shop-seo-audit-handoff.md` ข้อ 10 · เจ้าของเลือกให้วางแผนข้อนี้ก่อนข้อ 9 (27 พ.ย. 2569)

## ปัญหา

หน้าร้านเป็น HTML ที่ prerender ไว้ตอน build (`apps/web-shop/scripts/prerender.mjs` ดึงข้อมูลจาก API จริง)
แต่ build เกิดเฉพาะตอนมีโค้ดเข้า `main` หรือกดรันเอง (`.github/workflows/deploy-gcp.yml` job `build-web`)
⇒ ราคา สต๊อก รายการเครื่อง และ sitemap ที่ Google / AI เห็นค้างตั้งแต่ deploy ครั้งล่าสุด
(คนที่เปิดเว็บเห็นของสด เพราะหน้าโหลดข้อมูลใหม่หลังเปิด — ค้างเฉพาะ HTML ดิบที่บอทอ่าน)

## แนวทาง

workflow ใหม่ `.github/workflows/shop-refresh.yml` — ตั้งเวลา (`schedule`) + กดรันเองได้ (`workflow_dispatch`)
build และ deploy **เฉพาะหน้าร้าน** (`hosting:shop`) ไม่แตะ API ฐานข้อมูล หรือหลังร้าน

| ขั้น | ทำอะไร | ทำไม |
|---|---|---|
| 1 | หาคอมมิตที่ขึ้นเว็บอยู่จริง = run ล่าสุดของ `deploy-gcp.yml` บน `main` ที่ job `deploy-web` สำเร็จ (`gh api` · `GITHUB_TOKEN` สิทธิ์ `actions: read`) แล้ว checkout คอมมิตนั้น | ไม่ใช้หัว `main` — โค้ดที่ยังไม่ผ่านเทสต์ / deploy ล้ม ต้องไม่หลุดขึ้นเว็บทางนี้ รอบนี้เปลี่ยนแค่ข้อมูล ไม่เปลี่ยนโค้ด |
| 2 | มี run ของ `deploy-gcp.yml` บน `main` กำลังรันหรือรอคิว → จบรอบนี้แบบสำเร็จ (ข้าม) | **ห้ามใช้ concurrency group ร่วมกับ deploy หลัก** — GitHub ยกเลิก run ที่รอคิวอยู่เมื่อมี run ใหม่เข้า group เดียวกัน ⇒ รอบตั้งเวลาอาจไปยกเลิก deploy จริงที่รอคิว |
| 3 | `npm run build:prerender --workspace=apps/web-shop` ด้วยโหมดเข้มใหม่ `PRERENDER_STRICT=1` | ปกติหน้าสินค้าเป็น best effort: ดึงรายการสินค้าไม่ได้ ⇒ build ผ่านแต่**ไม่มีหน้าสินค้าเลย** และ sitemap ไม่มีสินค้า (`prerender.mjs:222-247`) — รับได้ตอน deploy โค้ด แต่ถ้ารันทุกวัน API สะดุดครั้งเดียวสินค้าทั้งร้านหายจาก Google · โหมดเข้มล้มเมื่อ: ดึงรายการไม่ได้ · เก็บหน้าสินค้าได้ไม่ครบ · หน้าที่ใช้ API มีกล่อง error |
| 4 | เทียบจำนวนหน้าสินค้าที่ build ได้กับ sitemap บนเว็บจริง — น้อยกว่าครึ่ง → ไม่ deploy | กัน API ตอบผิดแบบไม่ error (เช่นคืนรายการว่าง) · ขายหมดจริงครึ่งร้านในวันเดียวแทบไม่เกิด ถ้าเกิด กดรันเองได้ |
| 5 | ตรวจซ้ำขั้น 1–2 ทันทีก่อน deploy | ลดช่วงที่ deploy หลักเริ่มระหว่างรอบนี้ (ถ้าชนกันจริง หน้าร้านกลับเป็นโค้ดเดิมจน deploy ถัดไป — ไม่พัง แค่ช้า) |
| 6 | `firebase deploy --only hosting:shop` แล้วตรวจหน้าร้านขึ้น (ใช้ด่านเดียวกับ `deploy-gcp.yml:847-879`) + sitemap บนเว็บมีจำนวนสินค้าเท่าที่ build | ยืนยันว่าข้อมูลใหม่ขึ้นจริง |
| — | ล้มขั้นใดก็ตาม = **เว็บคงของเดิม** + GitHub ส่งอีเมลแจ้ง run ล้ม | ทางล้มต้องปลอดภัยกว่าทางผ่าน |

### ต่างจากแผนตอนทำ (และเหตุผล)

- **เครื่องที่ขายออกระหว่าง build ไม่นับว่า "เก็บไม่ครบ"** — เก็บหน้าได้ไม่ครบ ⇒ ดึงรายการสินค้ารอบสอง เครื่องที่ยังขายอยู่แต่ไม่มีหน้าเท่านั้นทำให้ล้ม
  (ถ้านับทุกเครื่อง รอบ 15:00 น. จะล้มทุกครั้งที่มีคนซื้อระหว่าง build) · ดึงรอบสองไม่ได้ = นับทุกเครื่องที่ขาด (ล้ม)
- **โหมดเข้ม: หน้าที่ใช้ API มีกล่อง error = ลองใหม่ 1 ครั้ง แล้วล้ม** (หน้า marketing ⇒ build แดง · หน้าสินค้า ⇒ นับเป็นเครื่องที่เก็บไม่ได้)
- **โหมดเข้มนับคำขอ /api ที่ล้มต่อหน้าด้วย** (ต่อไม่ติด / 5xx / 429) — ดูกล่อง error อย่างเดียวไม่พอ: ทดสอบชี้ API ไป URL ที่ตอบไม่ได้
  หน้าแรก / หน้ารวม / โปรโมชันผ่านด่านเดิมทุกข้อ เพราะ React Query ลองใหม่แบบเว้นช่วง networkidle จึงมาถึงตอนหน้ายังเป็น skeleton
  ก่อนกล่อง error ขึ้น · คำตอบที่ส่งไม่ถึงหน้า (หน้าปิด / หน้ายกเลิกคำขอเอง) ไม่นับเป็น API ล้ม
- **เว้นระยะคำขอ `installment-preview` 1.25 วินาที (ทั้งรอบตั้งเวลาและ deploy หลัก)** — endpoint นี้ติด `@Throttle` 60 คำขอ/นาที/IP
  และหน้าสินค้าหนึ่งหน้าเรียก 3–4 ครั้ง (ยอดผ่อนเริ่มบนหัวหน้า + เรท 1 / เรท 2 ในตัวคำนวณ) ⇒ ทดสอบโหมดเข้มกับ API จริง (28 พ.ย.)
  เก็บหน้าสินค้าได้ 32 จาก 52 — ตัวที่พังทั้งหมดเป็น 429 ของ endpoint นี้ · **deploy หลักวันนี้ก็โดน** (best effort จึงเก็บหน้าไปทั้งที่ยอดผ่อนยังไม่ขึ้น
  ราว 40% ของหน้าสินค้า) · เว้นระยะแทนโควตาต่อนาที เพราะโควตาปล่อยยิงรวดเดียวแล้วคำขอถัดไปรอเกือบเต็มนาที นานกว่า timeout ของหน้า (45 วิ) ·
  แลกกับ build ช้าลงราว 3–4 นาที (เพดานของ API) · ไม่แตะเพดานฝั่ง API
- **เทสต์รันในตัว workflow** (job `tests` ก่อน job `refresh` + ทุก PR ที่แตะไฟล์ด่าน) — เทสต์ vitest ของหน้าร้านไม่ได้รันใน CI เลย
  (`deploy-gcp.yml` job `test-web` รันเฉพาะ `apps/web`) ด่านของรอบนี้จึงเป็น `node --test` ที่ไม่ต้อง npm ci
- **เครื่องมือมาจากคอมมิตของ workflow ส่วนหน้าร้าน build จากคอมมิตที่ขึ้นเว็บ** — คัดลอกเครื่องมือไว้ใน `RUNNER_TEMP` ก่อน checkout คอมมิตที่ขึ้นเว็บทับ ·
  คอมมิตที่ขึ้นเว็บยังไม่มีโหมดเข้ม (ช่วงหลัง merge ก่อน deploy หลักขึ้น) ⇒ **ข้ามรอบ** แทนการ build แบบ best effort
- **ขั้น 4 กดรันเองไม่ข้ามอัตโนมัติ** — ต้องติ๊ก `allow_big_drop` (กันกดรันซ้ำตอน API ตอบผิดแล้วหลุดขึ้นเว็บ)
- **ขั้น 5 ข้ามเมื่อคอมมิตที่ขึ้นเว็บเปลี่ยนไปด้วย** (ไม่ใช่แค่ deploy หลักกำลังรัน) — ไม่งั้น deploy โค้ดเก่าทับโค้ดใหม่
- **ข้ามรอบ = run เขียว + เหตุผลในสรุปของ run** · ล้ม = run แดง + อีเมล GitHub
- `GH_TOKEN` ใส่เฉพาะสองขั้นที่ถาม GitHub API และยืนยันตัวกับ GCP หลัง build — โค้ดใน node_modules ตอน npm ci/build ไม่เห็นทั้งคู่
- ชื่อ job `Deploy Web to Firebase Hosting` ของ `deploy-gcp.yml` มีเทสต์อ่านไฟล์จริงจับการเปลี่ยนชื่อ (PR ที่แตะ deploy-gcp.yml รันเทสต์นี้)

## ตรวจหลังทำ

1. กดรัน `shop-refresh` เองหนึ่งครั้ง ดูว่า deploy เฉพาะ `hosting:shop` และใช้คอมมิตเดียวกับที่ขึ้นเว็บ
2. เทียบราคาเครื่องหนึ่งใน HTML ดิบ (`curl -A GPTBot …/products/<id>`) กับ `GET /api/shop/products/<id>`
3. จำลอง API ล้ม (ชี้ `PRERENDER_API_BASE` ไป URL ที่ตอบ 503) ⇒ run ต้องล้มก่อน deploy

## ค่าใช้จ่ายและผลข้างเคียง

- เวลา GitHub Actions ราว 10–14 นาทีต่อรอบ (ช่วงเก็บหน้าสินค้าราว 4 นาทีเพราะเพดาน installment-preview ของ API)
- Firebase Hosting เก็บทุกเวอร์ชันที่ deploy — ควรตั้งจำนวนเวอร์ชันที่เก็บ (Firebase console › Hosting › site `bestchoicephone-shop` › Release storage settings) ไม่งั้นพื้นที่โตทุกวัน
- `schedule` ของ GitHub เป็นเวลา UTC (06:00 น. ไทย = `0 23 * * *` · 15:00 น. = `0 8 * * *`) และอาจช้าได้หลายนาทีช่วงคนใช้เยอะ
  · repo สาธารณะที่ไม่มีความเคลื่อนไหว 60 วัน GitHub ปิด schedule เอง (repo นี้มีคอมมิตทุกวัน)
- deploy หลักยังทำงานเหมือนเดิม ยกเว้นการเว้นระยะ installment-preview ⇒ job `Build Web + Web-Shop` ช้าลงราว 3–4 นาที
