# ใบสำคัญจ่ายรับซื้อเครื่อง — 8 กันยายน 2026

ปรับ PDF จากปุ่มใบสำคัญในหน้ารับซื้อเป็น A4 พื้นขาว เขียวเข้มเฉพาะเส้นแบ่งและยอดจ่าย ข้อมูลเรียงจากบริษัท/เลขเอกสาร → ชื่อเอกสาร → ผู้ขาย → เครื่อง → ยอดสุทธิและจำนวนเงินตัวอักษร → วิธีจ่าย → คำรับรองและลายเซ็น ใช้ IBM Plex Sans Thai 400/500/600 ที่มีอยู่และฝังใน PDF จาก asset ที่ Nest บรรจุไปกับ API

## รายละเอียด

- หัวเอกสารแสดงชื่อ ส่วนยอดสุทธิขนาดใหญ่อยู่ด้านขวาใต้ตารางรายการเครื่อง พร้อมจำนวนเงินตัวอักษรด้านซ้ายตามคำขอเจ้าของ ใช้เส้นตารางบางแทนแถบพื้นสีเต็ม และรักษารายการกับยอดรวมให้อยู่หน้าเดียวกัน
- ตัดข้อมูลติดต่อซ้ำ อีเมลและสำนักงานใหญ่ที่เติมตายตัว ไอคอนประดับ กล่องคำเตือน และ watermark ใหญ่
- เงินสดระบุผู้ขายเป็นผู้รับเงิน บัญชีโอนยังเป็นของผู้ขาย ไม่ใช้บัญชีจ่ายของบริษัท
- คงเลขเอกสาร วันที่ จำนวนเงิน IMEI ข้อมูลผู้ขาย คำรับรอง และลายเซ็นทั้งสองฝ่าย เมื่อไม่มีลายเซ็นมีพื้นที่ลงชื่อ
- ต้นฉบับ/สำเนาเห็นชัดที่หัวกระดาษ สำเนามีข้อความที่ขอบล่างทุกหน้าผ่าน CSS page margin box; ถอดเลขหน้าตายตัว 1/1 และรักษาบล็อกลายเซ็นร่วมกันเมื่อมีการต่อหน้า
- ถอด QR ที่ชี้ `/verify/voucher/:number` เพราะเว็บไม่มีเส้นทางนี้ ไม่เปลี่ยนสิทธิ์ของ API ตรวจเอกสาร
- เอกสารเครดิตเทิร์นยังใช้ชื่อใบรับเครื่องเทิร์นและระบุว่ายังไม่ยืนยันการใช้เครดิต ใช้ paymentMethod ที่บันทึกจริงเช่นเดิมสำหรับ CASH/TRANSFER เก่า

การเปลี่ยนนี้ไม่แก้ยอด วิธีลงบัญชี การอนุมัติ หรือลำดับการออกเลขเอกสาร ไฟล์ blob ที่เปิดไว้ก่อนแก้เป็นข้อมูลเดิม ต้องกดเปิด PDF ใหม่จากหน้ารับซื้อ

## ตรวจสอบ

- API trade-in: 105 tests / 7 suites ผ่าน รวม escaping, ข้อมูลเอกสาร, สำเนา และลายเซ็น
- PostgreSQL แยก: 32 tests / 5 suites ผ่าน รวมเส้นทางรับซื้อและเอกสารย้อนหลัง
- Render ด้วย VoucherHtmlBuilder + VoucherPdfRenderer จริง: CASH, TRANSFER, CREDIT และชื่อ/ที่อยู่ยาวพร้อมยอด 12,345,678.25 บาท อยู่ใน A4 หนึ่งหน้า
- ตัวอย่างที่อยู่ 28 บรรทัดต่อสองหน้าอย่างครบถ้วน ลายเซ็นอยู่ด้วยกันและทุกหน้ามีสถานะสำเนา ตรวจภาพจาก PDF จริง ขอบเขตข้อความ และฟอนต์ที่ฝังแล้ว
- ตัวอย่าง render อยู่ `.tmp/voucher-design/` (ข้อมูลตัวอย่าง; ไม่ commit PDF/ภาพลายเซ็นทดสอบ)
- `npm run local:check` ผ่าน 17 checks รวม types, lint, Web 1,696 tests, Shared 35 tests, build และ browser 1440/390 px ตรวจ PDF ผ่าน API ของ preview ที่รีสตาร์ตจาก checkout นี้แล้วเป็นแบบใหม่หนึ่งหน้าและฝังฟอนต์ไทย ผลล่าสุดอยู่ `.tmp/local-preview/check.json`

## ชื่อไฟล์เมื่อส่งออก

ยืนยันจากไฟล์ที่ผู้ใช้แนบ: `8b6785e2-39e7-488c-8910-4f3d49116983.pdf` คือเอกสารแบบเก่าเลขที่ `EXP-20260900008` ชื่อ UUID มาจากการเปิด Blob URL ซึ่งไม่เก็บ Content-Disposition เดิมไว้ ทดสอบใน Chromium แล้วทั้ง Blob และ File ที่กำหนดชื่อยังดาวน์โหลดแบบ default เป็น UUID

- API ส่งชื่อ UTF-8 เช่น `ใบสำคัญจ่ายเงิน_EXP-20260900008.pdf` พร้อม ASCII fallback และเปิดเผย Content-Disposition ให้ frontend อ่านข้าม origin ได้
- ชื่อ `ใบรับเครื่องเทิร์น_EXP-….pdf` ใช้เฉพาะ paymentMethod เป็น TRADE_IN_CREDIT เหมือนประเภทเอกสาร ไม่อนุมานจาก flow ของรายการเก่า
- ปุ่มใบสำคัญเปิดตัวอย่างในโปรแกรม พร้อมปุ่มดาวน์โหลดที่ระบุชื่อ ใช้ PDF bytes เดียวกันกับตัวอย่าง ไม่เรียก render รอบใหม่ตอนดาวน์โหลด
- คืน Blob URL เมื่อปิดตัวอย่างหรือเปลี่ยนไฟล์ ป้องกันคำขอใบเก่าที่ตอบช้าทับใบล่าสุดหรือเปิดกลับหลังปิดแล้ว
- Browser smoke ตรวจ suggestedFilename และเปรียบเทียบ bytes ที่ดาวน์โหลดจริงทั้ง 1440/390 px มี unit test การเก็บ URL ระหว่างเปิดและคืนเมื่อปิด และ PostgreSQL regression สำหรับชื่อเครดิต/รายการ CASH/TRANSFER เก่า
- ทดลองหน่วงคำขอใบ A แล้วเปิด/ปิด B ก่อนปล่อย A: ตัวอย่างไม่ถูกเปิดกลับและไม่เปลี่ยนไปเป็นใบเก่า

ผลตรวจรอบชื่อไฟล์: local:check ผ่าน 17 checks (Web 1,696 tests, Shared 35 tests), API trade-in 105 tests และ PostgreSQL แยก 32 tests ผ่าน สร้างใบ EXP-20260900008 ใหม่จาก record เดิมและตรวจข้อความ/รูปแบบ PDF แล้ว พร้อมสำเนาชื่อ `ใบสำคัญจ่ายเงิน_EXP-20260900008.pdf` ใน Downloads โดยเก็บไฟล์ UUID ต้นฉบับที่ผู้ใช้แนบไว้

## ออกแบบซ้ำด้วย ui-ux-pro-max

ผู้ใช้ขอใช้สกิลนี้โดยตรง จึงค้นแบบเจาะจงสำหรับเอกสารพิมพ์และเลือกเฉพาะผลที่ตรงบริบท:

- `Swiss editorial document minimal --domain style`: Minimalism & Swiss Style → จัดแนวข้อมูลร่วมกัน ลำดับตัวอักษรชัด พื้นขาวและสีเน้นเดียว
- `typography hierarchy readability --domain ux`: Line Height, Contrast Readability, Font Size Scale → ใช้เนื้อหา 11pt / label 9pt, หัวเอกสาร 24pt, ยอด 30pt; body line-height 1.5
- `IBM Plex Sans Thai --domain google-fonts`: พบตระกูลตรงชื่อ ใช้ TTF ที่ vendored อยู่ใน `modules/other-income/assets/fonts` พร้อม OFL เดิม ไม่เพิ่ม dependency หรือ asset ฟอนต์ซ้ำ
- ผลค้นสี Document Manager ใช้พิจารณาตัวอักษรเข้ม/พื้นขาว คงสีเขียวของ BESTCHOICE แทน accent สีน้ำเงินที่เครื่องมือเสนอ ส่วน palette Financial Dashboard แบบมืดไม่ตรงเอกสารพิมพ์จึงไม่ใช้

สีข้อความ #192d25, label #53635c และยอด #16694f บนพื้นขาวมี contrast 14.55:1, 6.35:1 และ 6.63:1 ตามลำดับ ไม่มีเงา gradient หรือกราฟประดับ คงความหมายเครดิตและชื่อไฟล์ส่งออกจากรอบก่อน

ตรวจ PDF จริงซ้ำ: เงินสด โอน เครดิต และชื่อ/ที่อยู่ยาวพร้อมยอดหลักล้านอยู่ A4 หน้าเดียว; กรณีที่อยู่ 28 บรรทัดต่อสองหน้าโดยสำเนาและลายเซ็นครบ ตรวจด้วยภาพและขอบเขตข้อความแล้ว ชุดทดสอบเดิมยังตรวจข้อมูลและประเภทเอกสาร นอกจากนี้ build API แล้วเรียก compiled renderer จาก cwd อื่นและยืนยันว่าฟอนต์ไทยถูกฝังโดยไม่พึ่ง source directory หรือ network
