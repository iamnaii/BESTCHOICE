# BESTCHOICE — ระบบนัดเข้าร้านหลังผ่านเครดิตเบื้องต้น

วันที่: 11 ตุลาคม 2026 · เขตเวลา Asia/Bangkok

สถานะ: ร่างสเปกสำหรับเจ้าของตรวจทาน — อนุมัติแนวทางในแชทแล้ว ยังไม่ได้อนุมัติเอกสารฉบับนี้หรือเริ่มพัฒนา

## 1. เป้าหมายและขอบเขตที่เจ้าของยืนยัน

ให้ลูกค้าที่ผ่านเครดิตเบื้องต้นนัดเข้าร้านล่วงหน้าได้ ร้านรู้ว่าใครจะมา เวลาใด และใครรับผิดชอบ โดยจำนวนคิวสัมพันธ์กับพนักงานที่พร้อมให้บริการจริง

- พนักงานนัดให้ได้ และลูกค้าจองเองผ่านลิงก์เฉพาะลูกค้าได้ ใช้ตารางคิวเดียวกัน
- กันเวลา 45 นาทีต่อท่าน พนักงานหนึ่งคนรับได้หนึ่งท่านต่อช่วงเวลา
- ผู้จัดการกำหนดพนักงานและช่วงเวลารับนัดของแต่ละคน แยกตามสาขา
- ลูกค้าเลือกสาขา วัน และเวลา ระบบเลือกพนักงานว่างให้ พนักงานหน้าร้านเปลี่ยนผู้รับผิดชอบได้เมื่อคนใหม่ว่าง
- เริ่มจองได้เมื่อผ่านเครดิตเบื้องต้น ไม่ต้องรออนุมัติยอดผ่อน
- รองรับเช็กอิน เริ่มบริการ เสร็จงาน เลื่อนนัด ยกเลิก และไม่มาตามนัด

การนัดหมายเป็นขั้นตอนเข้ารับบริการ ไม่ได้ทำให้เครดิตเต็มผ่าน ไม่อนุมัติสัญญา และไม่รับรองว่ามีเครื่องพร้อมส่งมอบ การทำสัญญายังคงใช้กติกาอนุมัติเดิม

## 2. ค่าเริ่มต้นที่เสนอในสเปกนี้

รายละเอียดต่อไปนี้เป็นข้อเสนอในการออกแบบ ไม่ใช่คำตอบที่เจ้าของระบุไว้แล้ว:

| รายการ | ค่าเริ่มต้นรุ่นแรก |
| --- | --- |
| วันและเวลาเปิดรับ | ใช้ช่วงเวลาที่ผู้จัดการลงไว้ ไม่มีตารางเท่ากับไม่เปิดรับ |
| ระยะเวลาต่อคิว | 45 นาทีคงที่ ไม่มีเวลาพักเผื่อเพิ่มอัตโนมัติ |
| วันเปิดให้จองล่วงหน้า | 14 วันตามปฏิทินไทย รวมวันนี้ |
| ระยะเผื่อก่อนนัด | เลือกเวลาเริ่มที่ห่างจากเวลาปัจจุบันอย่างน้อย 30 นาที |
| นัดที่ยังไม่จบต่อลูกค้า | สูงสุด 1 นัด รวมทุกสาขา |
| อายุลิงก์ | 30 วันนับจากออกลิงก์ เพิกถอนและออกใหม่ได้ |
| เลื่อน/ยกเลิกด้วยตนเอง | ทำได้ก่อนเวลาเริ่มและก่อนเช็กอิน หลังจากนั้นให้ติดต่อสาขา |
| จัดพนักงานอัตโนมัติ | เลือกผู้ว่างที่มีนัดคงเหลือในวันนั้นน้อยที่สุด เสมอกันเรียงรหัสพนักงาน |

เวลาและจำนวนวันอยู่ในนโยบายกลางของโมดูล ไม่ hard-code ซ้ำตามหน้าจอ รุ่นแรกยังไม่เพิ่มหน้าตั้งค่านโยบายทั้งหมด

## 3. สิ่งที่มีอยู่และจุดเชื่อม

- `apps/api/prisma/schema.prisma`: มี `Branch`, `User`, `EmployeeProfile`, `Customer`, `CreditCheck` และ `CreditApproval`; ไม่พบโมเดลตารางรับนัดรายพนักงานในการสำรวจครั้งนี้
- `apps/api/src/modules/credit-check/services/credit-check-crud.service.ts`: ประวัติเครดิตเดิมเลือก FULL ก่อน PRE จึงไม่ใช้ผลจากเมธอดนี้โดยตรงเป็นเงื่อนไขนัดเบื้องต้น
- `credit-check-override.service.ts`: มีการเปลี่ยนผลเครดิตและสรุปสถานะบนลูกค้า
- `room-credit-history.ts`: มี transaction lock ของลูกค้าและผลเครดิตที่นำกลับมาใช้ได้
- `room-credit-access.ts`: มีขอบเขตสิทธิ์อ่านเครดิตที่มาจากห้องแชท ต้องรักษาขอบเขตเดิม
- `UnifiedInboxPage/components/RoomDossier.tsx`: นัดเดิมเป็น `Todo` ของห้อง ใช้แสดงงานติดตามทั่วไป
- `apps/api/src/modules/bookings/` และ `BookingsPage`: เป็นใบจองสินค้าและมัดจำ มีธุรกรรมเงินและล็อกสินค้า

เพิ่มโมดูล `store-appointments` สำหรับตารางเวลาและนัดเข้าร้านโดยเฉพาะ เชื่อมลูกค้า ห้องแชท และพนักงานด้วยรหัสเดิม ใบจองมัดจำและ Todo เดิมคงความหมายเดิม ไม่มีการย้ายข้อมูลเก่าหรือคัดลอกนัดใหม่ลง Todo ให้เกิดสองแหล่งข้อมูล

ทางเลือกที่พิจารณา: ขยาย Todo จะต้องเพิ่มกติกาพนักงานว่างและการจองพร้อมกันให้ระบบงานทั่วไป ส่วนขยาย Booking จะผูกนัดเข้ากับสถานะเงินมัดจำที่ไม่จำเป็น จึงเลือกโมดูลนัดเฉพาะที่แสดงร่วมในแชทได้

## 4. หน้าจอและการใช้งาน

### ผู้จัดการ: ตารางรับนัด

อยู่ใน BESTCHOICE SHOP เมนู “นัดเข้าร้าน” แท็บ “ตารางพนักงาน” เลือกสาขาและวัน แล้วเพิ่มช่วงเวลาให้พนักงานแต่ละคน เช่น 10:00–12:15 และ 13:00–17:30 ช่วงที่ไม่ระบุถือว่ารับนัดไม่ได้

เลือกเฉพาะผู้ใช้ที่ active ไม่ถูกลบ และสังกัดสาขานั้น ใช้ข้อมูลชื่อและรหัสผู้ใช้ ไม่ดึงข้อมูลเงินเดือนหรือข้อมูล HR ส่วนตัว หนึ่งคนมีหลายช่วงเวลาในวันเดียวได้ แต่ช่วงเวลาห้ามซ้อนกัน

มีคำสั่งคัดลอกตารางของวันหนึ่งไปวันอื่น โดยตรวจทุกแถวก่อนบันทึกทั้งหมด ไม่มี recurring schedule หรือระบบจัดกะอัตโนมัติในรุ่นแรก

### พนักงาน: สร้างนัด

จากหน้าลูกค้าหรือห้องแชทที่ผูกลูกค้าแล้ว กด “นัดเข้าร้าน” ระบบแสดงสิทธิ์นัดและนัดที่ยังเปิดอยู่ ถ้ามีนัดแล้วให้เปิดนัดเดิมเพื่อจัดการ แทนการสร้างเพิ่ม

เลือกสาขาที่ตนมีสิทธิ์ทำงาน วัน และเวลา ยืนยันแล้วได้รับเลขนัด พร้อมข้อมูลวัน เวลา สาขา และผู้รับผิดชอบ หรือกด “สร้างลิงก์ให้ลูกค้าเลือกเวลา” แล้วคัดลอกลิงก์ไปส่งเอง

ห้องที่ยังไม่ผูกลูกค้าต้องผูกลูกค้าก่อน สร้างนัดจากหมายเลขห้องอย่างเดียวไม่ได้

### ลูกค้า: จองผ่านลิงก์

หน้าเว็บรองรับมือถือ ไม่บังคับสมัครบัญชี: เลือกสาขา → วันและเวลา → ตรวจรายละเอียด → ยืนยัน แสดงเฉพาะสาขา active ในขอบเขตลิงก์และมีตารางรับนัด ไม่แสดงรายชื่อพนักงานหรือรายชื่อลูกค้าคนอื่น

หลังจอง แสดงเลขนัด สาขา ที่อยู่/เบอร์โทรที่มีในระบบ วันเวลา และปุ่มเลื่อน/ยกเลิก พร้อมข้อความ “กรุณามาตามเวลานัด การอนุมัติยอดผ่อนและเอกสารจะดำเนินการตามขั้นตอนของร้าน” ไม่ใช้ข้อความรับรองว่าอนุมัติสัญญาแล้ว

### หน้าร้าน: คิวประจำวัน

ตารางรายวันแบ่งตามพนักงาน มีรายการที่ใช้งานสะดวกบนมือถือ กรองสาขา วันที่ พนักงาน และสถานะได้ แสดงลูกค้า เวลา ผู้รับผิดชอบ และสัญญาณเตือนผลเครดิตเปลี่ยน

ปุ่มตามสถานะ: เช็กอิน → เริ่มบริการ → เสร็จงาน; ยกเลิกและไม่มาตามนัดเป็นทางออกอื่น มีประวัติผู้เปลี่ยนและเวลา พนักงานเปลี่ยนผู้รับผิดชอบหรือเลื่อนเวลาได้เฉพาะก่อนเริ่มบริการและต้องตรวจตารางใหม่เสมอ

## 5. เงื่อนไขเครดิตสำหรับนัด

สร้างตัวประเมินสิทธิ์นัดเฉพาะ ใช้ผลจริงของ `CreditCheck` ที่ไม่ถูกลบ ไม่เชื่อ badge บนหน้าเว็บหรือ `Customer.creditCheckStatus` เพียงอย่างเดียว

1. อ่าน PRE ล่าสุดและ FULL ล่าสุดของลูกค้า เรียง `createdAt DESC, id DESC` ให้คงที่
2. FULL ล่าสุดเป็น APPROVED: นัดได้โดยไม่ต้องมี `CreditApproval` หรือยอดผ่อน เพราะเป็นเพียงการนัดเข้าร้าน
3. FULL ล่าสุดเป็น REJECTED: นัดใหม่ไม่ได้ แม้มี PRE เก่าที่ผ่าน ต้องกลับไปทบทวนผลเครดิตตามขั้นตอนเดิม
4. FULL ไม่มีหรือยัง PENDING/MANUAL_REVIEW: นัดได้เมื่อ PRE ล่าสุดเป็น APPROVED; การรอตรวจเต็มไม่ล้างสิทธิ์ที่ผ่านเบื้องต้น
5. ไม่เข้าเงื่อนไขผ่านด้านบน: ยังนัดไม่ได้ แสดงเหตุผลสั้นที่เหมาะกับผู้ดู

ตรวจสิทธิ์ตอนออกลิงก์ อ่านเวลาว่าง สร้างนัด และเลื่อนนัด การยกเลิกต้องยังทำได้แม้เครดิตเปลี่ยน ผลเครดิตที่เปลี่ยนภายหลังไม่ลบนัดเดิมอัตโนมัติ: แสดงให้เจ้าหน้าที่ทบทวน และลูกค้าเห็นเพียงให้ติดต่อสาขา นัดเดิมยังกันเวลาจนพนักงานยกเลิกหรือจัดการ

บันทึก `creditCheckId` และชนิดผลที่ใช้ตอนสร้าง/เลื่อนเพื่อสอบย้อนกลับ ไม่คัดลอก statement หรือข้อมูลวิเคราะห์ลงนัด ผู้ใช้ที่อ่านแหล่งเครดิตไม่ได้จะไม่ได้รับรายละเอียดเครดิตจาก endpoint นัด

## 6. การคำนวณเวลาและป้องกันจองซ้อน

- เก็บเวลาเป็น UTC แสดงและเลือกวันด้วย Asia/Bangkok ช่วงเวลาทั้งหมดเป็น `[start, end)` จึงนัดต่อกันที่เวลาเดียวกับจบคิวก่อนหน้าได้
- แต่ละช่วงรับนัดสร้างเวลาเริ่มทุก 45 นาทีจากต้นช่วง เช่น 10:00–12:00 เปิด 10:00 และ 10:45; ไม่เปิด 11:30 เพราะเวลาที่เหลือไม่ครบ
- ช่วงพักแบ่งเป็นคนละช่วงรับนัด ห้ามนำเวลาว่างสองฝั่งช่วงพักมาต่อกัน
- รวมเวลาเริ่มที่ซ้ำกันจากพนักงานแต่ละคนเป็นตัวเลือกเดียว จำนวนว่างคือจำนวนคนที่ให้บริการช่วงนั้นได้จริง
- จองได้เมื่อครบทั้ง 45 นาทีอยู่ในช่วงรับนัด และไม่มีนัดเปิดของพนักงานทับช่วงนั้น ใช้เงื่อนไข `existing.start < requested.end AND existing.end > requested.start` ไม่ตรวจแค่เวลาเริ่มตรงกัน
- นัดสถานะ BOOKED, CHECKED_IN และ IN_SERVICE ยังกันเวลา COMPLETED, CANCELED และ NO_SHOW ไม่กันเวลา; ไม่เปิดเวลาที่ผ่านไปแล้วกลับให้จอง
- จบก่อนเวลาจะไม่เปิดคิวสั้นแทรกนอกกริดเดิม หากทำงานเกิน 45 นาที ให้แสดงว่าเกินเวลาและนัดถัดไปต้องได้รับการจัดการโดยหน้าร้าน ไม่เลื่อนนัดลูกค้าอัตโนมัติ
- การเปลี่ยนตาราง ลบช่วงรับนัด ปิดผู้ใช้ หรือย้ายสาขาพนักงานต้องตรวจนัดที่ยังเปิด ถ้าทำให้นัดไม่มีคนรองรับ ให้ปฏิเสธพร้อมแสดงนัดที่ต้องย้าย/ยกเลิกก่อน

ทุกการสร้าง/เลื่อน/ย้ายพนักงาน/ยกเลิกและแก้ตารางใช้ transaction บน PostgreSQL พร้อม lock ร่วมกัน ไม่พึ่ง UI หรือ cache เพื่อกันซ้อน:

1. ล็อกลูกค้าและผลเครดิตที่เกี่ยวข้องตามลำดับ lock ของระบบเครดิตเดิม แล้วอ่านสิทธิ์ซ้ำ
2. ล็อกนัดเดิมเมื่อเป็นการแก้ และล็อกแถว User ของพนักงานที่เกี่ยวข้องเรียง ID คงที่ ก่อนอ่านตารางและนัดซ้ำ; การจองแบบจัดคนให้อัตโนมัติต้องล็อกผู้สมัครที่พิจารณาเรียงลำดับเดียวกัน
3. ผู้แก้ตารางล็อก User ก่อนแก้ ไม่ย้อนมาล็อกลูกค้า จึงไม่สร้างวงจรรอ lock กันกับการจอง
4. ตรวจทุก invariant และเขียนนัดพร้อมประวัติใน transaction เดียว การย้ายล้มเหลวต้องคงนัดเดิมครบทั้งเวลาและผู้รับผิดชอบ
5. ใช้ partial unique index ให้ลูกค้ามีนัดเปิดไม่เกินหนึ่งนัด และ idempotency key สำหรับ create/reschedule/cancel เพื่อรองรับกดซ้ำหรือ retry

เส้นทางแก้ผู้ใช้/ย้ายสาขาต้องใช้ User lock และตรวจนัดร่วมกับโมดูลนี้ด้วย การกันซ้อนรายคนต้องทดสอบกับฐานข้อมูลจริงแบบ concurrent transactions ข้าม API instance

เมื่อช่วงเวลาเต็มระหว่างกดยืนยัน ส่ง 409 พร้อมข้อความ “ช่วงเวลานี้เต็มแล้ว กรุณาเลือกเวลาใหม่” แล้วโหลดเวลาว่างอีกครั้ง หาก transaction ขัดแย้งให้ retry แบบจำกัดจำนวน ไม่วนไม่สิ้นสุด

## 7. สถานะและการแก้ไข

| สถานะ | ไปต่อได้ | ผู้ดำเนินการ |
| --- | --- | --- |
| BOOKED | CHECKED_IN, CANCELED, NO_SHOW | พนักงาน; ลูกค้ายกเลิกได้ก่อนเริ่ม |
| CHECKED_IN | IN_SERVICE, CANCELED | พนักงาน |
| IN_SERVICE | COMPLETED, CANCELED | พนักงาน; ยกเลิกต้องมีเหตุผล |
| COMPLETED / CANCELED / NO_SHOW | สิ้นสุด | สร้างนัดใหม่เมื่อเข้าเงื่อนไข |

NO_SHOW ทำได้เมื่อถึงเวลาเริ่มแล้วและยังไม่เช็กอิน ไม่เปลี่ยนเป็นไม่มาตามนัดอัตโนมัติ เลื่อนนัดไม่ใช่สถานะใหม่: คง BOOKED หรือ CHECKED_IN ตามเดิมและเก็บประวัติเวลาเก่า/ใหม่ การเลื่อนไปวันอื่นหลังเช็กอินต้องคืนสถานะ BOOKED และล้างเวลาเช็กอินปัจจุบัน โดยเก็บหลักฐานเช็กอินเดิมใน event

ตรวจ version ของนัดทุก mutation หากเจ้าหน้าที่สองคนแก้พร้อมกันให้แจ้งโหลดข้อมูลใหม่ ไม่เขียนทับเงียบ ๆ

## 8. โครงสร้างข้อมูลและขอบเขตโมดูล

เพิ่มโมเดลแบบ additive ตามมาตรฐาน UUID, timestamps และ soft delete ของ repo:

- `StaffAppointmentWindow`: branchId, staffUserId, startsAt, endsAt, createdById และ version; index สำหรับสาขา/วันและพนักงาน/เวลา
- `StoreAppointment`: reference, customerId, branchId, staffUserId, windowId, sourceRoomId แบบ optional, creditCheckId, creditCheckTypeAtBooking, startsAt, endsAt, status, source STAFF/CUSTOMER_LINK, createdById แบบ optional, checkedInAt, serviceStartedAt, completedAt, canceledAt, noShowAt, reason และ version
- `StoreAppointmentLink`: customerId, tokenHash แบบ unique, allowedBranchIds ที่ตรวจสิทธิ์ตอนออกลิงก์, expiresAt, revokedAt, issuedById; ลิงก์ลูกค้าไม่รับ customerId จาก request body
- `StoreAppointmentEvent`: นัด, ชนิดเหตุการณ์, ผู้กระทำ STAFF/CUSTOMER_LINK, staffUserId/linkId ตามกรณี, old/new ค่าเวลา/สาขา/ผู้รับผิดชอบ/สถานะ, createdAt เป็นประวัติ append-only
- `AppointmentRequest`: actor scope, key, requestHash และผลลัพธ์อ้างอิงนัด/เวอร์ชัน เพื่อรับ retry อย่างคงที่ ไม่เก็บ token ดิบในผลลัพธ์; key เดิมกับ payload ต่างกันส่ง 409

ใช้ FK แบบ Restrict กับข้อมูลอ้างอิงสำคัญ ประวัติไม่มีการแก้/ลบผ่าน API ปกติ ระบุข้อยกเว้น timestamps ของ immutable event ตามกฎฐานข้อมูล สร้าง check constraint ให้ end > start และนัดยาว 45 นาที; partial unique index ของนัดเปิดต้องมี migration และ integration test กำกับ

แยกบริการ: eligibility, availability, schedule, appointment lifecycle, public link และ query/read model ทั้ง staff และ public controller เรียกกติกาชุดเดียวกัน

API กลุ่ม staff: ตารางรับนัด, eligibility, availability, list/detail, create, reschedule, reassign, status transitions และ issue/revoke link. API กลุ่ม public: อ่านบริบทลิงก์/นัดของตน, availability, create, reschedule, cancel. Public ไม่มี endpoint ที่ค้นลูกค้าอื่นหรือเปลี่ยนสถานะหน้าร้าน

## 9. สิทธิ์และลิงก์ลูกค้า

- OWNER จัดการสาขา SHOP ที่มี company grant; BRANCH_MANAGER จัดตารางและนัดในสาขาตน; SALES ดูและจัดการนัดในสาขาที่ได้รับสิทธิ์ แต่แก้ตารางพนักงานไม่ได้
- ทุก endpoint staff ใช้ auth/roles/company/branch scope เดิม และตรวจขอบเขต entity ใน service แม้ route มีแค่ ID
- ลิงก์ใช้ token สุ่ม 256-bit เก็บ SHA-256 hash เท่านั้น token ดิบคืนครั้งเดียวเมื่อสร้าง ไม่ใส่ใน audit, log, analytics หรือ Sentry
- หน้า public ใช้ URL fragment รับ token และส่ง token ใน header เฉพาะคำขอ API; ไม่เก็บใน localStorage/sessionStorage ไม่โหลด analytics ของบุคคลที่สาม ตั้ง no-referrer/noindex/no-store ตามความเหมาะสม
- Public controller แยกจาก staff ใช้ token guard, validation, rate limit และ response allow-list เปิดข้อยกเว้น CSRF เฉพาะ endpoint ที่ใช้ capability token โดยไม่มี cookie authentication ตาม pattern public share เดิม ไม่ปิด global guard
- ลิงก์เพิกถอน/หมดอายุ/ไม่ถูกต้องให้ข้อความทั่วไปเดียวกัน แสดงเบอร์ติดต่อสาขาเมื่อทราบอย่างปลอดภัย มีหน้า retry เมื่อเครือข่ายขัดข้อง
- ลิงก์ออกโดยผู้จัดการ/พนักงานถูกจำกัดตามสาขาที่ผู้ออกมีสิทธิ์ ห้ามรับ allowedBranchIds จาก client โดยไม่ตรวจ ปิดสาขาหรือถอนสิทธิ์ผู้ออกแล้วต้องตรวจขอบเขตลิงก์ใหม่ก่อน mutation
- การออกลิงก์ใหม่เพิกถอนลิงก์เดิมของลูกค้าใน transaction เดียว ไม่ยกเลิกนัดเดิม ผู้ใช้ลิงก์ใหม่เห็นนัดเดิมของตนได้
- ข้อมูลลูกค้าใน public response มีเท่าที่จำเป็นสำหรับนัด ชื่อปกปิดบางส่วน ไม่มีเลขบัตร statement คะแนนเครดิต หรือชื่อพนักงานทั้งสาขา

## 10. การเชื่อมหน้าเดิมและข้อจำกัดรุ่นแรก

เพิ่มเมนูใน SHOP ตาม navigation rule เดิม เชื่อมจากหน้าลูกค้าและ RoomDossier แสดงนัดจากโมดูลกลาง ไม่เขียนนัดซ้ำเป็น Todo การเลือกห้องต้องตรวจสิทธิ์เข้าห้องและความสัมพันธ์กับลูกค้าก่อนเสมอ

ยังไม่มีการส่ง LINE/SMS/email อัตโนมัติ รุ่นแรกสร้างและคัดลอกลิงก์ รวมทั้งแสดงใบยืนยันนัดในเว็บ พนักงานเป็นผู้ส่งลิงก์ ไม่มีการส่งข้อความจริงระหว่างพัฒนาและทดสอบ

ไม่รวมระบบลงเวลางาน HR, การลา, เงินเดือน, walk-in queue, waitlist, นัดกลุ่ม, มัดจำ, สำรองเครื่อง, ปรับเงื่อนไขทำสัญญา และการแจ้งเตือนอัตโนมัติ ผู้จัดการสะท้อนวันลา/พักโดยแก้ช่วงรับนัดและจัดการนัดที่ได้รับผลกระทบ

## 11. เกณฑ์ตรวจรับ

1. PRE ผ่านและ FULL ยังรอพิจารณาจองได้; ไม่ผ่านหรือไม่มีผลที่ให้สิทธิ์จองไม่ได้; FULL ถูกปฏิเสธไม่ใช้ PRE เก่าข้ามเงื่อนไข
2. พนักงานว่าง 3 คนในเวลาเดียวกันรับได้ 3 นัด คำขอที่ 4 ไม่สำเร็จแม้ยิงพร้อมกันจาก staff และ public
3. นัดต่างเวลาเริ่มที่ทับกันบนพนักงานคนเดียวกันถูกปฏิเสธ นัดต่อกันพอดีรับได้
4. เวลาใกล้พัก/ปิดที่เหลือไม่ครบ 45 นาทีไม่แสดง วันไม่มีตารางไม่มีเวลาจอง วันที่และเวลาตรงกับกรุงเทพฯ ใกล้เที่ยงคืนด้วย
5. กดซ้ำหรือ retry ไม่เกิดสองนัด ลูกค้าคนเดียวจองพร้อมกันต่างสาขายังมีนัดเปิดได้เพียงหนึ่ง
6. เลื่อนนัดสำเร็จแล้วเวลาเก่าคืน เลื่อนล้มเหลวคงนัดเดิม; เปลี่ยนพนักงานและแก้ตารางพร้อมกับจองไม่ทำให้เกิดนัดเกิน
7. การลา/ปิดผู้ใช้/ย้ายสาขาที่กระทบนัดถูกแจ้งและป้องกันจนย้ายหรือยกเลิกนัดแล้ว
8. สถานะเปลี่ยนได้เฉพาะทางที่กำหนด มีประวัติ actor และเวลา; public เปลี่ยนสถานะหน้าร้านไม่ได้
9. หมดอายุ/เพิกถอนลิงก์ แก้ customerId/branchId หรืออ่านนัดคนอื่นไม่สำเร็จ ไม่มีข้อมูลส่วนตัวหรือ token ใน log
10. นัดถูกแสดงจากแหล่งเดียวกันในตาราง หน้าลูกค้า และแชท; Todo และใบจองมัดจำเดิมยังทำงานตามเดิม
11. เครดิตเปลี่ยนเป็นไม่ผ่านหลังจอง: นัดเดิมยังอยู่ มีคำเตือนให้พนักงานทบทวน ลูกค้ายกเลิกได้แต่สร้าง/เลื่อนตามสิทธิ์ใหม่ไม่ได้
12. ทดสอบ flow จริงใน local ทั้งหน้าจอ desktop/mobile และ PostgreSQL แยกสำหรับทดสอบ พร้อม API backend ที่สร้างใหม่หลังเปลี่ยน schema

ชุดทดสอบ: unit สำหรับ eligibility/เวลา/state machine; database integration สำหรับ race, rollback, uniqueness และ locks; API authorization/token/idempotency; browser flow ผู้จัดการลงตาราง → พนักงานจอง/ออกลิงก์ → ลูกค้าจอง/เลื่อน/ยกเลิก → หน้าร้านเช็กอิน/ปิดงาน

หลังพัฒนารัน `npm run local:check` และเพิ่มการทดสอบนัดจริงบน backend ของ checkout นี้ เพราะ managed preview เดิมไม่ได้ยืนยันระบบนัดใหม่ ตรวจ migration กับฐานข้อมูลทดสอบเท่านั้น และคง local server ที่ตรวจแล้วไว้ให้เจ้าของทดลอง

## 12. สถานะส่งมอบเอกสาร

ฉบับนี้เป็นสเปกที่ตรวจความสอดคล้องภายในแล้ว ยังไม่มีการแก้ product code, schema หรือฐานข้อมูล และยังไม่มีผลทดสอบระบบนัด หลังเจ้าของตรวจเอกสารนี้ ขั้นถัดไปคือเขียนแผนพัฒนาเป็นงานย่อยพร้อมลำดับ migration/API/UI/integration และตรวจรับแผนก่อนเริ่มลงมือ
