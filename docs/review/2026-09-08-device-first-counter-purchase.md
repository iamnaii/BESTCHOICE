# รับซื้อหน้าร้าน: ตรวจเครื่องและราคาก่อนข้อมูลผู้ขาย

ปรับปุ่ม “รับซื้อเครื่อง” จากฟอร์มที่เริ่มด้วยผู้ขาย เป็น 4 ขั้นตามลำดับงานหน้าร้าน:

1. เลือก iPhone และความจุจากรุ่นที่มีราคารับซื้อ พร้อมสี IMEI / Serial Number และเหตุผลกรณีหมายเลขขาด แสดงราคาสูงสุดก่อนหักสภาพ
2. ตรวจสภาพด้วยแบบตรวจชุดเดียวกับหน้าเว็บและหน้าประเมินรายการ คำนวณราคาจากเซิร์ฟเวอร์อัตโนมัติ แสดงค่าหักและราคาเงินสดก่อนกรอกผู้ขาย
3. ยืนยันสาขาและกรอกผู้ขาย โดยมีรุ่น/ราคาที่ตรวจแล้วแสดงประกอบ
4. ตรวจบัตร ยอมรับคำรับรอง เลือกเงินสด/โอน และลงลายเซ็นก่อนรับซื้อและออกใบสำคัญ

ขั้นดูราคายังไม่สร้างผู้ขาย รายการรับซื้อ สต็อก หรือรายการจ่ายเงิน ระบบเขียนเมื่อยืนยันขั้นสุดท้ายเท่านั้น และใช้การกู้รายการ/ป้องกันการส่งซ้ำเดิมเมื่อคำตอบจากเซิร์ฟเวอร์ขาดหาย

## การตรวจราคาและหลักฐาน

- `GET /trade-ins/quick-buy/catalog` และ `/quick-buy/questions?model&storage` อ่านข้อมูลรุ่นและแบบตรวจ
- `POST /trade-ins/quick-buy/preview` รับข้อมูลเครื่อง/คำตอบโดยไม่ต้องมีผู้ขาย ส่งราคาเงินสด เกรด รายละเอียดค่าหัก และ previewToken
- `POST /trade-ins/quick-buy` คำนวณซ้ำก่อนเริ่มเขียนข้อมูล ไม่ยอมรับราคา/เกรด/token ที่ไม่ตรงผลประเมิน และเก็บคำตอบ/ราคา/ผู้ตรวจในรายการรับซื้อ
- ข้อมูลเครื่องหรือคำตอบที่เปลี่ยนจะไม่ใช้ราคาจากคำตอบเก่า เปลี่ยนรุ่น ความจุ IMEI หรือ Serial Number ต้องตรวจใหม่
- ย้อนกลับเก็บข้อมูลที่กรอกไว้ แต่ล้างการยืนยันและลายเซ็น เมื่อต้นทางราคาหรือเงื่อนไขเปลี่ยนระหว่างกรอก จะกลับไปดูราคาล่าสุดและต้องเซ็นใหม่
- ผลอ่านบัตร/ผู้ติดต่อที่มาช้าหลังออกจากขั้นผู้ขายไม่สามารถเปลี่ยนข้อมูลที่กำลังลงนามได้
- API manual เดิมยังรองรับเพื่อความเข้ากันได้ ฟอร์มใหม่ส่งผลตรวจและใช้ราคาที่เซิร์ฟเวอร์ยืนยัน

ใช้ `InspectionQuestions` ร่วมกับหน้าประเมินเดิม แยกการตรวจข้อมูลเครื่องออกจากข้อมูลผู้ขายใน shared evidence helper โดยยังตรวจทั้งสองส่วนก่อนยืนยันรับเครื่อง ไม่เพิ่ม migration

## การตรวจสอบ

ชุดทดสอบครอบคลุมลำดับขั้น การดูราคาก่อนผู้ขาย การย้อนกลับ คำตอบและราคาที่มาช้า การกู้รายการ การเปลี่ยนราคาก่อนบันทึก การบังคับเซ็นใหม่ และผลอ่านบัตรล่าช้า

`tools/check-local-trade-in.mjs` เดิน 4 ขั้นกับ API และฐานข้อมูลจำลองจริงทั้ง desktop/mobile ตรวจผลราคา คำตอบที่บันทึก ใบสำคัญ การตั้งราคาขาย ถ่ายรูป และรับเข้าสต็อก ผลตรวจรวมอยู่ที่ `.tmp/local-preview/check.json`

งานนี้แก้และทดสอบ local ยังไม่ push/merge/deploy

ผลตรวจ 8 กันยายน 2569 เวลา 22:01 น.:

## ปรับหน้าตาตาม UI UX Pro Max

หลังผู้ใช้ยืนยันข้อมูลและลำดับงาน ปรับเฉพาะการแสดงผลใน `QuickBuyModal` และ `InspectionQuestions`:

- ใช้หัวหน้าต่างและแถบขั้นตอนรูปแบบเดียวกัน แยกขั้นปัจจุบัน/ตรวจเสร็จ/ยังไม่ถึงด้วยเส้น ตัวเลข และเครื่องหมายถูก
- จัดข้อมูลเครื่องกับราคาสูงสุดเป็นสองคอลัมน์บนคอม และเรียงลงบนมือถือ; จัดข้อมูลผู้ขายและสรุปก่อนจ่ายเงินให้เป็นหมวด
- ช่องกรอกและปุ่มสูงอย่างน้อย 44px ใช้ช่องว่างและตัวอักษรชุดเดียวกัน; ปุ่มบันทึกบนมือถือขึ้นบรรทัดได้
- ใช้ปุ่มหลักสี emerald ที่ปรับความเข้มตามธีม ปุ่มรองแบบเส้นขอบ และพื้นหลังหน้าต่างสีดำโปร่งแทนการอิงสีข้อความที่กลายเป็นสีขาวใน dark mode
- แบบตรวจแบ่งกรอบชัดเจน แต่คง fieldset/legend และชื่อที่ใช้กับ accessibility; เก็บค่า คำตอบ เงื่อนไข และการคำนวณเดิม
- พื้นผิวแผ่นลายเซ็นเป็นสีอ่อนเพื่อให้เห็นหมึกดำทั้งสองธีม โดยไม่แก้ภาพลายเซ็นที่ส่งให้ API

แนวทางจาก skill: `form visual hierarchy spacing --domain ux` (touch spacing, text reflow) และ `dialog form consistent spacing --stack shadcn` (Dialog สำหรับฟอร์ม) ใช้เฉพาะคำแนะนำที่ตรงกับ component ที่มีอยู่

## เลือกสีจากข้อมูลรุ่นในระบบ

ช่อง “สีเครื่อง” ใช้ dropdown จาก `getModels(brand)` ใน `apps/web/src/data/productCatalog.ts` ซึ่งเป็นข้อมูลชุดเดียวกับหน้าสร้างสินค้าและ PO ค้นหาชื่อรุ่นโดยไม่แยกตัวพิมพ์ใหญ่/เล็กเพื่อรองรับ `Mini` ในแคตตาล็อกรับซื้อกับ `mini` ในคลัง โดยคงชื่อรุ่นและความจุที่ส่งให้ API ราคาเดิม

เปลี่ยนรุ่นแล้วล้างสีเดิม รุ่นที่ยังไม่มีสีในแคตตาล็อก (ปัจจุบัน iPhone 17e) แสดง “ยังไม่มีข้อมูลสีรุ่นนี้ในระบบ” และไม่เปิดให้พิมพ์สีอิสระ ไม่เพิ่มข้อมูลสีชุดใหม่หรือเปลี่ยนการคำนวณราคา

ตรวจใน Chrome: iPhone 17 Pro Max แสดง Silver / Cosmic Orange / Deep Blue; เลือก Cosmic Orange แล้วเปลี่ยนเป็น iPhone 12 Mini แสดงสีของ mini และล้างสีเดิม ถูกต้อง หลังแก้ครบ `npm run local:check` ผ่าน 21 หมวด ณ 22:21 น. source fingerprint `7425e17ae8b38b4b89c55e30936f445e6486d48ea66d8b52969971fddb37cf05` และ local running/current

## ปรับ dropdown ในฟอร์มรับซื้อ

ใช้ `PurchaseSelect` ครอบ Select ของระบบสำหรับรุ่น ความจุ สี และสาขา ให้ช่องเลือกและรายการที่เปิดใช้พื้นผิว สี ขอบ และระยะห่างชุดเดียวกันทั้ง light/dark รายการที่เลือกมีเครื่องหมายถูก เมนูกว้างเท่าช่องเลือกและปรับความสูงตามพื้นที่จอ แต่ละตัวเลือกสูงอย่างน้อย 44px

คงข้อมูลและการคำนวณเดิมทั้งหมด สีล้างได้ด้วย “ยังไม่ระบุสี” การเปลี่ยนรุ่นยังล้างความจุและสีเดิม รองรับคีย์บอร์ดและ Escape โดยไม่ปิดฟอร์มรับซื้อ ใช้ component เดิมของระบบ ไม่เพิ่ม dependency หรือเปลี่ยน dropdown ทั้งโปรแกรม

ผลตรวจเฉพาะส่วน: TradeInFlow 20 tests ผ่านโดยใช้ Select จริง พร้อม lint; ตรวจเมนูที่เปิดทั้งสามช่องบนจอ 1440×1000 และ 390×844 ใน light/dark รวม 12 ภาพ ไม่พบเมนูล้นจอ ตรวจเลือกด้วยคีย์บอร์ด ปิดด้วย Escape ล้างสี และเปลี่ยนรุ่นผ่าน (`.tmp/purchase-select-review/report.json`) ปรับ browser flow ของ `local:check` ให้เลือกผ่าน dropdown ใหม่ด้วย
