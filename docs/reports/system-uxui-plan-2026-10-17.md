# แผนตรวจ UX/UI ทั้งโปรแกรม BESTCHOICE — 17 ตุลาคม 2026

สถานะ: **เริ่มดำเนินการแล้ว — ยังไม่ครบทุกปุ่ม/ทุกสถานะ**

ผลและบัญชีตรวจรอบใหม่อยู่ที่ [รายงานดำเนินงาน](system-uxui-execution-2026-10-17.md).
บัญชีด้านล่างเป็น baseline ตอนวางแผน; ใช้บัญชี execution ในรายงานใหม่ติดตามผลล่าสุด

## 1. ขอบเขตที่นับได้จากโค้ดปัจจุบัน

ตรวจเทียบ `apps/web/src/App.tsx`, `apps/web-shop/src/App.tsx`,
`apps/web/src/config/settings-registry.tsx` และเมนูงานปัจจุบัน กับบัญชีตรวจเดิม
พบ 216 route declarations ในแอปหลังบ้าน/หน้าสาธารณะ/LIFF, 53 รายการตั้งค่า
และ 38 route declarations ในเว็บลูกค้า รวม **307 รายการ** มี 299 คู่ app/path
ไม่ซ้ำ อีก 8 รายการเป็นทางเข้าจากตั้งค่าไปหน้าที่มีอยู่แล้ว ต้องตรวจลิงก์ทางเข้า
และอ้างผลหน้าปลายทาง ไม่บวกเป็นหน้าที่ตรวจซ้ำสำเร็จอีกหน้า

ตัวเลขนี้รวม redirect, aliases, หน้า placeholder, settings category และ route
ที่มี parameter จึงไม่เรียกว่า “307 หน้าธุรกรรม” จำนวนแท็บ/หน้าต่างย่อย/ปุ่ม
จะเพิ่มจากการสำรวจสถานะจริงในขั้นแรก และยังไม่ระบุจำนวนขึ้นมาเอง

รายการหลักฐาน:

- [บัญชีตรวจครบ 307 รายการ — CSV](system-uxui-plan-2026-10-17/page-checklist.csv)
- [บัญชีตรวจ — JSON](system-uxui-plan-2026-10-17/page-checklist.json)
- [แบบบันทึกปุ่มและหน้าต่างย่อย](system-uxui-plan-2026-10-17/action-checklist-template.csv)
- [รายการ native select ที่ต้องพิจารณา](system-uxui-plan-2026-10-17/native-select-review.csv)

ทุกแถวเริ่มที่ NOT_RECHECKED ไม่ยกผลตรวจเดิมมาเป็นผลผ่านรอบใหม่ หน้า PO ระบุ
เพิ่มเติมว่าเฉพาะตัวกรองและ chip ผ่านรอบวันที่ 17 ตุลาคมแล้ว ส่วนแท็บและฟอร์ม
อื่นยังต้องเข้าบัญชีตรวจ การค้นโค้ดพบ native select 239 จุดใน 137 ไฟล์ เป็น
รายการคัดกรองความเสี่ยง ไม่ใช่ข้อผิดพลาดยืนยัน และอาจรวมไฟล์ที่ไม่ได้ใช้แล้ว

## 2. เหตุผลที่ต้องเปลี่ยนวิธีตรวจ

รายงานวันที่ 16 ตุลาคมมีหลักฐาน route/state และฟอร์มหลายชุด แต่การเปิดหน้าได้
ไม่มี horizontal overflow และใช้ font ถูก ไม่ได้พิสูจน์ว่าแนวข้อความ/ลูกศร
สวยสม่ำเสมอ หรือเปิดครบทุกหน้าต่างย่อยแล้ว ตัวอย่างล่าสุดคือ PO ยังมี native
arrow ชิดขอบและสัดส่วนตัวกรองต่างกัน รวมถึง chip ที่ล้นเมื่อข้อความยาวติดกัน

รอบนี้แยกหลักฐานสามส่วน: **หน้าตา**, **การกดใช้งาน**, **ขอบเขตข้อมูล/สิทธิ์**
ต้องระบุผลทั้งสามส่วน ไม่ใช้จำนวน screenshot หรือจำนวน tests แทนความครบ
ของงาน และไม่ถือว่าหน้า error/ไม่มีข้อมูลผ่านแล้วเท่ากับหน้ามีข้อมูลผ่านด้วย

## 4. วิธีตรวจหนึ่งหน้าให้ครบ

1. **ทำบัญชีส่วนที่เปิดได้จริง**: ใช้ข้อมูลจำลองที่มีรายการและสถานะครบ เปิดทุก
   tab, accordion, dropdown, context menu, row action, drawer/modal และ wizard
   step ลงทะเบียนส่วนซ้อนต่อจากส่วนแม่ รวมทางเข้าจาก sidebar, deep link และ
   query/hash ที่ต่างกัน ปุ่มที่ถูกซ่อนตามสิทธิ์/สถานะมีกรณีแยก
2. **ดูภาพและวัด**: เก็บ screenshot แล้วตรวจด้วยสายตาเทียบคู่กับค่า geometry
   ของ field/label/icon/action ทั้งแถว ต้องเห็นตอนปิดและเปิดรายการ ตอน focus
   ตอนเลือกค่า และเมื่อ error/helper text ปรากฏ ไม่จบแค่ภาพแรกหลังเข้า route
3. **กดให้เกิดผล**: กรอก/ล้าง/เลือก/ค้นหา/เรียง/เปลี่ยนหน้า/กรอง/ล้างตัวกรอง,
   เปิด–ปิดและยกเลิก, ถัดไป–ย้อนกลับ, เพิ่ม–ลบแถว, preview/download และปุ่ม
   บันทึก/ยืนยันในฐานทดสอบ ตรวจผลหน้าจอและผล API/ข้อมูลที่เกี่ยวข้องหลังคลิก
   `trial: true` ใช้พิสูจน์ว่าเอื้อมถึงได้เท่านั้น ไม่นับว่าทดสอบพฤติกรรมผ่าน
4. **ตรวจสถานะผิดปกติ**: ค่าว่าง/ไม่ถูกต้อง, loading/disabled, สำเร็จ, ล้มเหลว
   แล้ว retry, timeout, ไม่มีผลค้นหา, token หมดอายุ, สิทธิ์ไม่พอ, ข้อมูลที่
   เปลี่ยนระหว่างเปิดหน้า และกลับจาก modal โดยข้อมูลร่างยังอยู่ตามพฤติกรรมที่ตั้งใจ
5. **ตรวจคีย์บอร์ดและมือถือ**: Tab/Shift+Tab/Enter/Space/Escape/ลูกศร,
   focus ต้องมองเห็นและกลับจุดเดิมเมื่อปิด overlay; ทดสอบ scroll ภายในรายการ
   และฟอร์ม ปุ่มยืนยัน/ยกเลิกไม่ถูกส่วนท้ายจอบัง รองรับข้อความภาษาไทยและ IME
6. **ตรวจสิทธิ์และหมวดงาน**: OWNER, BRANCH_MANAGER, SALES, FINANCE_MANAGER,
   ACCOUNTANT, VIEWER ตามที่หน้าอนุญาต รวมผู้ใช้ไม่มีสิทธิ์และสาขาต่างกัน
   ทวน SHOP/FINANCE, การ refresh/back/forward และการคงตัวกรองตามนโยบายหน้า
7. **บันทึกผลแยก**: visual, interaction, role/data scope, responsive, copy
   พร้อมภาพ/trace/ข้อผิดพลาด หากข้อมูลไม่พอให้ระบุ BLOCKED พร้อม fixture ที่ขาด

“ทุกปุ่ม” หมายถึงทุกคำสั่งและเงื่อนไขที่แตกต่างกันของหน้าที่ผู้ใช้เข้าถึงได้
รวมปุ่มใน menu/overlay และสถานะที่ทำให้ปุ่มเปลี่ยน ไม่ใช้การกดปุ่มรูปแบบเดียว
ในแถวแรกมาแทน action ของแถวสถานะอื่น บันทึกจำนวน discovered/tested/passed/
failed/blocked ต่อหน้าจึงคำนวณความครบได้

## 5. เกณฑ์ UX/UI ที่ใช้ร่วมกัน

| หัวข้อ | เกณฑ์ตรวจ |
| --- | --- |
| Font | Noto Sans Thai Looped ใน UI ตามที่เจ้าของกำหนด; เอกสาร/PDF คงฟอนต์เดิม ขนาดและน้ำหนักเท่ากันในบทบาทเดียวกัน ไม่บังคับหัวข้อและเนื้อหาให้มีขนาดเท่ากัน |
| Fields | กลุ่ม control ปกติสูง 2.75rem (44px ที่ root 16px), desktop 14px/mobile 16px ตามระบบปัจจุบัน; textarea, editor, ช่องจำนวนใน table และยอดเงินใหญ่บันทึกข้อยกเว้นตามหน้าที่ |
| Alignment | เปรียบเทียบ top/bottom/แนวข้อความและตำแหน่ง icon; shared Select แบบ PO ใช้ icon 16px และ inset 12px ภายใน border ที่ขนาดปกติ; label เว้นที่ให้ focus ring ไม่ชนตัวหนังสือ |
| Proportions | ตัวกรองหน้าที่เดียวกันใช้สัดส่วนเดียวกัน ช่องค้นหา/ชื่อยาวกว้างตามงาน; breakpoint ที่มี sidebar กางต้องไม่บีบ field จนอ่านค่าไม่ได้ ไม่ขยายแต่ละช่องตามความยาว option โดยไร้ขอบเขต |
| Long values | ทดลองชื่อไทยยาว, รหัส/อังกฤษไม่มีช่องว่าง, จำนวนเงินยาว, หลายบรรทัด, file name ยาว และรายการจำนวนมาก; arrow/remove button คงพื้นที่ มีทางดูข้อความเต็มได้ |
| Color | ใช้ semantic tokens เดิม ตรวจ light/dark, hover/focus/selected/error/disabled และ contrast ข้อความปกติเป้าหมาย 4.5:1; รายการที่เครื่องมือสรุปไม่ได้ต้องดูเองก่อนปิด |
| Buttons | พื้นที่กดหลักบนมือถืออย่างน้อย 44×44px, เว้นปุ่มข้างกันตามการใช้งาน, icon/label อยู่กลาง, ไม่มีปุ่มนอกจอ; disabled/loading บอกเหตุผลหรือสถานะชัด |
| Overlays | กำหนดขนาดตามพื้นที่, เลื่อนเนื้อหาได้, footer ไม่ทับข้อมูล, overlay ซ้อนไม่แย่ง focus, Escape ปิดชั้นที่ถูกต้อง; menu ไม่ถูกตาราง/parent ตัด |
| Tables | header/body ตรงกัน, ตัวเลขอ่านเทียบกันได้, sort/filter/page/action ใช้ได้; ถ้าต้อง scroll ให้จำกัดใน table พร้อมไปถึงปุ่มทุกจุด ไม่ทำให้ทั้งหน้าเลื่อนแนวนอน |
| Copy/minimal | หนึ่งส่วนมีหัวข้อหลักและคำอธิบายที่จำเป็น ลดข้อความซ้ำ/ศัพท์เทคนิค ย้ายรายละเอียดเสริมไปส่วนขยาย; งานหลักมองเห็นทันที แต่ข้อมูลยอด สถานะ และเงื่อนไขสำคัญต้องยังชัด |

ใช้ UI UX Pro Max เป็นแนวทางประกอบ โดยยึดรูปแบบและ tokens ของ BESTCHOICE
ผลค้นที่นำมาใช้ตรงงานคือ text reflow/spacing, chip reflow, form labels,
submit feedback และ Select composition ไม่เปลี่ยน UI library หรือแทน native
control ทุกจุดอัตโนมัติ ต้องยืนยันหน้าที่และพฤติกรรมของ control นั้นก่อน

## 6. ชุดจอและสถานะที่ต้องทดสอบ

- ทุกหน้าที่แสดงเนื้อหาจริง: baseline ที่ 320, 390, 768, 1024, 1280, 1440,
  1512, 1920px ทั้ง light/dark โดยใช้ข้อมูลมีรายการ; หน้าที่ตั้งใจเป็น light
  อย่างเดียวบันทึกข้อยกเว้นและตรวจว่าการสลับธีมของระบบไม่ทำให้เสีย
- ทุกคำสั่งและ overlay: อย่างน้อย 390px และ 1440px; เพิ่ม 320px และจอที่เกิด
  ปัญหาเฉพาะเมื่อพบ breakpoints/ตาราง/หลายคอลัมน์ ปิดแล้วเปิดใหม่เพื่อตรวจ reset
- ทุกหน้าที่มีข้อมูล: empty/loading/error/retry และชื่อ/ยอดยาวที่ 390/1440px
  สถานะธุรกิจเพิ่มเติมให้ผูกกับ fixture และ role ของ action ที่เปลี่ยน
- ตัวอักษร root 20px และ browser zoom 200% แยกกัน ไม่อ้างว่าทดสอบอย่างหนึ่ง
  เท่ากับอีกอย่าง; ตรวจว่า label/action/ข้อมูลสำคัญไม่หาย

  ปัจจุบันผู้ใช้ยืนยันว่าไม่มี staging/เครื่องจริง จึงไม่อ้างผ่านส่วนนี้

## 8. วิธีแก้และตรวจซ้ำ

1. ปิดบัญชีหน้า/สถานะและวัด baseline ก่อนแก้ในชุดนั้น จัดระดับ P0 ใช้งานไม่ได้
   หรือข้อมูล/สิทธิ์ผิด, P1 ช่องหรือปุ่มเบียด/ซ้อน/ล้น/อ่านไม่ได้, P2 สเกล สี
   ระยะห่างและข้อความไม่สม่ำเสมอ
2. แก้ส่วนกลางก่อนเฉพาะปัญหาที่พิสูจน์ว่าใช้ร่วมกัน จากนั้นเก็บส่วนเฉพาะหน้า
   ไม่ใช้ global CSS ใหม่ไปกลบปัญหาทุกแบบ และไม่เปลี่ยน business logic เพื่อแก้หน้าตา
3. ต่อชุด: read-only code review → tests ของพฤติกรรมที่แก้ → ดูภาพหลังแก้และ
   กดซ้ำ → `npm run local:check` หลัง source ล่าสุด → เก็บ hash/ผลตรวจ
4. ถ้าแก้ shared component/CSS ให้นับทุก consumer ที่ได้รับผลเป็นรายการต้อง
   ทวนอีกครั้ง แม้เพิ่งผ่านไปในชุดก่อน ส่วนที่ไม่เปลี่ยนและไม่มีความเสี่ยงใหม่
   ใช้หลักฐานเดิมที่ระบุ source ชัดได้ ไม่รันทดสอบซ้ำโดยไม่มีเหตุผล
5. รอบปิดงานหยุดแก้ source ระหว่างรัน เปรียบเทียบรายการ routes/registry/เมนู
   อีกครั้ง เพื่อจับหน้าและปุ่มที่เพิ่มระหว่างทำงาน เก็บ fail เดิมและผล rerun
   แยกกัน พร้อมเหลือ local preview ที่ตรงกับ source ล่าสุด

## 9. หลักฐานและเกณฑ์ปิดงาน

แต่ละหน้าและ action ต้องมี page ID/surface ID, role, zone, fixture, viewport,
theme, ขั้นตอน, expected/actual result, ภาพก่อน–หลังหรือ trace, source hash,
defect ID และผลทวน ใช้ PASS / FAIL / BLOCKED / NOT_TESTED / N/A พร้อมเหตุผล
แยกกัน หน้า placeholder และ redirect ต้องยืนยันพฤติกรรมที่ตั้งใจ ไม่แสดงว่าเป็น
feature ที่เปิดใช้งานสำเร็จแล้ว

นับความครบแยก route entry, distinct surface, action และ state จากจำนวนที่
ค้นพบจริง ทุก fail/blocked ต้องมีสถานะและเหตุผลอยู่ในรายงานสุดท้าย ห้ามใช้
คำว่า “ครบทั้งระบบ” หากยังมีเส้นทางที่เข้าถึงได้หรือ action ที่ไม่อยู่ในบัญชี
และห้ามใช้ local smoke 39 ข้อแทนการตรวจทั้งโปรแกรม

ปิดส่วน local ได้เมื่อรายการที่ทดสอบได้ในสภาพแวดล้อมแยกมีหลักฐานครบ ไม่มี
P0/P1 ค้าง และทุก P2 ที่พบได้รับการแก้หรือมีข้อยกเว้นพร้อมเหตุผลชัดเจน ส่วนอุปกรณ์
และ integration จริงที่ยังไม่มีให้ระบุค้างชัดเจน ไม่รวมเป็นผลผ่าน production

ผลส่งมอบ: บัญชีครบ/ผลคลิกจริง, backlog ข้อผิดพลาด, ภาพก่อน–หลัง, รายงาน
ผลทวนตาม source, รายการข้อจำกัดจริง และลิงก์ local ล่าสุด การ deploy เป็น
ขั้นตอนแยกจากแผนตรวจนี้
