# เชื่อมยอดอนุมัติค่างวดกับสัญญา

ผู้ใช้สั่ง “จัดการให้ ใช้ได้เลย” หลังยืนยันสูตรและวันเงินเดือนแล้ว รอบนี้ลงมือให้ครบการกรอกข้อมูล → คำนวณ → อนุมัติ → เปิด/ตรวจสัญญา โดยไม่ deploy production

1. เขียนและรันเทสต์ให้ล้มก่อนแก้ทุกส่วน: สูตร Decimal, approval snapshot, ข้อมูลเปลี่ยนระหว่างพิจารณา, เพดานทุกงวดรวมงวดสุดท้าย, วันชำระ, การใช้ผลซ้ำ, UI ที่ข้อมูลยังไม่ครบ
2. เพิ่ม CreditApproval เก็บตัวเลขที่ยืนยัน เหตุผล หลักฐานอ้างอิง เวอร์ชันสูตร ผู้อนุมัติ วันเงินเดือน และการนำไปใช้ แยกจาก OCR ที่คงเดิม เก็บประวัติการทบทวนด้วย snapshot ใหม่
3. ใช้ transaction และ customer lock ร่วมกับประวัติเครดิต: อ่านภาระสัญญาที่มีอยู่ใหม่ก่อนอนุมัติและก่อนใช้ผล; ใช้ revision ของข้อมูลที่ผู้จัดการเห็นป้องกันอนุมัติจากฐานเก่า การทบทวนผลที่ยังไม่ใช้แทนผลเดิม ไม่เพิ่มสิทธิ์ซ้ำ
4. การอนุมัติ FULL ต้องมีตัวเลขและวันชำระครบ รวมผล APPROVED เก่าที่มีแค่สถานะ; PRE ไม่ใช่สิทธิ์เปิดสัญญา สูตร max(0,min((I-E-D)*50%,I*40%-D)) ปัดลงหลักร้อย ยอดอนุมัติต้องมากกว่า 0 และไม่เกินสูตร
5. บังคับใน backend ตอนสร้างสัญญา/ขายผ่อนและก่อน activate รวมการแก้เงื่อนไข: ทุกงวดต้องไม่เกินยอดอนุมัติ วันตรง snapshot ใช้หนึ่งผลต่อสัญญา ลบสัญญาไม่คืนสิทธิ์อัตโนมัติ สัญญา ACTIVE เดิมไม่ถูกเขียนตารางใหม่
6. reuse dialog คิวและประวัติเครดิต เพิ่มแบบฟอร์มยืนยันตัวเลขและยอดอนุมัติ แสดงภาระในระบบจาก server; เชื่อม approval ในหน้าเปิดสัญญาและตรวจตอน submit แผงขวายังคงไม่มีคะแนน/ผ่านไม่ผ่าน
7. ตรวจ agent review, unit/regression, types/build และ PostgreSQL/HTTP/Chromium จริงบนฐานแยก บันทึกผลและเปิด local ให้ลอง

ไม่มีนโยบายอายุผลเป็นจำนวนวันที่ผู้ใช้กำหนด จึงตรวจผลล่าสุดและฐานการเงินที่เปลี่ยนก่อนนำไปใช้ ไม่ตั้งอายุขึ้นเอง ส่วน provider/storage จริงยังขึ้นกับ config ที่เตรียมไว้ก่อนหน้า


ผลดำเนินการ 8 กันยายน 2026: ทำข้อ 1–7 แล้วบน local แยก ผ่าน API 528, web 185, PostgreSQL/HTTP 17 กรณี และ Chromium กดสร้างสัญญาจริง 12 งวดหลังอนุมัติยอด/วันเงินเดือน ดูรายละเอียดและข้อจำกัดใน `docs/review/2026-09-07-chat-credit-verification.md`. Provider/storage และ journal จริงไม่ได้ยืนยันจาก preview; ไม่มีการ deploy production
