# แบบหน้าแชทมือถือและส่วนตอบกลับ

## หน้าแชทมือถือทั้งหน้า — 15 ตุลาคม 2026 (V5 ล่าสุด)

ผู้ใช้แก้ความเข้าใจให้ชัดเจนว่า **ต้องการหน้าแชทบนมือถือทั้งหน้าโดยใช้ LINE เป็น reference ไม่ใช่เฉพาะรายการตอบด่วน** จึงออกแบบรายการแชท ห้องสนทนา ช่องพิมพ์ เครื่องมือแนบ ข้อมูลลูกค้า และโน้ตภายในร่วมกันใหม่

- [ลองหน้าแชทใหม่](http://localhost:5231/reply?screen=room)
- [รายการลูกค้า](http://localhost:5231/reply?screen=list)
- [งานทีม](http://localhost:5231/reply?screen=list&tab=team)
- [เครื่องมือแนบ](http://localhost:5231/reply?screen=room&state=tools)
- [ภาพรวมสามหน้าจอ](mobile-v5-board.png)
- [ผลตรวจ viewport และการใช้งาน](mobile-v5-checks.json)
- [ตรวจซ้ำข้อความอ้างอิงข้ามห้อง](mobile-v5-review-checks.json)

อ้างอิงจากภาพมือถือใน [คู่มือ LINE: แชทกับเพื่อน](https://guide.line.me/ja/communication/chat-friends.html) ซึ่งแสดงวันปรับปรุง 3 กันยายน 2026 และ [คู่มือส่งรูป/วิดีโอ](https://guide.line.me/ja/communication/send-images-videos.html) โดยเปิดตรวจภาพ `linetalk_03.png` และ `linetalk_04.png` จริง: หัวห้องขนาดสั้น พื้นที่บทสนทนาต่อเนื่อง ช่องพิมพ์ติดล่าง เครื่องมือแนบด้านข้าง และยุบปุ่มแนบเพื่อขยายช่องพิมพ์ขณะพิมพ์ ไม่ได้ตรวจ LINE บนเครื่องมือถือจริง

นำรูปแบบดังกล่าวมาปรับกับ BESTCHOICE ดังนี้:

- รายการใช้แท็บลูกค้า / งานทีมที่เห็นชัดพอกัน งานทีมเป็นทางเข้าคิวและโน้ตเดิม ไม่สร้างระบบแชททีมใหม่ และเปิดอ่านงานไม่ถือว่าทำงานเสร็จ
- เมื่อเข้าห้อง เหลือหัวห้อง 64px ชื่อและช่องทาง แตะชื่อเปิดข้อมูลลูกค้า ส่วนมอบหมาย ปักหมุด บอท แจ้งเตือน และปิดงานอยู่ในเมนูห้อง สถานะบอทปรากฏเป็นแถบเมื่อเปิดใช้
- ข้อความเข้า/ออกเป็นบับเบิลคนละด้าน ข้อความหลัก 16px เวลาเป็นข้อความรอง โน้ตใช้สีและชื่อกำกับว่าภายใน
- Composer เริ่มที่ 103px รวมโหมดตอบและช่องพิมพ์: แนบรูปได้โดยตรง กด + เปิดเครื่องมือ เมื่อพิมพ์ยุบปุ่มรูปและเปลี่ยนไมค์เป็นส่ง การขยายเครื่องมือคงท้ายบทสนทนาไว้เมื่อผู้ใช้อยู่ท้ายรายการ
- โหมดโน้ตมีสี ข้อความ “ลูกค้าไม่เห็น” และเครื่องหมายถูกสำหรับบันทึก เก็บร่างแยกจากข้อความลูกค้าและแยกตามห้อง รูปแนบไม่ติดไปกับโน้ต
- แตะบับเบิลเพื่ออ้างอิงคำตอบได้ ข้อความอ้างอิงแยกตามห้อง ตอบด่วนใช้ต้นแบบ V4 เป็นเครื่องมือรองและปรับชื่อลูกค้าตามห้องที่เปิด
- คง Noto Sans Thai Looped และสี Emerald ของ BESTCHOICE ไม่ใช้ฟอนต์จากชุดแนะนำทั่วไป ไม่มีการเพิ่มปุ่มโทรที่ยังไม่มี flow รองรับ

ใช้ UI UX Pro Max: `mobile chat navigation --domain ux` ได้ Back Button และ Sticky Navigation ที่ตรงกับงาน ส่วน `input keyboard safe area --stack html-tailwind` ได้ Input sizing และ Focus visible เท่านั้น ไม่ได้ใช้เป็นหลักฐานยืนยันพฤติกรรม keyboard/safe area จริง คำค้น design-system `customer messaging mobile minimal` และ retry `messaging collaboration app` ให้โครง landing page ซึ่งไม่ตรงกับหน้าสนทนา จึงไม่ใช้โครงหรือชุดฟอนต์/สีเหล่านั้น แบบนี้ยึด reference LINE และ design tokens เดิมเป็นหลัก

ผลวัดพื้นที่ข้อความ (ต้นแบบมีแถบแจ้งข้อมูลจำลอง 20px อยู่ด้วย):

| จอ | หน้าปัจจุบันจาก baseline | ต้นแบบ V5 |
|---|---:|---:|
| 320×568 | 43px | 381px |
| 375×667 | 114.5px | 480px |
| 390×844 | 343.5px | 657px |

เป็นการเปรียบเทียบพื้นที่ layout จากข้อมูลจำลองต่างชุด ไม่ใช่ผล usability study หรือการยืนยันประสิทธิภาพ production ตรวจ 14 viewport/theme กรณี: 320/375/390/430px สองธีม และ 375×440, 844×390, 768×1024 สองธีม ตรวจปุ่มอย่างน้อย 44 CSS px ไม่ล้นแนวนอน ค้นหา/กรอง การย้อนกลับ รายห้อง/ร่างโน้ต/ร่างลูกค้า สื่อแนบโดยไม่ส่งทันที ตัวรับข้อความสำเร็จรูป สถานะบอท และทางเข้างานทีม ตรวจ reduced motion ในจอสั้น/แนวนอน/แท็บเล็ตด้วย

Read-only reviewer พบ quote preview ค้างข้ามห้องและการเลือกแท็บด้วยแป้นพิมพ์ไม่เก็บ history แก้ทั้งสองจุดและตรวจซ้ำแล้ว ปรับพื้น tint จอสว่างเป็น `#eaf6ef` ให้ตัวอักษรสีหลักบนพื้นอ่อนมี contrast 4.51:1 คู่ข้อความหลัก/รอง โน้ต และปุ่มส่งตรวจทั้งสองธีม

ไฟล์ `mobile-chat-line-v5.html` เป็น source ของหน้าใหม่; `.tmp/chat-mobile-redesign/build-mobile-v5.mjs` รวมส่วนตอบด่วนจาก `quick-v4.html` แล้วสร้าง `reply-v2.html` ซึ่งเป็น entry ที่ server `/reply` ใช้อยู่ หน้า `/` แสดง `mobile-chat-line-v5-board.html` ผ่าน entry เดิม การปรับรอบนี้เป็นต้นแบบที่กดใช้งานได้ ไม่มี API ส่งแชท/อัปโหลด/ไมโครโฟนจริง ยังไม่ได้แทนหน้าแชทในแอปจริง และไม่ได้ทดสอบคีย์บอร์ดหรือ safe area บน iPhone/Android จริง

## ปรับรายการตาม LINE / LINE OA — 15 ตุลาคม 2026 (V4 รอบก่อน)

ผู้ใช้ยืนยันว่าต้องการออกแบบ **หน้ารายการข้อความ** ใหม่ และให้ไปดู LINE แล้วนำรูปแบบมาใช้ จึงตรวจหน้าจอแอป LINE บน Mac ที่เปิดอยู่ และภาพหน้าจอในคู่มือ LINE Official Account ของผู้ให้บริการ ไม่ได้เข้าบัญชี LINE OA จริงหรือทดสอบแอปมือถือจริง ข้อความและภาพในต้นแบบเป็นข้อมูลจำลอง ไม่คัดลอกข้อมูลในห้องสนทนาส่วนตัวมาใช้

- [ลองต้นแบบล่าสุด](http://localhost:5231/reply?state=quick)
- [ภาพสามสถานะ V4](quick-v4-board.png)
- [ผลตรวจ V4](quick-v4-checks.json)

สิ่งที่อ้างอิง: รายการเรียบ ชื่อเด่นกับตัวอย่างสั้น ช่องค้นหาด้านบน และขั้นตอนเลือกจากรายการไปดูตัวอย่างก่อนใช้ ภาพ LINE OA แสดงรายการและตัวอย่างคู่กันบนเดสก์ท็อป จึงปรับเป็นสองหน้าต่อเนื่องบนมือถือ ไม่ได้กล่าวว่าหน้าต้นแบบเหมือน LINE OA มือถือปัจจุบันทุกจุด

สิ่งที่ปรับสำหรับ BESTCHOICE: แผงเต็มหน้ามือถือ แตะทั้งแถวเพื่อดูตัวอย่าง ลดปุ่ม “ใช้/ดู” ที่ซ้ำในทุกรายการ ใช้ตัวกรองหมวดแบบเลือกเพื่อไม่ต้องเลื่อนชิปหลายอัน ตัวอย่างเป็นบับเบิลแชท แสดงแก้ข้อความเมื่อกดปุ่มเท่านั้น และใช้ปุ่มหลักด้านล่างเพื่อใส่ในร่างก่อนกดส่ง คง Noto Sans Thai Looped และสี BESTCHOICE การกลับรายการเก็บคำค้น หมวด ตำแหน่งเลื่อน และข้อความที่แก้ ข้อความพร้อมรูปจะแสดงทั้งสองส่วนก่อนนำไปเตรียมใน composer

แหล่งอ้างอิงที่เปิดตรวจ:

- [คู่มือ LINE OA — Chat](https://www.lycbiz.com/jp/manual/OfficialAccountManager/chats/) หน้าแสดงวันปรับปรุง 18 สิงหาคม 2026
- [ภาพหน้ารายการและตัวอย่างข้อความ](https://www.lycbiz.com/sites/default/files/inline-images/chat_contents.png)
- [ภาพหน้าจอการตั้งค่าบนมือถือ](https://www.lycbiz.com/sites/default/files/inline-images/chat_app3.png)
- [คู่มือ PDF ของ LINE OA](https://go.lycbiz.com/rs/265-EZN-548/images/oa_manual_240228.pdf?version=0) ใช้หน้า PDF 8 เป็นภาพเสริมเก่าของโครงเมนูมือถือ ไม่ใช่หลักฐานว่าเป็นหน้าตาปัจจุบัน

UI UX Pro Max query `list selection mobile --domain ux` ให้ Mobile First และ overscroll containment ที่ใช้กับแผงเลื่อนในต้นแบบ ส่วนรูปแบบรายการและตัวอย่างยึดจากภาพอ้างอิงจริงข้างต้น ขนาดพื้นที่แตะยังใช้เป้าหมาย 44 CSS px ของรอบก่อน

ผลตรวจเป็น viewport จำลอง 320/375/390/430px ทั้งสองธีม และจอสั้น 320×568, 375×440, 844×390 ตรวจการค้นหา หมวด ไม่พบข้อมูล การแก้แล้วกลับ การห้ามเลือกข้อความว่าง focus การต่อท้ายร่างเดิม รูปแนบ และไม่ส่งอัตโนมัติ ดูรายละเอียดในผลตรวจ V4 ยังไม่ใช่การตรวจแป้นพิมพ์เครื่องจริงหรือ API ขณะส่ง ขณะนี้เปลี่ยนเฉพาะต้นแบบใน docs ไม่ได้แก้หน้าตอบด่วนของแอปจริง

`reply-v2.html` และหน้า `/reply` แสดง V4 ล่าสุด เก็บ V3 ก่อนเปลี่ยนไว้ที่ `quick-v3.html` และ `quick-v3-board.html` ภาพและผลตรวจ V2/V3 ด้านล่างเป็นหลักฐานรอบเก่า

## ปรับหน้าข้อความสำเร็จรูป 15 ตุลาคม 2026

ผู้ใช้ขอเปลี่ยน “ตอบด่วน” จึงร่างหน้ารายการข้อความใหม่ในต้นแบบเดียวกัน โดยถามเพิ่มเติมว่าต้องการเปลี่ยนรายการ ชื่อปุ่ม หรือเอาปุ่มออก ระหว่างรอใช้แนวทางปรับรายการเป็นหลัก ยังไม่ได้เปลี่ยนชื่อปุ่มหรือถอดปุ่มจาก composer

- [ลองหน้าข้อความสำเร็จรูปใหม่](http://localhost:5231/reply?state=quick)
- [ภาพสามสถานะ](quick-v3-board.png)
- [ผลตรวจเฉพาะต้นแบบ](quick-v3-checks.json)

รายการเต็มความกว้าง มีค้นหาตามชื่อ เนื้อหา หมวด และคำย่อ แยกหมวดแบบเลื่อนแนวนอน กด “ใช้” สำหรับข้อความล้วนเพื่อเพิ่มต่อท้ายร่างเดิม หรือแตะชื่อเพื่ออ่านและแก้เต็มหน้า การกลับรายการคงคำค้น หมวด ตำแหน่งเลื่อน และข้อความที่แก้ในครั้งนั้นไว้ รายการมีรูปต้องเปิดตัวอย่างก่อนนำข้อความและไฟล์ตัวอย่างไปเตรียมใน composer ไม่มีการส่งจริง

UI UX Pro Max query `search filter empty state --domain ux` ได้ Empty States และ No Results ที่ตรงกับการค้นหา จึงเพิ่มทางกลับไปดูข้อความทั้งหมดเมื่อค้นไม่พบ ส่วน `dialog keyboard focus --stack html-tailwind` ได้ Focus visible / Focus states สำหรับปุ่มและการกลับไปยังช่องพิมพ์

ทดสอบ 320/375/390/430px ทั้งสองธีม พร้อมการค้นหา กรองหมวด คำค้นไม่พบ แก้แล้วกลับรายการ รักษาร่างเดิม เตรียมรูปโดยไม่ส่งอัตโนมัติ และพื้นที่ปุ่ม/ชื่อหมวดไม่ถูกตัด ตรวจเพิ่มจอ 320×568, 375×440, 844×390 สำหรับปุ่มหลักและ Escape/focus ทั้งหมดเป็น viewport ของต้นแบบ ไม่ใช่คีย์บอร์ดเครื่องจริง การส่ง canned response จริงแบบหลายชนิดและการจัดการส่งไม่ครบยังต้องออกแบบเชื่อม API และทดสอบเมื่อทำในแอปจริง

ไฟล์ `reply-v2-original.html` และ `reply-v2-board-original.html` เก็บแบบก่อนปรับตอบด่วนไว้ หน้าพรีวิว URL เดิมแสดงแบบใหม่ล่าสุด ส่วนไฟล์ผลตรวจ V2 และภาพเก่าเป็นหลักฐานรอบก่อนหน้า

โครงหน้ารายการลูกค้า / งานทีม / ห้องสนทนาใน [แบบแรก](proposal.png) ได้รับความเห็นชอบแล้ว ผู้ใช้ขอออกแบบส่วนตอบลูกค้าใหม่ จึงทำต้นแบบ V2 สำหรับส่วนนี้ โดยยังไม่มีการแก้โค้ดแอปจริงในรอบออกแบบ

- [ลองกดต้นแบบ V2](http://localhost:5231/reply)
- [ดูสามสถานะพร้อมกัน](http://localhost:5231/)
- [ภาพแบบใหม่](reply-v2-board.png)

V2 ให้พื้นที่พิมพ์เต็มความกว้างและขยายตามข้อความ แยกแถวเครื่องมือด้านล่างเป็นแนบ ตอบด่วน ไมค์ และส่ง ส่วนเครื่องมือที่เหลือเปิดจากแผงด้านล่าง โหมดโน้ตยังเลือกได้โดยตรง มีสีและข้อความบอกว่าลูกค้าไม่เห็น พร้อมปุ่ม “บันทึก” และเครื่องหมายถูก

ต้นแบบลองพิมพ์ เลือกข้อความตอบด่วน สลับโหมดโดยเก็บข้อความร่างแยกกัน แนบไฟล์ตัวอย่างและกดส่งภายในหน้าได้ ทุกการทำงานเป็นข้อมูลในเบราว์เซอร์ ไม่มีการส่งแชทจริง อัปโหลดไฟล์จริง เปิดไมโครโฟน หรือเชื่อม API แอป การแสดงไฟล์แนบก่อนส่งเป็นพฤติกรรมที่เสนอในแบบนี้ ยังไม่ใช่ผลจากระบบจริง

ใช้ UI UX Pro Max ประกอบการเลือกพื้นที่แตะและระยะห่าง ค้น `touch target spacing --domain ux` ได้แนวทาง Touch Spacing / Touch Target Size ที่ตรงกับโจทย์ โดยเลือกพื้นที่แตะอย่างน้อย 44 CSS px เป็นเป้าหมายของต้นแบบเว็บนี้ ค้น `input label feedback --stack html-tailwind` ได้แนวทางชื่อกำกับปุ่มไอคอนและการจัด label แบบกระชับ

ตรวจต้นแบบที่ 320/375/390/430px สองธีม รวมแปดกรณี: ไม่ล้นแนวนอน ปุ่มที่มองเห็นมีพื้นที่อย่างน้อย 44px ข้อความร่างแยกโหมด เลือกตอบด่วนหรือไฟล์แล้วไม่ส่งทันที และล้างร่างหลังส่งตัวอย่าง ตรวจเพิ่มที่ 320×568, 375×440, 844×390: Enter ขึ้นบรรทัดใหม่ ปุ่มส่งยังเห็น และปิดแผงด้วย Escape แล้วคืน focus รวมถึงตรวจ focus กลับช่องพิมพ์หลังเลือกตอบด่วน ดู [ผลตรวจต้นแบบ](reply-v2-checks.json)

การลดความสูง viewport ไม่ใช่การทดสอบแป้นพิมพ์จริงบน iPhone/Android ส่วนการส่งล้มเหลว การส่งซ้ำ การกลับไปมาระหว่างห้อง สิทธิ์ และ API ต้องตรวจอีกครั้งตอนนำแบบเข้าระบบจริง ผลตรวจในเอกสารนี้ไม่ใช่การรับรอง production
