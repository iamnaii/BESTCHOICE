# คำตอบที่พนักงานส่งจาก Meta ปิดรอบรอตอบ (FB echo → ปิด response cycle)

วันที่ 2026-11-26 · สถานะ: รอเจ้าของอ่านสเปก · ขอบเขต: API อย่างเดียว ไม่มี migration ไม่แตะหน้าเว็บ

## ปัญหา

เปิดสวิตช์ "คิวงานแชท" (`chat_work_queue_enabled`) แล้ว ห้องแชทหน้าร้านไม่หลุดจากแท็บ "รอตอบ" อีกเลย
แม้พนักงานตอบแล้ว เพราะพนักงานหน้าร้านตอบแชท Facebook ผ่าน Meta Business Suite ทั้งหมด ไม่ได้ตอบใน
inbox ของเรา

หลักฐานบน prod (อ่านอย่างเดียว 2026-11-26):

| ข้อเท็จจริง | ค่า |
|---|---|
| ข้อความพนักงานในห้อง FB ที่ส่งจาก inbox ของเรา (มี `client_message_id`) | 0 ต่อสัปดาห์ 4 สัปดาห์ติด (สัปดาห์ 23 พ.ย. = 3) |
| echo จาก Meta | 3,600–8,000 ต่อสัปดาห์ |

สเปกเดิม `2026-10-05-chat-operations-six-features-design.md` เขียนไว้ว่า "ส่งสำเร็จ/echo STAFF/ปิดงานล้าง"
`waitingSince` และให้บันทึก "ไม่ทราบผู้ตอบ" สำหรับ echo ของเพจ แต่โค้ดทำไม่ตรง:

- `RoomManagerService.confirmExternalEcho` → `ResponseCycleService.confirmUnknownEcho` แค่ประทับว่าส่งถึงแล้ว
  ไม่ปิดรอบ ไม่ล้าง `waitingSince` (`response-cycle.service.ts:221`)
- `MessageRouterService.mirrorOutbound` ข้าม `clearWaiting` เมื่อ `confirmExternalEcho` คืน `true`
  (`message-router.service.ts:876-882`)
- ทางเดียวที่ปิดรอบได้คือส่งจาก inbox ของเรา (`confirm` → `closeHumanInTx`) ซึ่งไม่มีใครใช้

งานนี้แก้โค้ดให้ตรงกับสเปกเดิม

  ข้อความทักทายเดิมไม่ได้ (นับ "ขาออกใบเดียวพอดี" ณ เวลาที่เรียก)

## กติกาเดียว: echo นี้เป็นคนตอบไหม

echo ของพนักงาน (`role = STAFF` จาก `mirrorOutbound`) **เป็นคนตอบ** เมื่อครบทั้งสองข้อ:

1. **ไม่ใช่ข้อความทักทายใบแรกของห้อง** — `shouldSkipFirstOutboundClear(roomId, messageId)` ตัวเดิม
   (ขาออกใบแรกของห้อง + มาภายใน 60 วิ นับจาก `waitingSince`) — เรียกหลังบันทึก echo เหมือนเดิม
2. **ไม่มีข้อความลูกค้าในห้องเดียวกันที่บันทึกภายใน 5 วินาทีก่อน echo** — มีข้อความ `CUSTOMER`
   (`deletedAt = null`) ที่ `createdAt` อยู่ในช่วง `[echo.createdAt − 5 วิ, echo.createdAt]` = ข้อความอัตโนมัติ

ทั้งสองฝั่งเป็นเวลาที่เซิร์ฟเวอร์เราบันทึก (`createdAt` default now) จึงเทียบกันได้ตรง ข้อความลูกค้าที่ประมวลผลช้า
(ดึงโปรไฟล์) ทำให้ระยะดูสั้นกว่าจริง → ตกข้อ 2 → ห้องค้างในคิว — ผิดได้ทางเดียวคือทางปลอดภัย

โค้ด:

- ฟังก์ชันล้วน `isHumanStaffEchoTiming({ echoAt, customerAtBefore })` + ค่าคงที่
  `PAGE_AUTOREPLY_MAX_DELAY_MS = 5_000` ใน `chat-engine/utils/staff-echo-rule.ts` (ใหม่) — ไม่แตะฐานข้อมูล
  ทดสอบเป็นตารางได้
- `RoomManagerService.isHumanStaffEcho(roomId, messageId): Promise<boolean>` — อ่านเวลา echo + ข้อความลูกค้า
  ใบล่าสุดที่ไม่เกินเวลา echo + เรียก `shouldSkipFirstOutboundClear` แล้วส่งเข้าฟังก์ชันล้วน
  **ผู้เรียกทุกทางใช้ตัวนี้ตัวเดียว** ห้ามเขียนเงื่อนไขชุดที่สอง

## ทางของ echo หลังแก้

`MessageRouterService.mirrorOutbound` (หลัง `saveMessage` ของ echo สำเร็จ):

```
human = role === STAFF && await roomManager.isHumanStaffEcho(room.id, saved.id)
tracked = await roomManager.confirmExternalEcho(saved.id, { closeAsHuman: human })
if (!tracked && human) await roomManager.clearWaiting(room.id)
```

- **เปิดสวิตช์คิวงานแชท** (`tracked = true`): `confirmExternalEcho` → `ResponseCycleService.confirmUnknownEcho
  (messageId, { closeAsHuman })` ใน transaction เดิม หลังล็อกห้อง (`lock` — `SELECT … FOR UPDATE` ตัวเดียวกับ
  ตอนลูกค้าทัก):
  1. ประทับส่งถึงแล้ว (`outboundSentAt`, `CONFIRMED`) เหมือนเดิม
  2. `closeAsHuman` ไม่จริง → จบ (ข้อความอัตโนมัติ / ทักทาย ไม่ปิดรอบ)
  3. หารอบที่เปิดอยู่ของห้อง — ไม่มี → จบ · **รอบเริ่มหลัง echo** (`startedAt > echo.createdAt`) → จบ
     (echo ตอบข้อความเก่า ไม่ใช่ข้อความที่เปิดรอบนี้)
  4. เส้นแบ่ง = ข้อความ `CUSTOMER` ที่ `inboundSequence` ไม่ว่างและ `createdAt ≤ echo.createdAt` ใบที่
     `inboundSequence` มากสุด — ไม่มี → จบ
  5. เขียนลง echo: `cycleId` = รอบที่เปิด · `answeredThroughSequence` · `answeredThroughMessageId`
  6. `closeHumanInTx({ roomId, cycleId, messageId, answeredThroughMessageId, staffId: null,
     sentAt: echo.createdAt })` ตัวเดิม → `endReason HUMAN_REPLY` · `firstHumanSentAt = echo.createdAt` ·
     `firstHumanStaffId = null` · `waitingSince = null` · ข้อความลูกค้าหลังเส้นแบ่ง → เปิดรอบใหม่ทันที
- **ปิดสวิตช์คิวงานแชท** (`tracked = false`): ล้าง `waitingSince` เมื่อ `human` เท่านั้น — เดิมล้างทุก echo
  ยกเว้นข้อความทักทาย ⇒ ข้อความอัตโนมัติไม่ปลดห้องแล้ว (ความหมายเดียวกันทั้งสองโหมด)

echo ซ้ำจาก Meta (ส่งซ้ำ) ชน unique `externalMessageId` แล้วจบที่ `saveMessage` เหมือนเดิม — ไม่ถึงขั้นนี้

## สิ่งที่ไม่เปลี่ยน

- การหยุดบอทเมื่อพนักงานตอบ (`pauseAiForStaffEcho`) — กติกาของตัวเอง ไม่แตะ
- ส่งจาก inbox ของเรา (`prepareAttempt` → `confirm` → `closeHumanInTx`)
- ฝั่งการเงิน (LINE ไม่มี echo แบบนี้) · ผู้ดูแลห้อง (echo ไม่มี `staffId` จึงไม่ตั้งเจ้าของห้อง — เหมือนเดิม)
- ลำดับแชทในแท็บรอตอบ — กลับมาคุยหลังงานนี้ขึ้นระบบ (คิวจะเหลือแต่ห้องที่รอจริง)
- รายงานแชท — นับ "ไม่ทราบผู้ตอบ" อยู่แล้ว (`chat-analytics-v2.service.ts:97, :156`)

## ข้อจำกัดที่รู้

- พนักงานที่ตอบภายใน 5 วินาทีหลังลูกค้าทัก (ราว 3% ของคำสั้น) — รอบไม่ปิด ห้องค้างจนพนักงานส่งข้อความ
  ถัดไป
- พนักงานกดข้อความสำเร็จรูปตอบภายใน 5 วินาที — นับเป็นข้อความอัตโนมัติ (เหมือนข้อบน)
- ข้อความอัตโนมัติที่ข้อความลูกค้าต้นเหตุถูกบันทึก **หลัง** echo (1 ใน 425 ของ "อัปเดตสต๊อค") — ถ้ามีรอบเก่า
  เปิดอยู่ รอบเก่าจะถูกปิดว่าคนตอบ แล้วข้อความลูกค้าใบใหม่เปิดรอบใหม่ทันที — ห้องยังอยู่ในคิว เสียแค่ตัวเลขของ
  รอบเก่า
- ข้อความที่เพจหน่วงเกิน 5 วินาที (ถ้าเจ้าของตั้งไว้ใน Meta) จะนับเป็นคนตอบ
- echo ที่ Meta ส่งมาช้าเกิน 5 วินาที ขณะลูกค้าทักแทรกระหว่างพนักงานกดส่งกับเวลาที่เราบันทึก echo — ข้อความที่แทรกถูกนับว่า
  ตอบแล้ว (เวลา echo = เวลาที่เราบันทึก ไม่ใช่เวลาส่งจริงของ Meta) · ทางแก้ถ้าพบจริง: ส่งเวลา event ของ Meta เข้า `mirrorOutbound`
- ห้องค้างแบบเก่าก่อนเปิดสวิตช์ (ข้อความลูกค้าไม่มีเลขลำดับ) echo ไม่ปิด — ต่างจากส่งจาก inbox ที่ `prepareAttempt` ใช้ตัวนับของห้อง
  (prod ล้างห้องค้างฝั่ง SHOP ทั้งหมดแล้ว 2026-11-26 จึงไม่มีห้องแบบนี้)
- echo ของข้อความที่ส่งจาก inbox ของเราเองไม่ถึงทางนี้ — controller ข้าม echo ที่ `app_id` = `FACEBOOK_APP_ID` (ตั้งไว้บน prod)
- บันทึก echo สำเร็จแต่ปิดรอบล้ม (ฐานข้อมูลสะดุด) → Meta ส่งซ้ำถูกกันด้วย `externalMessageId` ซ้ำ ⇒ รอบไม่ปิด ห้องค้างในคิว (ทางปลอดภัย ·
  ช่องเดิมก่อนงานนี้)
- เกณฑ์ 5 วินาทีเป็นค่าคงที่ในโค้ด ไม่มีหน้าตั้งค่า (เปลี่ยน = แก้โค้ด)

## ทดสอบ

1. **ฟังก์ชันล้วน** (`staff-echo-rule.spec.ts`) — ตาราง: ไม่มีลูกค้าก่อนหน้า · 4.999 วิ · 5 วิพอดี (ขอบ =
   อัตโนมัติ) · 5.001 วิ (ลูกค้าหลัง echo ไม่นับ — ทดสอบที่ `RoomManagerService.isHumanStaffEcho`
   ซึ่งเป็นผู้เลือกข้อความลูกค้าใบที่ส่งเข้ากติกา)
2. **`ResponseCycleService.confirmUnknownEcho`** (db.spec บนฐานทดสอบแยก — ยังไม่มีเทสต์ของ service นี้เลย):
   ปิดรอบด้วย echo คน (`HUMAN_REPLY` · `firstHumanStaffId` null · `firstHumanSentAt` = เวลา echo ·
   `waitingSince` null) · ข้อความลูกค้าหลังเส้นแบ่งเปิดรอบใหม่ · `closeAsHuman = false` ไม่ปิด ·
   ไม่มีรอบเปิด = ไม่ทำอะไร · รอบเริ่มหลัง echo = ไม่ปิด · ไม่มีข้อความลูกค้าที่มีเลขลำดับ = ไม่ปิด
3. **ทางจริงผ่าน `mirrorOutbound`** (db.spec) — เปิดสวิตช์: ลูกค้าทัก → echo หลัง 30 วิ → รอบปิด ·
   echo หลัง 2 วิ → รอบเปิดอยู่ · ข้อความทักทายใบแรก → รอบเปิดอยู่ · ปิดสวิตช์: echo คนล้าง `waitingSince` ·
   echo อัตโนมัติไม่ล้าง
4. **รายงาน** — ไม่เพิ่มเทสต์: ตัวนับ `unknownStaffCycles` (`chat-analytics-v2.service.ts:97`) กรอง
   `origin LIVE` + `first_human_sent_at` ไม่ว่าง + `first_human_staff_id` ว่าง ซึ่งเทสต์ข้อ 2 ยืนยันทั้งสามค่า
   บนแถวรอบแล้ว · ห้องที่ปิดรอบจะหลุดจากคิวกระจายงาน (`ChatDispatchService` อ่าน `waitingSince`) ด้วย — ถูกต้อง
5. เทสต์เดิมของ `message-router.service.spec.ts` ส่วน `clearWaiting`/`shouldSkipFirstOutboundClear` ปรับตาม
   (mock `isHumanStaffEcho` แทน)

## ขึ้นระบบ

- ไม่มี migration · ไม่มีค่าตั้งใหม่ · ไม่แตะเว็บ (ไม่ต้องขยับเลขเวอร์ชันเว็บ)
- หลัง deploy ตรวจบน prod ภายในวันแรก (อ่านอย่างเดียว): รอบที่ปิดด้วย `HUMAN_REPLY` + `firstHumanStaffId`
  null เพิ่มขึ้น · แท็บรอตอบเหลือเฉพาะห้องที่ข้อความล่าสุดเป็นของลูกค้า/ข้อความอัตโนมัติ · แจ้งเตือน `CHAT_SLA`
  ใหม่ลดลงชัดเจน
- ระหว่างยังไม่ deploy คิวจะสะสมใหม่ทุกวัน (สวิตช์ยังเปิด) — เคลียร์ซ้ำได้ด้วยคำสั่ง SQL ชุดเดียวกับ 2026-11-26
